# Execution Authority

The durable Trade chain is `Broker Update → immutable Prepared Transaction → Runtime Persistence Store → ordered Projection →
Projection Ready → durable Outbox`. Each Fill is an independent transaction; the Order is the cumulative authority.

PR4.3.2 opens Generic T0 Cash LIMIT BUY OPEN partial-fill accounting. Order alone determines terminal Fill; Position/Allocation
retain exact cumulative cost; independent Order Fee Accrual converts cumulative fee targets into Fill deltas; cash and Risk
reservations consume incrementally; Account, Strategy Ledger and Risk receive explicit deltas. Each Fill remains one immutable,
Projection Ready transaction with a contiguous per-Order Fill index. Duplicate Fill identity is idempotent and conflicting payload
fails before authority mutation. See ADR 0049, ADR 0050 and `execution_trade_planning.md`.

PR4.3.3 adds the plugin-owned deterministic Virtual Broker Fill Plan and complete Generic T0 Cash LIMIT BUY OPEN Multi-Fill
Recovery. WHOLE, legacy MAX_PER_BAR and explicit SCHEDULE share one execution chain; ONE_PER_BAR and ALL_DUE produce one
independent immutable Runtime transaction per Step. Broker execute-before-publish, Commit, Projection, Outbox and partial-plan
checkpoint boundaries recover through the existing phases. The same Fill Plan is now also proven for Long Close.

PR4.4.2 completes the deliberately narrow Close slice in that same chain: `GENERIC_T0_CASH + LIMIT + SELL + CLOSE + LONG +
NETTING`, cash account, one currency and Margin disabled. Every partial or final Fill is an independent transaction. The Planner captures existing Position, Allocation,
Position Reservation, Risk Reservation, Account, Strategy Ledger, fee, settlement and valuation authority before producing one
immutable transaction. Its projection order is Order, Position, Allocation, Settlement, Order Fee Accrual, Fee, Account,
Strategy Ledger, Position Reservation, Risk Reservation, Risk and Valuation. Removed non-durable execution source is absent;
unsupported shapes fail closed.

Position is the single realized-PnL authority: `(fill price × fill quantity - exact released cost) × multiplier`. Position and
Allocation use one cumulative-cost reducer; partial fills release `cumulative cost × fill quantity / quantity before`, while the
final Fill releases every remaining cost unit and sets cumulative cost exactly to zero. Allocation, Account, Strategy Ledger and
committed fact consume that exact delta. Gross cash inflow is sale notional,
net cash inflow is notional less the authoritative Fee instruction. Close carries no cash Reservation; its Position Reservation
is consumed inside the same ordered projection batch. Existing Fill identity/index, Coordinator, recovery phases, Event Gate and
at-least-once Outbox semantics are unchanged. Partial Fill Cancel/Reject/Expire uses an `ORDER_TERMINAL` transaction with stable
`ETERM-...` identity, no Trade ID and four ordered projections. Same identity/same payload is idempotent; a conflicting payload
fails closed. Terminal Facts are excluded from Trade Results. Short, Hedging, CloseToday/CloseYesterday, Futures/Margin and
SIM/Live products remain outside this implemented Backtest scope. SIM 的相同经济 shape 由共享 Trading Kernel 和独立 streaming
product tests 证明；Live 仍是未来目标。See ADR 0053 and ADR 0068.
# Attributed Close Cost

`OnlyTradeExecutionTransactionPlanner` 在 reducer 前创建 `OnlyAttributedCloseCostAuthority`。只有 builder 调用平均成本归约函数；Position 和 Allocation reducer 安装 Authority 给出的 after state，不再独立计算 released cost 或 PnL。缺失 Allocation、scope 冲突、数量不足或 Position 成本无法由 Allocation 聚合解释时，在 commit 前 fail closed。

## Rust component execution boundary

`crates/onlyalpha-kernel/execution/` composes the isolated Order, Position, Account, Strategy Ledger and Risk libraries through public immutable inputs and their canonical checkpoint/restore readers. Domain is the only additional local dependency. This library is not an activated Runtime participant, second production persistence store or LIVE permission.

The bounded shape is single-currency Generic T0 Cash LIMIT or MARKET BUY OPEN / SELL CLOSE LONG NETTING, including admission, explicit submission outcome, external acceptance, pending cancellation, partial/full fills and terminal cancellation/rejection/expiry/failure. Explicit scoped plugin fee cumulative targets produce incremental cash charges/rebates; settlement requires a proved Generic T0 cash/settled-quantity instruction. No missing fee, market permission or settlement is interpreted as zero/available. Position remains the single attributed close-cost authority, including fractional proportional cost and the final all-remainder rule. Non-cash cost/PnL preserves exact admitted precision; currency settlement amounts retain their owning money precision.

MARKET requests retain `price: null`. Their admission `market` proof requires an explicit canonical `reference_price` (`schema_version`, `value`, `precision`) to bind notional and the funding envelope; the reference is not an Order limit. The existing scoped market evidence occurrence and committed input bind that value. A MARKET Fill requires its own explicit `price_precision`; the exact positive Fill price must fit that declared precision without rounding. Reference and Fill precision are independent of the instrument's venue order-price precision, which is not rewritten. LIMIT admission, limit checks and Fill wire fields retain their existing semantics. Both shapes continue through the same fee, cash/position reservation, Risk budget, commit and recovery authorities. Actual Fill notional must remain within the admitted reservation budget; missing reference, precision, funding or fee/settlement proof fails closed. This bounded native support does not re-authorize historical facts or extend the older capability-policy-v1 resolver.

The Execution envelope and retained ADMIT payload1 remain unchanged. Explicit ADMIT payload2 adds exactly `settlement_fill_contract` to the existing request, Fee contract/budget, market proof, Order identity and collateral fields. It is restricted to BACKTEST MARKET Orders and a one-Fill model. The contract fields are `schema_version: 1`, `kind: BACKTEST_WHOLE_FILL`, `maximum_fill_count: 1`, the complete `model`, `model_fingerprint`, and `fee_estimate_assumptions_fingerprint`. The model has schema1, `kind: GUARANTEED_WHOLE_FILL`, BACKTEST, a maximum of one Fill, `configuration_fingerprint` and `policy_fingerprint`. Configuration must match the actual canonical composition; policy must match the canonical request's retained `metadata.replay_policy`; Fee assumptions must match the actual Order Fee estimate. All shapes and fingerprints are exact. A caller-supplied SHA without that manifest cannot select this profile.

The canonical Settlement owner retains the admission contract and reserves one possible whole Fill instead of all quantity quanta. Execution retains the same binding with the Order relation and rechecks it before a Fill; both owners reject any partial or distinct second model Fill. An actual whole Fill still traverses the existing Risk, funding, Fee, Order, Position, Ledger and Account paths. SIM/LIVE reject payload2 and retain their existing resource semantics; there is no venue-specific Core rule or permission inferred from a model DTO. Settlement schema2 marks the new retained resource profile inside the existing atomic metadata projection, without rewriting old ADMIT or conservative Settlement records.

Prepared payloads lock complete before/result component identities and exact immutable result checkpoints, including receipts/indexes. Construction and transport decode perform complete canonical, identity, payload/projection hash and Event validation. The payload and planner-origin marker are private immutable fields; coordination and ordered projection installation consume that validated typed value rather than re-encoding the same value for pure integrity checks. Exact current Store records, predecessor Ready, configuration/sequence, before/result and owning component installation checks remain mandatory. An opaque planner-produced value is required for a new commit. Decoded transport values can only recover an already committed exact Store record; a digest is integrity proof, not producer authentication. Source admission/authentication remains the future official Runtime adapter's responsibility. Replayed frozen component commands validate component state without rerunning Execution Planner, fee schedules, market rules or mutable queries.

An original in-process plan may privately retain its actual post-plan typed owners as a rebuildable data optimization. This representation is absent from canonical bytes, hashes and equality; `Prepared::clone` drops it while preserving the original planner marker, and transport decoding never creates it. The coordinator may pass that original plan to its private continuation only after the actual committed record matches its complete canonical payload. Before even an idempotent projection return, the selected retained owner's actual complete checkpoint Value and digest must exactly match the original projection result; a present mismatch is an error, never a fallback. Only the selected Order/Position/Account/Ledger/Risk manager is independently copied, after the original before/result and projection-order gates. Sequence, pending progress and other owners are not copied. Execution metadata keeps the original schema/Fee/Settlement/Margin restore and valuation checks. A plan without this transient representation, including all decoded durable history, follows the original complete restore path; Ready marking, completion and restart recovery are unchanged. No typed copy supplies Store, dispatch or publication authority.

Within one immutably borrowed read operation, complete current-owner and configured-genesis checkpoint images are captured once and reused by the existing Ready, lineage, complete-source and reconciliation checks. Store observations and all transaction/scope/owner comparisons remain independent checks; no caller payload or retained image supplies a grant. The planner independently copies its already source-checked typed data before applying the explicit input and constructs the same complete canonical before/result payloads. Persisted checkpoint restoration still invokes the original complete reader. No image is cached as a source proof across calls or mutations, and checkpoint schemas, bytes and economic histories remain unchanged.

The Store port is the sole durable execution authority: atomically commit Prepared + pending Events, verify the immediate predecessor Ready, install ordered component results, durably mark Ready, then expose business/outbox results. Public technical projection installation requires the exact owning Store record; completion requires its observed Ready state. Events have stable identity and at-least-once delivery. Applied progress is a rebuildable index. Failure retains the installed prefix, blocks new plans and proceeds by forward recovery; no cross-component rollback, blind UNKNOWN retry or alternate order identity is introduced.

New-risk history budgets cannot block accepted observations, fills, cancellations, releases or proved close. Extended safety history remains complete and fresh-reader recoverable. These admission ceilings are not physical storage quotas; the official durable owner still needs storage pressure handling. Actual-file test adapter reopen evidence is technical library evidence, not official Runtime startup, Shipping UI or deployment-upgrade certification. See the [design](superpowers/specs/2026-10-19-rust-execution-design.md) and existing migration gates.

Rust Prepared schema1 is an isolated comparison representation with ordered atomic component groups: Order, Position+Allocation+sell hold, Account+cash holds, Strategy Ledger+cash holds, Risk, then Execution fee/settlement/identity metadata. The full committed payload binds every result before installation; all prefixes remain non-business-visible. It is not Python Prepared schema4, does not decode that wire format, and does not change the existing formal Runtime projection order. Official admission must resolve the owning integration/public-contract and history gates atomically; this library introduces no adapter or compatibility fallback.

Position alone maintains exact cumulative realized PnL per Allocation cycle and emits the difference between successive half-even currency targets. Consumers retain an explicit residual from exact cost, authoritative settlement and Money realized deltas; Ledger PnL equity includes that independently accumulated residual. This preserves each final currency remainder without recalculating Position cost in Account/Ledger. Allocation inputs carry exact identity, cycle, result version and exact/Money realized state; a new cycle cannot erase lifetime ledger PnL or reuse an old identity. The Python per-Fill rounding path is a classified reference deviation on fractional residual cases; correct common integral vectors remain comparable.

Position, Account and Strategy Ledger isolated checkpoint bodies use schema2 for these new mandatory semantic fields. Schema1 is explicitly rejected, with no automatic reinterpretation. These components have no admitted official Rust Runtime writer or production history migration in this task; the existing Python Runtime persistence format/readers are untouched, and the previous exact implementation remains in Git/artifact provenance. This is not an existing-history upgrade certification.

Generic T0 monetary inputs explicitly bind currency, resolved notional and HALF_EVEN settlement rounding. Position retains raw price-times-quantity cost. Ledger accumulates settlement-versus-cost/realized rounding residual from validated trade deltas; Account consumes the sum of those owning residuals. The residual is not inferred from the equity equation. Full Ready-prefix causal hashes must connect genesis to the current projection before query, admission or completed recovery.

Market and valuation source references identify immutable evidence occurrences within their respective family. Reuse for a new request, watermark or payload is rejected. Positive quantity/exact gross can resolve to zero currency settlement; this does not make the Fill absent or waive price/quantity/settlement proof.

Rust cash Settlement now consumes explicit Calendar/policy input and owns registration plus `SETTLEMENT_MATURITY` through the existing coordinator; metadata schema5 replaces the former settlement alias-only map. See [Settlement](settlement_model.md#rust-settlement-responsibility-and-admission-boundary) for supported economic shapes, preserved resource bounds and deferred activation/history gates.


Native metadata schema5 includes the Margin owner. Explicit collateral declarations join ADMIT/FILL/TERMINAL atomically; UNKNOWN/cancel request do not release, actual closing Trade relations determine lifecycle-bound release. The existing six projection groups and Store authority remain. See [Margin](margin_model.md#rust-margin-responsibility-and-consumer-boundary) for capability and source-admission boundaries.

`VALUATION` freezes a complete current Position source and explicit mark facts in one no-Fill transaction, updates Account via opaque source-derived effects, and revalues all Cluster Ledgers against their own complete Allocation relation. Account checkpoint schema4 and Execution metadata schema5 reject raw/old shapes without fallback. See [Valuation](valuation.md). No Runtime activation or business-history migration is implied.

## Rust Runtime Ledger Reconciliation

The source-bound read-only query `Components::reconcile` consumes the exact current complete Ready prefix and all configured Account/Cluster owners. It replays the canonical Fee producer from committed Fill inputs, checks aggregate economics plus complete Trade attribution, and returns immutable diagnostics without writing any owner. See [the owning Contract](runtime_ledger_reconciliation.md). A matching diagnostic does not grant Runtime/LIVE admission or silently absorb per-owner rounding differences.

Account-authoritative [Runtime Portfolio Performance](runtime_portfolio_performance.md) uses the same complete Ready source guard and reconstructs its immutable timeline through the Account owner, without a new writer or Runtime/Backtest activation.

[Backtest Result / Final Seal](backtest_result.md) is the source-bound read-only result adapter over this composition. Its explicit completion scope is Execution transcript closure, not official Runtime activation or market-driver exhaustion.

The Infrastructure [native Runtime persistence adapter](rust-runtime-persistence.md) supplies the SQLite Store Port and bounded recovery session. It preserves this library's opaque commit capability, six-owner projection order and at-least-once Events; it does not activate a formal Runtime.


Complete six-owner payload Values may be shared as a private immutable codec image while the component data is unchanged. This memo stores only the checkpoint data produced by the original owner readers, never Ready, Store, lineage, reconciliation or admission proof. Every outward source observation still reads its actual current Store and checks the complete owning lineage independently. Detached checkpoints are owned copies and cannot mutate the memo.

The candidate invalidates its own image before any planning mutation, including the checkpoint-based Risk-denial preview. Every projection-install attempt clears the image before calling an owner restore reader, including failed attempts. Component restore constructs and validates a fresh instance before replacing the old one. Sequence and pending-projection control are serialized from their current fields and are never part of this memo. Public checkpoint/Prepared schemas, canonical bytes and identity formulas are unchanged.

`Components::fork_ready` copies an independent typed in-memory head only after requiring no pending projection, the exact current Store head, and the original full reconciliation. The Runtime adapter reads the actual complete record source and reconciles the copy again. Planning may copy its already source-checked component data before applying its explicit input, without replaying its own checkpoint journals. These copies grant no commit, admission, external dispatch, source freshness or crash-recovery authority; persisted checkpoint readers and original recovery remain unchanged.


The private payload codec image stores the six complete Values and their canonical SHA-256 values together in one `OnceLock` initialization. The hashes are derived from those exact immutable Values and are invalidated with them before every owning mutation. Ready and reconciliation readers take their current-owner hash expectations only from that same private image; no caller can pair supplied hashes with unrelated Values. Actual Store/head, every retained row, scope, predecessor and Ready checks are still performed independently for every query. Configuration hashing may be reused within one immutably borrowed row scan without removing any per-row configuration comparison. This caches deterministic encoding data, never a successful source comparison or authorization.


Execution configuration schema1 retains its exact original fields, Account checkpoint4 constructor and genesis identities. Configuration schema2 adds only the mandatory fixed `account_checkpoint_version: 5` field and is restricted to BACKTEST. It selects Account's explicit `new_checkpoint5` constructor; there is no first-row inference, latest selection, retry of another codec or implicit conversion. The complete configuration participates in its original fingerprint, so the new variant has a distinct execution identity while the Strategy Revision remains unchanged.

Every Account projection must use the version selected by its Execution configuration. Cold restore, cached payload images, projection installation and original typed-after copies enforce this binding, including idempotent projection returns. Persisted checkpoint restore remains the owning reader's responsibility. Account checkpoint5 enforces its explicit 16 MiB bound on the equivalent complete expanded checkpoint; this BACKTEST resource profile does not impose a new bound on checkpoint4 or alter LIVE safety paths. Existing single-Step/Record decoder and transport limits remain unchanged.


The private immutable Prepared canonical body and its validated derived fields are shared by native `Arc`. Construction and cold transport decode each validate their complete body before deriving data.
