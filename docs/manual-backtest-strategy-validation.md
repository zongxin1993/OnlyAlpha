# Manual Backtest strategy validation

This contract implements [ADR 0148](adr/0148-manual-strategy-admission-for-experimental-backtest.md) under the unchanged Project Constitution. Manual Backtest is an additional verified origin at the existing Strategy Freeze authority, not a bypass around immutable Strategy identity, Qualification, Promotion or execution admission.

## User path and scope

The formal Shipping Web path is: select a published exact Factor Revision, save the Strategy Definition, choose a data source, confirm the Strategy and prepare Backtest, wait for READY, separately confirm start, then inspect progress and results. The source selector uses the existing Product source query; Factor selection uses the existing Private Assets registry and exact-revision reader. No Study, Research Run, Agent connection or model call is required. Existing strategy and preparation history remains discoverable after reload, including tasks that have not created a Run.

The initial profile is Binance Spot `BTCUSDT.BINANCE`, one-minute finalized bars and the existing price-volume momentum Factor. Entry is Factor >= 0.001 when flat; exit is Factor <= 0 when held. Position size is 0.01 BTC, initial cash is 10,000 USDT, with one long position and no additions, shorting or leverage. A close signal can execute no earlier than the next open. The existing two-basis-point full-precision slippage and 0.1 percent quote-currency fee model remain explicit. Current captured venue rules are simulation assumptions, not historical venue acceptance.

The Backtest samples bar opens from 2025-01-03 00:00 UTC inclusive to 12:00 UTC exclusive. Its exact graph determines the separate warmup. The protected 2025-01-05 to 2025-01-06 interval is not read. Final open positions are valued at the last available close; no fictitious liquidation, fee or fill is added. Results retain net profit, realized/unrealized profit, return, drawdown, fees, trades, positions and the same-quantity buy-and-hold comparison. Short samples do not acquire annualized performance claims.

## Preparation and original identity

Backtest preparation input version 2 carries a tagged origin. `MANUAL_STRATEGY` selects the exact existing private Strategy ID and revision fingerprint; private IDs keep their existing bounded identifier language and are not UUIDs. `FROZEN_STRATEGY` selects exact frozen Strategy, Freeze relation, Qualification Decision and Promotion references. Common source, release, expected Generation and original future Backtest Command remain explicit. Command and reserved Run identities remain UUID4-domain identities under the existing reservation formula.

The original preparation owns data acquisition/materialization, executable validation, Freeze, Qualification and Promotion. It does not require a not-yet-produced admission in order to accept a manual preparation. Existing source authorization, namespace and physical-session checks remain mandatory. The expected active Generation is the Human-observed compare-and-set predecessor. The existing installed environment producer may prepare and activate the selected release in the same Registry under the original preparation Command; the durable environment output records the actual resulting Generation and original reserved-work binding. Readers and execution bind that actual Generation rather than substituting the predecessor. No new Runtime mode or parallel environment is introduced.

Derived Strategy/Freeze/Qualification/Promotion references may be absent before READY and must never be filled with placeholder hashes. Stable operation checks compare original origin, source, Command and reserved work. READY requires complete re-opened owning proofs and a final preparation fingerprint. Confirmation pins that fingerprint and creates only the original reserved Run. UNKNOWN observes the original operation. After an accepted preparation, only an explicitly proven Start/service refusal with verified non-submission may permit another explicit Start attempt with that same future Command and intent.

The prepare POST has one scoped reply union: the complete accepted preparation view, or `NOT_ACCEPTED` with the original Command, complete typed input and `CONDITIONS_CHANGED` / `SOURCE_UNAVAILABLE`. Only the exact pre-accept release mismatch or Source permission refusal branches construct that reply, after re-reading the original Command binding. An already-accepted original returns its actual view; an admitted/uncertain binding remains UNKNOWN. No post-accept error, generic error code, 404 or absence query can manufacture this reply.

The reply reports that this original HTTP invocation did not start preparation; it does not revoke the Command or create a terminal ledger fact. Web verifies both original Command and every input field before retaining that explicit refusal. A retained refusal never overrides a subsequently accepted original preparation. Fresh context and original-Command observations give that positive authority priority. The user's “return to conditions and confirm again” action queries the original Command first: an actual preparation or Run is restored through the normal successful exact-intent validation and consumption path, with identity retained in its canonical URL and database history; an unavailable or uncertain query retains the auxiliary marker. Only the already-correlated explicit refusal together with the Backtest Command query's successful strict `{schema_version:2,command_id,state:"NOT_ACCEPTED"}` observation matching that exact Command permits that explicit action to discard the still-matching auxiliary intent and refresh conditions. This successful read-only observation is emitted only after verifying the expected semantic namespace, taking the original Command barrier and proving canonical Binding None with no operation row. Admitted, foreign, missing-downstream, driver and integrity failures never use it; generic Research/resource NOT_FOUND behavior remains unchanged. Ordinary `loadPreparation` still requires a complete actual view. No HTTP status, error code, detail or message can manufacture this observation or establish refusal; the private explicit-refusal review path alone parses the strict GET union. A missing/failed query without the previously correlated prepare refusal remains UNKNOWN. A subsequent confirmation is a new logical request. A lost reply or transport uncertainty keeps the original intent/identity and observation path. A stale release is therefore not offered as a retry of permanently stale conditions, and no tombstone, fake cancellation or parallel rejection ledger is introduced.

## 构建认证、作业输入校验和正式发布

本节依据[ADR 0151](adr/0151-postgresql-business-publication-and-memory-work.md)演进；[有限作业契约](job-execution-contract.md)定义冻结输入、精确认证及正式结果成员。当前第一阶段只补契约，旧实现尚未切换。

独立构建任务消费精确作者／因子版本、完整类型程序、实现及数值规范，对每个精确参数绑定执行受控的batch/event逐点比较、因果前缀、缺失值、warmup和必要状态恢复认证。创建不可变版本后自动构建默认参数，新参数单独认证。真实Research或手工Backtest准备不重复运行受控案例全集，不以有限样例声明全域证明。

每次作业仍由实际owner核对真实来源权限、精确程序／参数证书、Generation／工件、CH版本／Seal／segment、实际轴／行数／内容、warmup和输出约束。实际数据不满足契约就拒绝；构建就绪不保证任意数据成功。手工准备不创建Research Target或Statistics；信号图不消费未来Target。

原准备Command仍拥有受理、保留Run和冻结意图。有效输入校验及精确构建证书的关系由原Authority持久化到PostgreSQL，不再先发布manifest文件再写引用。普通读取不能伪造producer、完成或Freeze许可。子进程原owner必须正向完成kill/wait/join；未知清理保留原归属并阻止发布。

发布前中断先观察原Command／Run的真实提交与发布；已发布复用，确定未发布且获得新有效Claim才从冻结输入重算。无锁查空、错误码、调用方boolean或自签JSON不能证明未提交。取消终态不发布部分结果；已完成发布不被迟到取消撤销。

## Freeze, Qualification and Promotion

The existing FrozenPlan and publisher derive SourceRevision from the owning verified validation; the new contract binds exact build certification and actual-job input checks, without re-running the controlled certification suite per job. A manual Freeze relation explicitly records its origin and validation reference; it does not fill Research fields with invented values. There is one frozen-revisions store and one Strategy fingerprint formula. Repeated identical semantics may retain distinct valid provenance while preserving the first verified immutable Source representation.

The existing Qualification evaluator gains `MANUAL_STRATEGY_TO_BACKTEST` and `STRATEGY_VALIDATION`. The initial `manual-backtest/1` policy requires `strategy.execution_validation_passed EQ 1`; only the complete owning validation and exact manual Freeze proof can provide that metric. Missing, stale or changed proof yields an error, not a user-supplied value. Manual evidence identifies the validation fingerprint, original preparation UUID and exact Freeze relation. Decision load and source-cut capture re-evaluate the actual original proofs; a Command receipt alone cannot authenticate the evidence.

Promotion records identify manual origin explicitly and target BACKTEST only. A frozen manual precursor is not a new Runtime mode and is not a fictitious Research transition. Existing Research-origin records keep their original bytes and interpretation. Repeated use of an already admitted exact Strategy re-opens the existing qualified admission instead of fabricating another same-stage transition. Any manual attempt to obtain SIM or LIVE admission is rejected.

## Verification boundaries

Correctness checks cover missing or changed graph nodes, mismatched exact revisions/implementations, missing exact build certification/required restore certification, unjoined children, stale source or namespace, publication interruption, original Command recovery, tampered artifacts and DB references, Qualification reevaluation, Promotion origin/target, and cancellation before/after atomic PostgreSQL publication. Immutable Kernel history, UNKNOWN, projection recovery and exact economic results retain their existing tests.

Business acceptance uses only normal Shipping Web navigation, selection, commands and visible feedback against the canonical application. Technical fixture/API tests do not replace the real path. Final deployment verification must preserve and load the existing model configuration and both original Factor reports. The research-first product flow remains separately scoped; manual validation is not presented as Research or evidence of profitability.
