# Rust Risk component design

## Ownership and scope

One independently buildable `crates/onlyalpha-kernel/risk/` library owns Runtime-scoped deterministic pre-trade decisions, explicit Cluster profiles, mandatory gates, risk exposure reservations, scoped Kill Switches, audit and atomic component recovery. Domain is its only local edge. No official Runtime activation, Broker effects, money/Position ownership, provider rules, fee formulas or durable cross-component transaction is introduced. Constitution impact: NO. ADR0012 and the owning Risk Contract govern; immutable admitted inputs replace live query callbacks in the component.

## Python audit and reference differences

The reference is the actual Risk Service/Pipeline/Reservation manager and Execution trade reservation reducer. Pipeline order is SYSTEM/RUNTIME/ACCOUNT/INSTRUMENT/CLUSTER, explicit order then stable rule ID. Mandatory gates cannot be observing or replaced. Current Python creation de-duplicates only by Order ID; fill consumption caps quantity/notional silently; service performs market/ledger gates before its decision cache, and restores multiple live collections incrementally. Rust requires complete normalized identity, exact conservation without silent clipping, immutable cached decision replay before new evaluation, and fresh candidate replay before replacement. Production Python is not repaired wholesale.

## Input boundary

Closed schema1 config binds engine/runtime/account/generation, BACKTEST/SIM/LIVE, canonical currency and explicit Cluster profiles with Strategy Revision and allowed Instruments. Config is immutable for this component lifetime. Rules are bounded built-in universal comparisons, not arbitrary Rust/Python callbacks. Scope ordering, enforcing/observing behavior and stable ID ordering follow ADR0012.

Immutable config includes positive `admission_limits` for command count, journal bytes, checkpoint bytes and reservation inventory, each no higher than 4096/8MiB/32MiB/1024. These are new-risk admission budgets, not hard limits on safety history. Commands carry exact context, command ID, causal digest, explicit integer nanosecond time and increasing Runtime sequence. EVALUATE contains Request identity/side/effect/position-side/quantity/price/notional/fee estimate, explicit market/plugin verdict, and immutable Account/Ledger/Position capacity envelopes. Notional and fee estimate are resolved externally and bound by source references; Risk does not invent price/multiplier/margin/fee formulas. OPEN increases risk, CLOSE is reducing only when side closes the stated Position and both account and Cluster Allocation available quantities, exact Position side and mode prove capacity; AUTO/UNKNOWN cannot prove reduction.

Each envelope binds owning family, engine/runtime/account/generation/Cluster/Instrument/Strategy Revision, source identity/version, as-of Runtime sequence and source digest to exact data. Payload identity is retained for conflict checks. Null/missing/unavailable facts are not certified absence. No boolean or digest alone authenticates a producer: official adapter/source admission remains Execution integration work. Capacity values explicitly mean available BEFORE this Risk owner's outstanding holds; adapters must not pass raw net-of-same-hold snapshots as equivalent. The as-of sequence must cover all economically consumed/released reservations. Same-callback outstanding holds are subtracted locally, including other Clusters for Account cash/Position and own Cluster for Ledger/Allocation. New callbacks after fills require refreshed owning inputs; no stale-capacity reuse.

Cash checks include an explicit owning-plugin-resolved cash requirement + nonnegative fee envelope, distinct from notional/margin exposure; there is no universal notional-to-cash formula. Risk conservatively retains the full cash requirement/fee envelope until terminal, while notional/quantity exposure consumes incrementally. Execution adapters must express capacity before these same local holds and refresh it after economic facts. Cash checks include the resolved requirement + fee envelope; no rebate discount. CLOSE does not reuse BUY cash holds. Ledger/Account non-ACTIVE and Kill Switch block OPEN; valid CLOSE remains available with current Position, market permission and safety evidence, without requiring cash/ledger readiness. Unknown classification blocks new submit; observation, fill, cancel-pending and terminal processing do not go through new-submit gates.

## Decisions and reservation lifecycle

EVALUATE commits an immutable ACCEPT/REJECT/ERROR decision/audit only, never Order or Reservation. Repeated identical Request (including complete evidence) returns original decision; changed payload is conflict. ACCEPT records an admission epoch. RESERVE requires that exact decision, Order identity, unchanged epoch and single-use Request-to-Order binding; actual Execution must place evaluate/create-order/reserve in its transaction before publishing or sending. Intervening hold/control changes invalidate an unconsumed decision. No retry or new Order identity is generated here.

Reservations retain original/consumed/released/remaining quantity and notional, plus fee/cash hold, full identity and stage. Unknown and cancel-pending retain holds; SENT cannot be released as NOT_SENT. FILL binds Order/Trade/source identity and exactly consumes remaining quantity/notional. Order-provided final flag must agree with zero remaining quantity, with price-improvement budget released rather than counted as consumption. Terminal cancelled/rejected/failed/expired releases only remaining; active count decreases once. Oversized fills are explicit errors, not clipped: Execution must persist/reconcile external facts and block exposure rather than discard them. Component rejection is not permission to drop a venue Fill. Duplicate aliases require identical complete payload; conflicts and invalid transitions leave state unchanged.

## Recovery, bounds and verification

Candidate clone -> validate -> one commit. Closed canonical schema1 checkpoint binds exact config, normalized complete command journal and entire reconstructed state by external SHA256. Prospective new OPEN decisions/reservations are atomically refused if their complete candidate exceeds any admission budget. Existing exact duplicates, observations, controls, fills, terminal handling and proved CLOSE may continue past these thresholds with full history. Encoder/reader must accept their own complete extended checkpoints; no truncation/compaction or quota-based refusal of safety facts is allowed. These logical budgets are not a physical memory/storage cap; the future durable Execution owner must provide storage pressure handling without abandoning accepted risk. Restore replays into fresh component, compares canonical journal/state then replaces. This proves component recovery, not durable Runtime service restart/upgrade. New-risk admission budget ceilings: commands4096/journal8MiB/checkpoint32MiB; safety history remains complete beyond them. Individual valid command64KiB, Clusters64, rules64/profile, new-risk reservation inventory ceiling1024; financial coefficients128 digits and scale0..18. No clocks/random/IO/reverse imports.

Authority proof dimensions: full context, request/profile/Strategy Revision, owner-family/source/version/as-of, immutable payload, Order-to-request, Trade-to-Order, control target and reservation conservation. Proved match permits cached reuse; proved different is conflict/reject; incomplete/unavailable is ERROR. Missing evidence never proves available capacity, terminality or absence. Adversarial mutations include whole context, nested owner, wrong family, source ref, payload leaf, duplicate IDs and complete-different identity.

Cross-check valid existing behavior against real Python Pipeline/Reservation classes and independent literals; stricter identity/atomicity/safety cases are Rust-specific regressions. Linux canonical dev validation runs targeted Python/Rust, debug/release, isolated closure, source guard, lint/types/version/Constitution and nearest Rust canonical lane. One bounded independent reviewer re-derives state space/relations/negative invariants.

## Engineering evidence

Curated FP-BROKER-002 (RQAlpha issue366) requires nonzero/unknown fees at full cash boundary tests, with no fixed haircut/venue retry. FP-BROKER-001 requires session-independent identities, UNKNOWN holds and partial/cancel exactly-once consumption/release. FP-RUNTIME-001 motivates exact generation/source binding and no ambient fallback. These references provide failure patterns, not authority, provider formulas or implementation patches.

Financial admission bounds apply to the stored plain-normalized coefficient, including zeros expanded from scientific notation. Normalizing an admitted config/command must never make it unreadable by a fresh component reader.
