# Rust Account component design

Account owns one explicit Engine/Runtime/Account/Gateway/Generation/currency CASH scope, local cash journal, cash reservations, received fee instructions, attributed PnL, valuation observations, Broker comparison and complete component recovery. Domain is its only local dependency; no Order/Position/Ledger/market/plugin/Broker/Runtime import or effects. Python remains the admitted Kernel; Account is neither Strategy Ledger nor external venue truth. ADR 0015, ADR 0050, ADR 0139 and the owning Account Contract apply. Constitution impact: NO.

## Inputs and invariants

Schema1 config binds engine/runtime/account/gateway/generation, account_type CASH, canonical Domain currency, initial_cash. Commands bind the exact scope, command_id, causal fingerprint, signed nanosecond time, op and closed payload. Domain IDs/currency and exact bounded decimal strings are validated before mutation. Cash inputs must be exactly representable at configured currency precision; no implicit rounding, FX, wall clock, hidden IDs or provider rules. Monetary output is fixed currency precision.

Cash accounting uses ledger_cash >= 0, reserved_cash >= 0, unsettled_receivable >= 0, trade_available = cash - reserved, withdrawable = trade_available - unsettled, equity = cash + position_market_value. Current cash-backed reservations and withdrawals conservatively use withdrawable cash. No margin/short/borrowing/derivative policy is inferred. Settlement restrictions consume explicit instructions, never inferred dates. Unsupported inputs fail closed without changing state.

TRADE receives explicit trade/execution/venue aliases, order, ordered external sequence, BUY/SELL, settled notional, authoritative incremental fee instruction (ID, charges, rebates), attributed realized delta, position evidence fingerprint, market-value delta and resulting unrealized PnL, cash_withdrawable and Order's terminal_fill. Account never computes fees, terminality, cost basis or realized PnL. BUY requires its exact cash Reservation and consumes notional + charges; rebates credit cash separately. Actual gross debit must fit its remaining Reservation, matching the formal reducer. Partial fills retain remaining holds, terminal fills release excess once. SELL never consumes a buy Reservation. Each Trade updates balances, Reservation, fees and supplied valuation together on one candidate; whole-Runtime transaction remains outside this crate.

CASH_CHANGE accepts explicit DEPOSIT/WITHDRAWAL with immutable source ID. ECONOMIC accepts explicit signed FUNDING/REALIZED_PNL/VARIATION_MARGIN facts, not policy calculation; source identity and instrument are bound. SETTLE consumes one explicit recorded receivable amount by source trade, no market convention. VALUATION binds explicit increasing version, exact current economic_version and position evidence; no obsolete financial basis can overwrite current equity. Portfolio performance/report orchestration remains outside this crate.

Reservations retain original/consumed/remaining/released, order identity and lifecycle. SENT, UNKNOWN, ACK and CANCEL_REQUESTED preserve funds until a normalized terminal confirmation. NOT_SENT release only before a possible submission. Late ACK cannot erase cancellation uncertainty. Economic fills continue while reconciliation blocks new reserves/withdrawals.

Verified Broker observations include snapshot identity, external sequence and exact current Account basis_sequence. This full state sequence also covers Reservation and valuation changes; it is distinct from the valuation economic_version. Compare cash, reserved, available, withdrawable and equity without replacing local values. Unverified observations block new risk. Old/missing proof cannot clear blocks. Only a later verified matching current-basis observation clears Broker mismatch; stale unapplied Trade remains a separate sticky block requiring future owning reconciliation resolution, not manual clear.

## Identity, atomicity and recovery

Every accepted command, including semantic duplicates and stale observations, binds its immutable payload; same command identity/different payload conflicts. Semantic identity aliases must all bind the same complete economic payload, not ID-only sets. New command IDs acknowledging the same fact are journaled without repeating economics or advancing financial time. All changes use validated candidate state. Errors/conflicts leave the owner unchanged.

Checkpoint is canonical schema1 JSON with exact config, complete command journal and derived state, externally bound SHA256. Restore replays into a fresh owner, requires one new receipt per journal entry and exact full-state reproduction, then replaces atomically. No old readers, union restore or fallback. This is component recovery, not durable service/history migration or Runtime admission.

Bounds: 16KiB command, 4096 commands, 4MiB journal, 16MiB checkpoint, 512 reservations, 1024 receipts per semantic family. Input monetary coefficient <=128 digits, scale <= currency precision, derived <=1024 digits. Signed timestamps <=40 characters. Resource failures occur before commit. Existing pinned Domain/BigDecimal/serde_json/SHA256 dependencies only.

## Reference audit and acceptance

Python direct Manager stores Trade/cash-change/fee dedup as IDs without full payload equality, can mutate before final Snapshot validation, and checkpoint omits some receipt histories; do not copy these behaviors. The formal trade reducer supports explicit fee charges/rebates, cash Reservation deltas and valuation. Use actual Manager for valid simple cash common cases and actual reducer for authoritative multi-fill balances, each checked against independent literals and native Rust output. Classify deviations rather than declaring whole-module parity. Test uncertainty, partial/terminal holds, same-ID conflicts, late/stale inputs, cross-scope/currency failures, tampered recovery and deterministic continuation in debug/release plus independent isolated builds. No official activation, business-data migration, broker access, Shipping UI claim or Release follows.

## Engineering failure lessons

Consulted curated upstream histories [cost-unaware allocation](../../engineering/failure_patterns/FP-BROKER-002-cost-unaware-full-allocation-sizing.md) and [projection without history](../../engineering/failure_patterns/FP-STORAGE-001-trading-projection-without-durable-history.md). Derived tests require gross fee-funded holds, no arbitrary affordability buffer, and full command/receipt replay with tamper rejection. These references do not confer official Runtime/durable-store admission. Account inputs are normalized fee/PnL projections; verifying their owning producers belongs to the later execution transaction boundary.

Signed net Trade effects are accepted when the final cash invariants hold: charge/rebate components remain nonnegative, but fees can exceed sale proceeds and rebates can exceed purchase cost. A nonpositive sale net creates no positive unsettled receivable. A Fill proves submission even without an earlier send callback and can never permit NOT_SENT release of remaining authority. The input coefficient bound applies after canonical currency-precision padding, so every admitted config is readable by its checkpoint reader.
