# Rust Runtime Persistence / Recovery

`crates/onlyalpha-runtime-persistence/` is an Infrastructure library implementing the existing Rust Execution `Store` Port and a bounded `Runtime` composition facade. It owns persistence/lifecycle, not trading economics. SQLite, filesystem paths and OS locks stay outside the Trading Kernel. `Runtime` is a library session name, not Product Runtime admission or permission to execute LIVE.

## Identity and lifecycle

`Runtime::create(root, configuration, kernel_artifact)` explicitly creates a new `runtime.sqlite3` under an existing, operator-owned stable Runtime state directory. `open` requires an existing exact database. Neither operation initializes, translates, rebinds or replaces an existing unknown/empty/foreign/corrupt database. Infrastructure supplies a trusted canonical directory from its user-data layout; paths are locators, never identities. The native constructor currently admits Linux only; other targets fail explicitly. Database symlinks and multiple hard links are rejected to prevent SQLite journal-locator aliases. One OS file lock on the actual database inode is retained for the session lifetime; another opener fails immediately. An abruptly terminated process releases the lock through the OS. Never unlink/replace an active database; leases are not protection against an administrator or hostile filesystem writer.

Native Store schema2 binds the complete canonical Execution configuration (including Runtime kind, Account, Cluster revisions and Runtime Generation) and exact Kernel artifact digest. It is a distinct format from admitted Python Store schema7 and Runtime checkpoint envelope5. An explicit `SqliteStore::migrate` upgrades fully verified native schema1 history atomically without rewriting its records/checkpoints; ordinary `open` rejects old formats. Schema2 also retains the [Replay Driver](rust-backtest-replay.md) journal in the same database. This component never opens Python history as native history, chooses latest, falls back to Memory or activates/rebinds work. Existing Python work retains its original exact implementation and owning readers under ADR0117. Production activation and historical-artifact availability remain R5 gates.

## Durable authority and transaction boundary

One SQLite database contains identity, contiguous head, immutable Prepared records and their input identity index, embedded immutable Events, monotone Projection Ready/delivered flags, and complete Execution checkpoints. There is no second Outbox database, trade writer or derived Result cache. SQLite uses rollback journal DELETE, synchronous FULL, zero busy timeout and explicit immediate transactions. I/O/SQL/codec errors retain their cause in the technical error; an uncertain commit never authorizes a replacement input/order identity. No automatic retry is introduced. SQLite's durability assumptions still depend on the actual filesystem/storage stack.

Only opaque `CommitIntent` from the canonical coordinator can introduce a record. Same identity/exact payload is idempotent; changed payload, missing predecessor, unready predecessor or foreign context fails closed. Record+index+embedded Events+head commit atomically. Before any SQL insertion, all six incoming projection `before_hash` values must equal the destination Store's actual predecessor results or configured genesis. A canonical intent produced against another complete same-config/same-head history cannot advance this Store. Ready is durable before component completion/outward visibility; acknowledgement requires Ready. Event delivery remains at least once: an external send followed by a crash before acknowledgement can redeliver the same stable Event ID. Consumers retain their owning idempotence obligation.

## Checkpoints and recovery

A checkpoint contains the complete canonical six-owner Execution checkpoint, exact Store identity, Ready sequence and causal source digest. It is validated against a genesis replay of the complete retained committed history, written atomically, and read back before success. The checkpoint is an optimization/evidence boundary, never a replacement for Order/Fill/Account/Ledger causal history. Existing checkpoints at the same sequence must be identical. No retention/pruning is added.

Exact-row decoding reuse always rereads the SQLite input index, full canonical payload and digest; only byte-for-byte equality with a previously verified row can reuse its immutable decoded value. Missing/changed rows cannot use prior decoded values; head/lineage/checkpoint proofs remain mandatory. This in-memory codec memo is rebuildable and never a durable Authority.

Opening validates metadata/schema, contiguous records, payload digests, identity indexes, complete scope/lineage and checkpoint composition before mutating durable readiness. A copied/syntactically valid/rehashed checkpoint cannot replace a different history. After full-history preflight, recovery restores the latest verified complete checkpoint through the owning reader (or explicit genesis when none has been captured), rehydrates its Ready suffix and completes the committed pending tail in projection order. A present invalid checkpoint is never bypassed by selecting an older one. There is no replay of external submission or mutable fee/model query and no cross-owner rollback.

`Runtime::apply` gates reads after any failed transition; callers explicitly recover the same session or reopen the same exact identity. `state`, `records`, pending Events and Result reads revalidate the complete owning causal source and expose only a verified recovered Execution boundary. Caller manifest/result remains `EXECUTION_TRANSCRIPT`; successful recovery does not prove Dataset exhaustion, Strategy/Broker/Event drain, Product READY, deployment upgrade or official Backtest completion.

## Consumer and proof boundary

The public `SqliteStore` implements the low-level technical Port for existing coordinators. It does not authenticate the upstream producer merely by validating digests. The `Runtime` facade retains exclusive owners and Store rather than exposing mutable manager internals. Official source admission, Dataset/StrategyRevision/work bindings, Market replay, Timer scheduling, full Runtime checkpoint participants and Shipping Web UI are composed by the R5 driver; no native Timer consumer exists in this module and no speculative Timer store is added.

Tests exercise real economics, full-history/result equality, every projection cut, unknown committed outcomes, SQL rollback, exact context/schema refusal and actual child-process kill/reopen using deterministic barriers. These are Linux native-library process restart proofs. Native schema migration tests preserve retained history/checkpoints through the current owning reader. They do not certify a deployed service stop/start or upgrade, product activation, Windows or macOS. Native on-disk history is retained and reread by a fresh current reader; existing Python production/history behavior is unchanged.
