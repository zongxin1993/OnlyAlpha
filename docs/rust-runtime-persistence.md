# Rust Runtime Persistence / Recovery

`crates/onlyalpha-runtime-persistence/` is an Infrastructure library implementing the existing Rust Execution `Store` Port and a bounded `Runtime` composition facade. It owns persistence/lifecycle, not trading economics. SQLite, filesystem paths and OS locks stay outside the Trading Kernel. `Runtime` is a library session name, not Product Runtime admission or permission to execute LIVE.

## Identity and lifecycle

`Runtime::create(root, configuration, kernel_artifact)` explicitly creates a new `runtime.sqlite3` under an existing, operator-owned stable Runtime state directory. `open` requires an existing exact database. Neither operation initializes, translates, rebinds or replaces an existing unknown/empty/foreign/corrupt database. Infrastructure supplies a trusted canonical directory from its user-data layout; paths are locators, never identities. The native constructor currently admits Linux only; other targets fail explicitly. Database symlinks and multiple hard links are rejected to prevent SQLite journal-locator aliases. One OS file lock on the actual database inode is retained for the session lifetime; another opener fails immediately. An abruptly terminated process releases the lock through the OS. Never unlink/replace an active database; leases are not protection against an administrator or hostile filesystem writer.

Native Store schema4 (with exact retained schema2 raw and schema3 ZLIB readers) binds the complete canonical Execution configuration (including Runtime kind, Account, Cluster revisions and Runtime Generation) and exact Kernel artifact digest. It is a distinct format from admitted Python Store schema7 and Runtime checkpoint envelope5. An explicit `SqliteStore::migrate` upgrades fully verified native schema1 history atomically without rewriting its records/checkpoints; ordinary `open` rejects old formats. Both formats retain the [Replay Driver](rust-backtest-replay.md) journal in the same database. This component never opens Python history as native history, chooses latest, falls back to Memory or activates/rebinds work. Existing Python work retains its original exact implementation and owning readers under ADR0117. Production activation and historical-artifact availability remain R5 gates.

## Durable authority and transaction boundary

One SQLite database contains identity, contiguous head, immutable Prepared records and their input identity index, embedded immutable Events, monotone Projection Ready/delivered flags, and complete Execution checkpoints. There is no second Outbox database, trade writer or derived Result cache. SQLite uses rollback journal DELETE, synchronous FULL, zero busy timeout and explicit immediate transactions. I/O/SQL/codec errors retain their cause in the technical error; an uncertain commit never authorizes a replacement input/order identity. No automatic retry is introduced. SQLite's durability assumptions still depend on the actual filesystem/storage stack.

Only opaque `CommitIntent` from the canonical coordinator can introduce a record. Same identity/exact payload is idempotent; changed payload, missing predecessor, unready predecessor or foreign context fails closed. Record+index+embedded Events+head commit atomically. Before any SQL insertion, all six incoming projection `before_hash` values must equal the destination Store's actual predecessor results or configured genesis. A canonical intent produced against another complete same-config/same-head history cannot advance this Store. Ready is durable before component completion/outward visibility; acknowledgement requires Ready. Event delivery remains at least once: an external send followed by a crash before acknowledgement can redeliver the same stable Event ID. Consumers retain their owning idempotence obligation.

## Checkpoints and recovery

A checkpoint contains the complete canonical six-owner Execution checkpoint, exact Store identity, Ready sequence and causal source digest. It is validated against a genesis replay of the complete retained committed history, written atomically, and read back before success. The checkpoint is an optimization/evidence boundary, never a replacement for Order/Fill/Account/Ledger causal history. Existing checkpoints at the same sequence must be identical. No retention/pruning is added.

Every checkpoint validation rereads the complete actual SQL records and every retained checkpoint. If any record lacks independently validated immutable transition data, the original isolated genesis replay advances through all ordered prefixes and compares every checkpoint before continuing to the current head. Cold transport decoding never supplies that data. Earlier prefixes are not repeatedly restarted from genesis.

When all actual Ready bodies carry that nonserialized pure data, each stored checkpoint is still checked against its exact original source prefix: configured genesis for zero, otherwise that prefix's complete six original projection results, exact configuration/sequence/control, Store identity and full Prepared source digest. The original owning Components restore reader reconstructs each such complete source checkpoint and the original aggregate/Trade-Fee reconciliation runs on its actual full prefix. Every retained checkpoint's raw digest, canonical bytes and entire envelope are compared independently, and the final complete source state is compared to the current owner before saving. Reconciliation retains both its original errors and its explicit financial-difference diagnostics. No successful source, checkpoint comparison or reconciliation result is cached across calls; a corrupt older checkpoint or changed intermediate body cannot be bypassed by a valid current head. Checkpoint fields, canonical bytes, source proofs, transaction and cold recovery semantics remain unchanged.

Same-operation native reads reuse one complete fresh ordered SQL source through the existing private Replay owner. Identity, every row's exact index/bytes/digest, complete genesis lineage, Ready flags and anchored head remain checked. Reconciliation and the immediate pure query consume that local observation; it is discarded before another public call, observer, await or durable mutation. Preparation and completion retain independent real pre/post source reads, and the writer coordinator retains its actual committed/projection/Ready readbacks. Replay-step input relations use the same operation's actual complete Execution rows rather than repeating a full head query for each input. Their input digest may reuse the canonical fingerprint already computed by each exact immutable Prepared's original validation; the fingerprint is selected only after this call has read and verified the actual full row bytes/index/digest/flags and lineage. A changed actual body cold-decodes a new Prepared and computes its own complete input fingerprint. This is encoding data reuse, never a cached source comparison. Those same-operation reads do not change stored bytes.

Exact-row decoding and complete Prepared encoding-digest reuse always reread the SQLite input index, full canonical payload and digest; only byte-for-byte equality with a previously verified row can reuse its immutable decoded value, derived digest and six before/result projection hashes. For schema3 Execution records, the actual input index, complete stored bytes and digest must exactly match that same memo entry before reusing its pure physical-SHA/codec result. Both actual flags are independently read and validated on every observation, including delivery-before-Ready rejection; a fresh Record snapshot shares only the immutable Prepared and contains those current flags. A flag-only change neither decompresses the body again nor reuses earlier Ready/delivery values. Schema2 keeps its original exact full Record/body reader and memo matching. A miss takes the original full physical digest, bounded codec and scope checks. The actual current identity, header, sequence, full genesis lineage, Ready/delivery and anchored head/reconciliation checks remain fresh; none is a cached proof. That digest includes the Prepared payload_hash itself and excludes the outer Record Ready/delivered flags. A changed actual row is decoded and its complete Prepared digest recomputed; the digest is returned with that exact decoded row, never selected merely by sequence. Missing/changed rows cannot use prior decoded values; head/lineage/checkpoint proofs remain mandatory. This in-memory codec memo is rebuildable and never a durable Authority.

Opening validates metadata/schema, contiguous records, payload digests, identity indexes, complete scope/lineage and checkpoint composition before mutating durable readiness. A copied/syntactically valid/rehashed checkpoint cannot replace a different history. After full-history preflight, recovery restores the latest verified complete checkpoint through the owning reader (or explicit genesis when none has been captured), rehydrates its Ready suffix and completes the committed pending tail in projection order. A present invalid checkpoint is never bypassed by selecting an older one. There is no replay of external submission or mutable fee/model query and no cross-owner rollback.

`Runtime::apply` gates reads after any failed transition; callers explicitly recover the same session or reopen the same exact identity. `state`, `records`, pending Events and Result reads revalidate the complete owning causal source and expose only a verified recovered Execution boundary. Caller manifest/result remains `EXECUTION_TRANSCRIPT`; successful recovery does not prove Dataset exhaustion, Strategy/Broker/Event drain, Product READY, deployment upgrade or official Backtest completion.

`Runtime::complete_replay_rows` accepts only the consistency expectation of the original retained proposal. The Store freshly reads and matches that full proposal before updating Ready, then returns the full actual post-write readback; Runtime performs canonical reconciliation before returning it. No returned JSON creates a grant. Failure leaves the same Runtime recovery boundary closed. The existing unit-returning `complete_replay` observes the actual owning proposal and delegates without an intervening external callback. No source cut is cached across public calls.

## Consumer and proof boundary

`VerifiedReplaySnapshot::read` is a distinct opaque read-side owner. It opens only an existing supported schema2/schema3 database with `SQLITE_OPEN_READ_ONLY`, `NOFOLLOW` and private cache, retains a shared lock on the original single-link inode, and never calls configuration, recovery, `mark_ready` or acknowledgement. It rejects all pending/unacknowledged Execution records, unready replay steps, missing head checkpoints, symlinks, multiple links, replacements, unanchored file tails and any WAL/SHM/rollback-journal sidecar. This profile reads the producer's existing DELETE-journal format; it neither converts WAL nor uses `immutable=1`. Actual retained checkpoint values are restored and reconciled through the six owning readers against their exact committed prefixes. Every cut verification opens a fresh real read-only connection and revalidates the actual inode, full source, checkpoint composition and journal heads; old cached pages cannot authenticate a changed source. This technical source observation grants no work, publication or new execution.

The public `SqliteStore` implements the low-level technical Port for existing coordinators. It does not authenticate the upstream producer merely by validating digests. The `Runtime` facade retains exclusive owners and Store rather than exposing mutable manager internals. Official source admission, Dataset/StrategyRevision/work bindings, Market replay, Timer scheduling, full Runtime checkpoint participants and Shipping Web UI are composed by the R5 driver; no native Timer consumer exists in this module and no speculative Timer store is added.

Tests exercise real economics, full-history/result equality, every projection cut, unknown committed outcomes, SQL rollback, exact context/schema refusal and actual child-process kill/reopen using deterministic barriers. These are Linux native-library process restart proofs. Native schema migration tests preserve retained history/checkpoints through the current owning reader. They do not certify a deployed service stop/start or upgrade, product activation, Windows or macOS. Native on-disk history is retained and reread by a fresh current reader; existing Python production/history behavior is unchanged.


## Explicit storage3 physical codec and immutable replay references

New Work creation selects SQLite `user_version3`. The original schema2 raw Record/Step reader and explicit schema1-to-2 migration retain their exact original meanings; opening never compresses, translates or upgrades retained facts. Schema3 has one original SQLite Authority and adds independently fresh `ready`/`delivered` columns to Execution records. The immutable Prepared body and complete Replay Step body use the exact `ZLIB_CANONICAL_JSON_V1` frame (schema1, codec, logical SHA-256, logical byte length, typed summary and base64-standard zlib data). The already locked flate2 safe Rust backend and base64 pins supply compression/encoding; no service or alternate execution engine is introduced.

The physical frame SHA binds exact canonical stored bytes. The original canonical logical SHA, Step previous-chain SHA, normalized input identities and Prepared head digest keep their original formulas. Storage fields do not enter those logical identities. Actual Kernel/Artifact changes continue to produce the identities required by their original contracts; this is not cross-Artifact equivalence. Compression cannot modify a decimal, null, integer, checkpoint, causal processing or retained `seen`/history entry.

Every new Step/Record logical decoder is bounded to 8 MiB. It proves exact declared output length, full input consumption, one complete zlib stream and canonical logical JSON/hash. Truncation, appended junk, concatenated streams, unknown codec/version, malformed metadata, false lengths and expansion bombs fail closed. Schema3 full logical Record size is independently checked before commit. Stored frames are bounded, and Reference scans visit one encoded row at a time rather than materializing all expanded Step bodies.

`ReplayEntryRef` is private-field immutable source data, with no JSON decoder, value constructor or authorization marker. Only the original proposal/store write or an actual source read produces its physical/logical expectations; the Backtest owner privately admits its StepRef only after canonical proposal or complete original rederivation. A reference never authenticates a producer, grants work or constructs publication authority. Every `verify_replay_refs` still freshly reads every actual encoded Replay row, including its complete bytes, stored physical digest, index and Ready flag, and proves the exact chain, anchored head and original Execution input relationships. Only schema3 frame metadata and its pure physical-SHA result may be reused when actual sequence, complete raw bytes, actual digest and the open-selected storage version exactly match the same private memo entry. A changed row takes the original full frame inspector; Ready is independently validated and reconstructed from the current SQL row even on a codec hit. Legacy schema2 keeps its original reader. Individual logical body reads still use the original bounded decoder and exact summary/body comparison; changed rehashed source cannot borrow an older private expectation. Its same-operation Execution source/reconciliation checks also retain the complete state/owner guard without constructing a redundant outward State DTO. A successful earlier verification is never cached as source proof.

Preparation and completion compare the entire original reference prefix, and completion compares the original final proposal before Ready and in independent real post-write readback. Failure preserves original identity and the recovery boundary. Original pending recovery reads each complete original Step, reruns the original owning derivation and ends with a full fresh reference check. `read_replay_step` is an individual actual-row observation; it is not complete-history certification and cannot replace that final check.

The read-only snapshot retains the existing original shared inode lease, physical/source checks and fresh-connection complete-cut verification. Its reference inventory replaces expanded history retention. `read_step`/`write_encoded_step` inspect an actual named row and compare its exact reference. `for_each_step` brackets bounded Step callbacks with full fresh cut checks; partial callback output is not a successful proof. The encoded export writes only existing canonical stored frame bytes to the supplied writer and never creates a file, repairs history or changes a source. Existing all-steps Value expansion is an explicit bounded technical query; the production trace path streams references and individual Steps. Evidence bundle and frame budgets remain owned by their original 128 MiB contracts.


Runtime source validation and new-commit predecessor checks borrow the existing immutable canonical Prepared body through `Prepared::value()`. This is the same complete Value exposed by the detached `record()` copy, with no mutable reference or new admission capability. Read-only drain checks use the typed Record flags rather than materializing a complete Record body for a boolean. Actual source/identity/lineage/flags are still freshly checked. Complete Record serialization remains in the original size-budget and legacy-output paths; logical and physical formats, canonical bytes, hashes and limits are unchanged.

Reference inventory scans borrow exact SQLite Text payload and digest bytes only within the current Row lifetime, using the same native strict type/UTF-8 reader as Execution records. Warm scans still compare the complete actual bytes, index, physical digest and current Ready flag before using codec metadata. A cold or changed valid frame retains its one necessary owned immutable memo copy. Borrowed views never leave the row, replace complete source/lineage/input/head checks, or grant authority; individual encoded export continues to return its original owned bytes.


New Work explicitly creates SQLite storage schema4. Execution Record payloads use `ZSTD_CANONICAL_JSON_DICTIONARY_V1`: sequences 1,17,33,... are self-contained fixed anchors and each remaining row names its block anchor's exact sequence, physical frame SHA and complete canonical Prepared SHA. The same bounded complete Prepared bytes, logical hashes, identities and six-owner projections are preserved; Record and frame expansion remain within their existing 8 MiB budgets. Both encoded Record readers (storage3/4) check the complete Record envelope against the Prepared length before expansion. Exact-byte codec memo hits retain only that verified length and recheck the envelope with the actual Ready/delivered flags on every read, including a flag change that increases its size. Storage2/3 retain their exact original raw/ZLIB readers and receive no implicit conversion. Storage3 Replay Steps retain their original ZLIB frames. New storage4 Replay Steps reuse the same strict fixed-anchor dictionary codec, with a separate REPLAY_STEP family and separate anchor-data memo; their logical Step and Trace2 transport remain unchanged. Storage4 readers explicitly select retained ZLIB or dictionary frames by their actual tag, without error fallback or rewriting original bytes.

Every complete source scan still freshly reads all actual Record bytes, indexes, digests, flags and exact head, then checks the original complete lineage. An anchor is observed once in that scan and its opaque bounded dictionary bytes are shared by its block, without a separate full logical history. Every point read observes the actual anchor while the target SELECT remains active in the same SQLite read snapshot. Pure codec reuse requires exact actual target and anchor bytes/digests and the open-selected version; a changed or missing anchor cannot borrow a dependent's old successful decode. Flags remain freshly validated independent columns. No successful Store/source/Ready proof is cached. A newly published schema4 row is read back through the same complete scope/codec reader before its original passive Prepared body may share only the immutable data-valid slot; planner and typed after-state authority are removed. Historical readers, readonly inode/source cuts and complete checkpoint rederivation remain in force.


The existing SQLite Store implements the optional Execution `read_prefix` query by running its complete fresh `read_records` owner and only then selecting the requested prefix. It rereads all actual rows, including a valid pending tail outside that prefix, and retains original header/identity, index/bytes/digest, codec/anchor, flags, full lineage and anchored head checks. Even a zero-length request performs that complete source observation. A missing requested prefix is an error. No Source proof survives the call: the returned detached records supply neither Ready nor execution permission, and Core rechecks every selected row with its original prefix rules. The default Port capability supplies no batch and preserves generic point-read callback and immediate-error order. No write, observer, await or later public call reuses this local observation. Record/checkpoint bytes, physical/logical identities, preparation/readback, pending-tail recovery and financial semantics are unchanged.

Within `Runtime::records` and the idempotence lookup of `Runtime::apply`, the private immutable source has already passed that call's complete SQL read and full current-component reconciliation. These two local readers use its original records directly, without repeating the same prefix traversal through `Components::ready_records`. Returned records remain owned snapshots. New-input preparation and coordinator checks remain independent; no source view crosses a write, observer or public call, and no successful source proof is retained.

Encoded-record commit reuses one operation-local canonical `Prepared::encode` result for the complete Record envelope budget, physical codec and logical head digest. The original raw Record is built only for storage2; value-based codec entry points retain their original encoding semantics. The temporary encoding buffer is dropped before the SQL transaction; no additional retained byte cache is introduced. Cold storage3/4 reads may reuse the actual frame's logical digest only after the full physical/body SHA, canonical JSON, original Record validation and complete scope checks succeed; the digest is of the complete Prepared including its inner payload hash, never the inner hash itself. Actual source, flags, lineage, head, commit readback and recovery checks remain independent and unchanged.

Replay dictionary dependents bind their fixed self-contained step anchor's exact sequence, complete physical SHA and logical SHA. Every fresh full metadata scan still reads every actual row and validates that relation, Ready flags, whole lineage and anchored head. A point read observes target and fixed base in one SQLite JOIN snapshot; a pending anchor itself can be read, while a dependent requires its actual base to be Ready. Pure anchor bytes can be reused only after re-reading and checking the complete actual row. Logical readers retain bounded full canonical decoding and summary/body checks. The original stored-frame limit is checked before parsing a storage4 codec tag. New writes never fabricate or re-encode a retained ZLIB anchor as a dictionary; historical exact-Artifact, read-only inode/source cuts and unchanged archival bytes remain required. This changes new physical frames, not the canonical full Step content, input identity or logical-hash formula.


`Runtime::apply_prepared` is a technical composition port for an original opaque canonical planner object. It freshly reads the complete actual SQL source and performs full current-owner reconciliation before the original coordinator checks configuration, predecessor/before hashes, planner origin, durable commit readback, ordered projections and Ready. Existing identities compare the entire Prepared body; decoded values cannot introduce a new fact. It neither reauthors the input nor creates Product work/admission. Any failure closes the original Runtime recovery boundary; no alternate planner, fallback or retry is selected.


Cold and warm Record observations hold compact canonical data with independent expansion lifetimes from the private codec cache. Full physical/body verification, actual indexes/flags, dictionary anchors, full lineage and anchored head checks remain unchanged. Expanding an outward observation cannot populate the cache's body memo. Isolated proof readers likewise use compact record views while retaining every original source/reconciliation and checkpoint check. The canonical body remains complete; no history is discarded or replaced by headers, and exact older schema/artifact readers remain required.

For storage4 commit readback only, the current invocation may supply its original opaque validated Record to the private target reader. The actual target and fixed base still pass the complete physical digest, base64, bounded single-Zstd-frame, checksum, logical digest and canonical JSON decoder. The complete decoded Value must equal that exact original Prepared; ordinary cold reads and recovery use the independent Prepared decoder. Readback still compares the exact originally encoded stored bytes and physical digest, then preserves all normal index, scope, lineage, coordinator and Ready checks. Only passive data is reused through `observation_snapshot`: flags come from the actual columns and planner/typed origin is dropped. A dependent Execution point read requires its actual base Record to be Ready; a pending self-contained anchor itself remains readable. Missing, changed or malformed source is never completed from the local original object.

`Runtime::pending_events_at_replay_refs` is one read-only composition of the existing complete actual Execution/reconciliation, expected Replay prefix and pending Events queries. The same invocation-local source supplies all three; no source proof or acknowledgement is returned. A changed actual Replay/Execution source is rejected even when there are no pending Events. Consumer execution, actual acknowledgement and a subsequent complete source check remain separate boundaries.
