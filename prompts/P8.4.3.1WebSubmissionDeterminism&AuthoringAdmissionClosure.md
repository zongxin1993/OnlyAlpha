# 2. First-principles invariants

Treat these as hard requirements.

## 2.1 Submission uniqueness

A single unresolved browser submission intent must keep one Idempotency Key until the server returns an authoritative successful Run response.

Required:

```text
same pending submission intent
+
same authoritative Specification
→ same Idempotency-Key
```

Do not rotate the key merely because an HTTP error/status was observed.

## 2.2 Browser must not infer commit outcome

The Browser cannot know whether an error occurred before PostgreSQL commit or after PostgreSQL commit but before valid response delivery.

Therefore:

```text
submit throws
→ preserve current submission intent/key

authoritative successful submit response
→ consume/clear current submission intent
```

Do not classify 500/503/contract/decode/network failures as proof that no Run exists.

## 2.3 Submission identity != Research semantic identity

Do not make Specification fingerprint permanently map to one Run.

Correct relationship:

```text
Specification S1 + Submission Intent A
→ K1 → Run R1

retry Intent A
→ K1 → same R1

explicit new Run / Intent B with same S1
→ K2 → Run R2
```

The Idempotency Key is an operational retry token, not Research semantic identity.

## 2.4 Fail closed on authoring ambiguity

Draft → Definition conversion must obey:

```text
valid user intent
→ exact formal transport

invalid / stale / ambiguous user intent
→ explicit ResearchDraftError

never
→ silently truncate
→ silently filter
→ silently fallback
→ silently coerce to another semantic choice
```

## 2.5 Browser remains non-authoritative

Do not add browser-side semantic fingerprint algorithms, Specification generation, Dataset resolution, Candidate expansion, Calculation resolution, Predicate lowering, Statistics execution, or Result inference.

Server/domain remain authoritative.

# 5. Stage A — Submission Intent / Idempotency determinism

This is the primary blocking issue.

## 5.1 Problem

Current/previous Studio logic may clear the pending Idempotency Key when an error has an HTTP status.

That is unsafe because backend submission may already have durably committed the Run before a later load/serialization/proxy/network/contract failure.

Forbidden outcome:

```text
one original user submission intent
→ Run R1 + Run R2
```

## 5.2 Correct lifecycle

Use the authoritative `specification_fingerprint` returned by the latest successful Resolution only as an immutable identity token consumed from the server.

The Browser must not calculate it.

Conceptual pending state:

```ts
{
    specificationFingerprint: string;
    submissionKey: ResearchSubmissionKey;
}
```

Required behavior:

```text
No pending intent + submit S1
→ create K1
→ pending = (S1, K1)

retry S1 after any thrown submission failure
→ reuse K1

authoritative successful CREATED/REUSED response
→ clear pending intent

explicit later Run of S1
→ create K2

latest authoritative Resolution changes from S1 to S2
→ S2 submission uses a new intent/key
```

## 5.3 Minimal implementation only

Do not introduce:

- backend state;
- localStorage/IndexedDB submission persistence;
- Redux/Zustand/MobX/XState;
- global workflow store;
- Python domain objects for browser state.

A strengthened `ResearchRunSubmissionIntent` is sufficient.

A small API such as the following is acceptable if it fits current code style:

```ts
keyFor(specificationFingerprint): ResearchSubmissionKey
confirm(specificationFingerprint): void
```

Requirements:

- same fingerprint while pending → same key;
- different fingerprint → new key;
- successful authoritative completion → clear only matching pending intent;
- no semantic hashing in browser.

## 5.4 Error handling rule

Prefer the simplest safe rule:

```text
submitRun throws anything
→ keep pending intent

submitRun returns a valid admitted successful response
→ confirm / clear pending intent
```

Do not create fragile HTTP status classification rules.

## 5.5 Refresh boundary

Do not add persistent Browser workflow storage.

Current authority remains:

```text
Browser state disposable
PostgreSQL Run state durable
```

After page refresh, operational recovery belongs to `/research/runs`.

### Stage A Exit Gate

Must prove:

```text
same unresolved submission intent → same Idempotency-Key
uncertain failure → key preserved
authoritative success → intent completed
explicit later Run → new key
new authoritative Specification → new intent/key
```

# 7. Fixed parameter exactness

Do not allow logic equivalent to:

```text
all parameter text
→ split(',')
→ FIXED uses first value
```

This can silently transform:

```text
FIXED "7,14"
→ 7
```

Required behavior:

```text
FIXED
→ parse entire trimmed field as exactly one scalar

SWEEP
→ split explicit finite values
→ parse each scalar
```

Examples:

```text
FIXED INTEGER "7"      → PASS → 7
FIXED INTEGER "7,14"   → FAIL CLOSED
SWEEP INTEGER "7,14"   → PASS → [7,14]
SWEEP with <2 values    → FAIL CLOSED
```

Do not introduce range/optimizer semantics.

---

# 8. Published output exactness

```text

```

Required:

```text

∈ exact authoritative Catalog outputs
```

Otherwise raise `ResearchDraftError` at the corresponding path.

Preserve:

```text

```

No new Output Registry/Store is needed.

P8.4.3.1 exists to make the existing Web-native Research control loop exact, not larger.

Desired result:

```text
User Intent
→ exact Draft transport
→ authoritative Resolution
→ exact Specification
→ stable pending Submission Intent
→ at most one durable Run under retry uncertainty
→ exact Result
```

while preserving:

```text
one authority per fact
one semantic path
deterministic identities
fail-closed authoring
no silent semantic repair
minimal abstractions
clean Web/domain boundary
```

If an implementation proposal adds flexibility but weakens submission uniqueness, fail-closed behavior, authority ownership, or determinism, reject it and choose the simpler exact design.
