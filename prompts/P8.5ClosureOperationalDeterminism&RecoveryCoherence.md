# OnlyAlpha P8.5 Closure — Operational Determinism & Recovery Coherence

## 0. 任务性质

这是 **P8.5 Closure**，不是新的产品功能阶段，不是 P8.6，也不是一次架构重构。

当前 P8.5 已经实现：

- Research Worker production composition root；
- PostgreSQL Research Run / Attempt operational authority；
- lease / heartbeat / expiry / retry / fencing；
- cancellation reconciliation；
- Worker presence；
- health / readiness；
- operational diagnostics；
- run / attempt audit；
- structured operational logs；
- forward-only PostgreSQL migration；
- migration compatibility verification；
- logical backup / restore-test；
- PostgreSQL server/client version pinning；
- graceful Worker drain；
- `OnlyEngine -> OnlyResearchRuntime` 唯一 Research semantic execution path。

本任务的目标不是继续增加能力，而是：

> **让 P8.5 当前代码实现与其已经声明的“唯一性、确定性、可审计、可恢复”架构语义完全一致，为 P8.6 Product Closure / Final Certification 清除最后的 operational semantic gap。**

必须从第一性原理解决问题。

禁止“为了让测试通过”增加旁路、特殊状态、额外 Manager、第二套 authority 或 test-only production API。

# 4. C1 — Operational Snapshot Determinism

## 4.1 当前需要验证的问题

重点检查：

```python
OnlyPostgresResearchOperationsStore.load_operational_snapshot()
```

当前或此前实现大致为：

```text
connection
    ↓
SELECT observed_at
SELECT research_run
SELECT research_run_attempt
SELECT research_worker_presence
```

即使这些 SQL 位于同一个 PostgreSQL transaction 中，也必须判断：

```text
one transaction
是否真的等于
one MVCC snapshot
```

PostgreSQL 默认 READ COMMITTED 下，同一个 transaction 内不同 statement 可以观察到不同已提交状态。

因此存在潜在混合视图：

```text
Run       @ T1
Attempt   @ T2
Presence  @ T3
```

导致一个 `OnlyResearchOperationalSnapshot` 并不对应数据库中任何一个真实 observation point。

这违反 P8.5 已声明的 deterministic operational diagnosis 原则。

---

# 5. C1 第一性原理

Operational diagnostics 的需求不是“尽量看到最新数据”，而是：

> **在某一个确定数据库 observation 上，机械地推导一个只读 diagnosis。**

所以必须满足：

```text
OperationalSnapshot S
=
Runs(S)
+
Attempts(S)
+
WorkerPresence(S)
+
ObservedTime(S)
```

不能是：

```text
Runs(S1)
+
Attempts(S2)
+
WorkerPresence(S3)
```

---

# 6. C1 推荐实现

优先采用数据库本身提供的 MVCC 一致性机制。

目标应类似：

```text
READ ONLY
+
REPEATABLE READ
+
one transaction
```

使整个 `load_operational_snapshot()` 只消费一个稳定的 PostgreSQL snapshot。

不要通过应用层锁模拟 MVCC。
不要通过缓存解决。
不要通过重试“碰运气”。
不要把多张表复制成新的 snapshot table。

不要创建：

```text
OnlyOperationalSnapshotManager
OnlyDiagnosticsCoordinator
OnlySnapshotAuthority
```

---

# 7. C1 Transaction 设计要求

实现应尽可能局部。

原则上 `OnlyPostgresResearchOperationsStore` 仍然是唯一 PostgreSQL operational read adapter。

读取事务应明确：

```text
isolation = REPEATABLE READ
read_only = True
```

然后在这个 transaction 中读取：

```text
observed_at
research_run
research_run_attempt
research_worker_presence
```

`observed_at` 必须是该 operational observation 的统一时间基准。

需要仔细理解：

```text
transaction_timestamp()
statement_timestamp()
clock_timestamp()
```

之间的语义，不要机械替换函数。

目标是让 queue age、worker freshness、lease overdue 全部相对于一个明确 observation time 进行比较。

如果当前设计使用 PostgreSQL server clock 作为 lease / presence authority，则不要退回 Python process wall clock。

---

# 8. 不要过度升级隔离等级

不要默认采用 `SERIALIZABLE`，除非通过当前代码证明真的有必要。

本需求只是 stable read snapshot，不是 serializable mutation transaction。

诊断事务是 read-only，因此原则上 `REPEATABLE READ` 已经足够。

同样不要使用 `SELECT FOR UPDATE`，因为 observation 不应该阻塞或改变 execution。

# 9. C1 并发 Integration Test

必须增加一个真正证明 MVCC 不变量的 PostgreSQL integration test。

不要只测试“调用两次函数结果相同”，那不能证明问题。

需要主动制造 Reader / Writer interleaving。

目标场景：

```text
Initial:
Run = QUEUED
Attempt = none
```

Reader：

```text
开始 Operational Snapshot transaction
固定 snapshot S
读取 Run
```

此时 Writer：

```text
claim Run
    ↓
Run QUEUED -> RUNNING
create ACTIVE Attempt
COMMIT
```

数据库最新状态变为：

```text
Run = RUNNING
Attempt = ACTIVE
```

Reader 继续读取 Attempt / Presence 并完成 snapshot。

Reader 必须得到一个内部一致状态，例如：

```text
S:
Run = QUEUED
Attempt = none
```

而不能得到：

```text
Run = QUEUED
Attempt = ACTIVE
```

之后新的 Reader S2 应看到：

```text
Run = RUNNING
Attempt = ACTIVE
```

核心不变量：

```text
S1 != S2
允许。

S1 内部跨时间拼接
不允许。
```

# 12. C2 — PostgreSQL + Immutable Store Recovery Coherence

第二个 Closure 问题不是增加 backup system。

目标是：

> **把 PostgreSQL operational backup 与 immutable semantic store snapshot 之间的正确关系明确成一个可以推导、可以验证的 recovery invariant。**

---

# 13. Recovery 的第一性原理

OnlyAlpha 当前有两类持久事实：

```text
PostgreSQL
=
operational projection
```

以及：

```text
USER_DATA_ROOT/research
=
semantic truth
```

完整灾备因此必然需要：

```text
Operational backup
+
Semantic storage backup
```

不存在一个单独 PostgreSQL dump 就能恢复完整 Research product 的情况。

但也不要因此试图把所有 semantic Result 写进 PostgreSQL，这会直接破坏现有 architecture。

---

# 14. 从 commit ordering 推导 backup ordering

先重新确认当前 Research execution commit 顺序。

原则应保持：

```text
semantic commit
    ↓
Research Result verified
    ↓
Artifact verified
    ↓
fenced PostgreSQL completion
```

也就是 semantic truth exists BEFORE Run is finalized COMPLETED with its references。

必须从实际源码验证，不要只相信 Prompt。

如果事实如此，则可推导恢复不变量：

```text
如果 PostgreSQL backup 已经记录
Run COMPLETED -> Result R -> Artifact A

那么 paired USER_DATA_ROOT snapshot
必须包含 R 和 A。
```

---

# 15. 推荐的 Backup Pair 顺序

对于在线 logical backup：

```text
T1:
capture PostgreSQL backup

        ↓

T2 >= T1:
capture immutable USER_DATA_ROOT snapshot
```

如果 T1 时 Run 已是 COMPLETED，由于 semantic commit 必须先发生，Result / Artifact 在 T1 前已经存在。

T2 又晚于 T1，因此 filesystem snapshot 应包含这些对象。

所以：

```text
PostgreSQL referenced semantic objects
⊆
restored immutable semantic objects
```

这是核心 recovery invariant。

---

# 16. Extra Semantic Objects 是允许的

如果发生：

```text
T1:
DB backup sees Run = RUNNING

T1 < Tsemantic:
Result + Artifact committed

T2:
filesystem snapshot contains Result + Artifact
```

恢复后可能得到：

```text
PostgreSQL:
Run = RUNNING

Immutable store:
Result + Artifact already exist
```

这是允许的。

因为 deterministic re-entry 应：

```text
verified-load
→ REUSED
→ fenced finalization
```

最终重新收敛。

所以正式原则应是：

```text
Extra immutable semantic objects
are safe.

Missing immutable semantic objects
already referenced by restored durable PostgreSQL facts
are unsafe.
```

---

# 17. 反向 Backup 顺序需要明确警告

以下顺序可能是不安全的：

```text
filesystem snapshot T1
        ↓
new Result / Artifact commit
        ↓
Run COMPLETED
        ↓
PostgreSQL backup T2
```

恢复时可能得到 PostgreSQL 已记录 COMPLETED + ResultRef/ArtifactRef，但 filesystem snapshot 不包含对应对象。

这种状态不能当作 normal cache miss，也不能 silent recompute / repair / overwrite / delete terminal Run。

它应被视为 recovery set 不一致 / immutable authority missing，并 fail closed。

---

# 18. Worker Drain 的定位

可以在 runbook 中提供更保守的维护窗口方案：

```text
Worker drain
→ 当前 Attempt safe completion
→ stop new claims
→ PostgreSQL backup
→ USER_DATA_ROOT snapshot
```

但是 Worker drain 不得成为恢复正确性的唯一前提。

它只是降低恢复时 forward re-entry 工作量的 operational optimization，不是 correctness authority。

在线 DB-first + semantic-snapshot-after 模式本身应该具有架构解释。

---

禁止：

```text
2PC
XA transaction
PostgreSQL/filesystem distributed transaction
global filesystem lock
backup database
```

```text

+

+

```

解决跨存储恢复问题。

# 26. Error Handling 原则

所有 uncertainty 必须 fail closed。

不能：

```text
except Exception:
    return empty snapshot
```

不能：

```text
DB unavailable
→ 假装 no workers
```

不能：

```text
Result missing during recovery
→ rebuild silently
```

不能：

```text
mixed operational state
→ choose newest row heuristically
```

正确方向：

```text
Unavailable
→ explicit unavailable error

Corrupt
→ explicit integrity failure

Unknown
→ no finalization / fail closed
```
