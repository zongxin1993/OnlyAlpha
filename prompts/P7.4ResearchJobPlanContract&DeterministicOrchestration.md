# OnlyAlpha P7.4 Codex Task Prompt

## P7.4 — Research Job / Plan Contract & Deterministic Orchestration

> 本任务用于 OnlyAlpha P7.4 阶段实现。
>
> **核心目标：**在不引入 Trading Runtime 语义、不复制既有 Calculation/Dataset/Result authority、不提前实现 Sweep/Statistics/Research Runtime 的前提下，为 Research 建立第一个正式、确定、可重入、可验证的单作业执行合同：
>
> ```text
> Resolved Research Job
> → verified upstream authorities
> → deterministic reuse-or-execute
> → immutable Calculation Result
> → explicit Job Outcome
> ```

---

# 0. 最高优先级原则

OnlyAlpha 的工程决策必须遵循：

```text
正确性
> 架构一致性
> 可验证性
> 可恢复性
> 可维护性
> 性能
> 自动化程度
```

不要为了减少代码、让 Prompt 更快结束、提高复用程度或让 Agent 更方便，而破坏前面的目标。

特别强调：

1. **Repository 是当前事实来源。**
2. 在开始实现前，必须重新完整阅读当前 HEAD，而不是仅依赖本 Prompt。
3. 本 Prompt 是阶段目标和设计约束，不覆盖当前源码、测试、ADR 和质量系统中的新事实。
4. 如果当前 HEAD 与本 Prompt 的前提发生冲突，应停止机械实现，先在最终报告中明确冲突；不得为了符合旧 Prompt 而破坏当前架构。
5. 不要在没有 current-truth 证据时假定 P7.3 已认证、某 API 名称仍然存在、某目录结构仍未变化。

# 2. P7.4 的阶段定位

P7.0–P7.3 已分别建立或正在建立以下基础：

```text
P7.0
Calculation Semantic Foundation

P7.1
Immutable Dataset Snapshot Authority

P7.2
Deterministic RESEARCH Calculation Execution

P7.3
Immutable Calculation Result Authority
```

P7.4 不再增加新的底层 Indicator 算法，不重新设计 Dataset Store，也不重新设计 Result Store。

P7.4 要解决的是当前最重要的 Application Layer 缺口：

> 对于一个已经完全解析、具有精确 Dataset 和 Calculation Graph 的 Research 请求，系统如何以唯一、确定、可验证、可重入的方式执行，并安全复用已有 durable Result？

当前已有 primitives 可以单独完成：

```text
verified Dataset
+ Calculation Graph
+ deterministic executor
+ immutable Result Store
```

但还没有一个正式 contract 定义：

```text
“执行一次 Research Job”
```

究竟意味着什么。

P7.4 必须建立这个 contract。

# 3. 第一性原理问题定义

P7.4 必须回答以下问题。

## 3.1 What exact work is requested?

Research Job 必须引用精确语义输入，而不是模糊、可变或环境相关输入。

禁止正式 Job 直接表达类似：

```yaml
dataset: latest_a_share
indicator: ema
period: 20
```

因为这里仍存在：

```text
latest 到底是哪一个 snapshot？
EMA 是哪一个 exact semantic version？
Input bindings 是什么？
Graph topology 是什么？
Dataset schema 是否匹配？
```

正式执行边界必须接收已经解析完成的 exact semantic references。

至少应建立概念上的：

```text
Resolved Research Job / Resolved Research Plan
```

它只引用：

```text
exact Dataset Snapshot identity
+
exact Calculation Graph authority
```

不得把 human-friendly resolution、latest alias、动态 registry lookup 等不稳定解析逻辑混入 durable semantic execution contract。

---

## 3.2 What is the semantic identity of a P7.4 single job?

必须首先检查当前 P7.2/P7.3 的 identity contract。

如果当前单一 Research Job 的全部语义仍然只是：

```text
Dataset Snapshot
+
Calculation Graph
+
fixed RESEARCH execution semantics
```

并且这些内容已经完整进入：

```text
calculation_fingerprint
```

那么 **P7.4 v1 不得为了“Job 看起来应该有自己的 hash”而额外创造重复的 `research_plan_fingerprint` 或 `research_job_fingerprint`。**

原则：

```text
One semantic fact → one authority identity
```

若新增 fingerprint 不增加任何新语义，只是再次 hash `calculation_fingerprint`，则属于重复 authority，应避免。

允许存在 operational identity，例如：

```text
job_run_id
attempt_id
trace_id
submitted_at
```

但这些字段只能属于 provenance / diagnostics，不得进入 Research semantic identity，不得改变 Calculation Result identity。

如果 current HEAD 已经增加了新的、确实超出 `calculation_fingerprint` 的 Research Plan 语义，则应重新评估；必须在 ADR 中解释为什么新 identity 是必要且非重复的。

# 4. P7.4 目标架构

目标逻辑链路：

```text
Resolved Research Job
        ↓
Validate exact semantic inputs
        ↓
Verified Dataset Snapshot
        +
Canonical Calculation Graph
        ↓
Derive / verify Calculation Identity
        ↓
Attempt verified Result load
        │
        ├── valid Result exists
        │       ↓
        │      REUSE
        │
        ├── Result absent
        │       ↓
        │   P7.2 execute
        │       ↓
        │   P7.3 immutable commit
        │       ↓
        │   verified Result
        │
        └── Result corrupt / invalid
                ↓
             FAIL CLOSED

        ↓
Explicit Research Job Outcome
```

P7.4 应该建立一个正式 orchestration layer。

建议逻辑 ownership：

```text
research/job/
    plan.py
    outcome.py
    errors.py
    executor.py
    ports.py       # only if current architecture truly needs an SPI boundary
```

具体文件名不是硬性要求；应按当前仓库风格决定。

但依赖方向必须明确：

```text
Research Runtime (future)
        ↓
Research Job layer
        ↓
Dataset / Calculation / Result authorities
```

禁止：

```text
Research Job
        ↓
Trading Runtime / Cluster / Account / Broker / Order / Position
```

# 6. Research Runtime 在 P7.4 中的处理

当前如果 `OnlyResearchRuntimeFactory` 仍为 unsupported，而 `OnlyResearchRuntime` 仍继承 trading-shaped `OnlyRuntime`，则：

## 必须保持 Research Runtime Factory unsupported

P7.4 不得为了展示“功能可运行”而直接激活 Research Runtime Factory。

原因：

当前 trading-shaped `OnlyRuntime` 如果仍然拥有或导入大量 Trading authorities，那么直接激活 Research Factory 会把错误的抽象永久固化。

P7.4 的正确目标是：

```text
先形成独立、干净、Research-shaped 的 Job contract
```

而不是：

```text
先把 Research 塞进现有 Trading Runtime
```

如果 current HEAD 已经完成了真正的 Research Runtime base extraction，则可以重新判断；但必须有源码与 architecture tests 证明该 Runtime 已不再依赖 Trading authority。

# 7. Research Job / Plan Contract

建立最小、精确、不可含糊的 resolved contract。

概念上可类似：

```python
@dataclass(frozen=True)
class OnlyResearchJobPlan:
    schema_version: int
    dataset_snapshot_fingerprint: str
    calculation_graph: OnlyCalculationGraph
```

这里只是表达语义，不要求机械复制名字。

要求：

1. immutable；
2. exact schema/version；
3. fail-closed parsing/validation（如果存在 serialized form）；
4. Dataset fingerprint 必须使用当前正式 identity validator；
5. Graph 必须是 current canonical graph contract；
6. 不允许 path、provider、machine、process、wall-clock、compression、worker 数、filesystem root 等 operational 属性进入 semantic plan；
7. 不允许 “latest”/“default” 等动态 alias 进入正式 resolved plan；
8. 不允许在 Job layer 重新定义 Calculation Graph 的 semantic payload；
9. 不允许复制 P7.0 Calculation Definition 的 schema；
10. 不允许复制 P7.1 Dataset identity；
11. 不允许复制 P7.3 Result identity。

如果 serialized plan 是必要的，则必须使用 exact field set / versioned schema / unknown-field reject 的 fail-closed contract，与 OnlyAlpha 当前 manifest/definition 风格一致。

如果没有业务需求，不要为了“完整”而引入 serialization。

---

# 8. Deterministic Research Job Orchestrator

建立一个 application-level executor/orchestrator。

概念上类似：

```python
class OnlyResearchJobExecutor:
    def execute(self, plan: OnlyResearchJobPlan) -> OnlyResearchJobOutcome:
        ...
```

职责必须严格限制在：

```text
validate plan
→ resolve/verify upstream authorities
→ decide reuse vs execute
→ invoke P7.2 executor
→ invoke P7.3 Result Store
→ return explicit outcome
```

它不得：

- 实现 Indicator 算法；
- 实现 Parquet store internals；
- 绕过 Dataset verified load；
- 绕过 Calculation Result verified load；
- 重复 graph fingerprint 算法；
- 重新定义 calculation fingerprint；
- 修改 Trading Kernel；
- 创建 mutable global Job registry；
- 创建 scheduler；
- 创建 worker pool；
- 创建 multiprocessing/distributed abstraction；
- 实现 retry daemon。

---

# 9. Verified Reuse Semantics

这是 P7.4 的核心 contract 之一。

必须严格区分：

```text
physical existence
```

与：

```text
verified durable authority
```

如果 current `CalculationResultStore.exists()` 只是检查 physical target 是否存在，则 Job orchestration **绝对不能**使用：

```python
if result_store.exists(calculation_fingerprint):
    return success
```

正确语义必须是：

```text
try load_verified(calculation_fingerprint)

valid
→ REUSE

RESULT_NOT_FOUND
→ execute

RESULT_CORRUPT / RESULT_INVALID / identity mismatch
→ FAIL CLOSED
```

不得把 corrupt result 当 cache miss。

不得自动 delete corrupt result。

不得自动 overwrite corrupt result。

不得 fallback 到 recomputation 来掩盖 durable authority corruption。

原因：

P7.3 Result Store 不是 cache，而是 immutable durable authority。

P7.4 必须保持：

```text
absence
→ calculation allowed

verified existence
→ reuse

corruption
→ fail closed

same calculation + different result
→ deterministic conflict
```

---

# 10. Execute Path

当且仅当 verified Result 明确不存在时，P7.4 才进入 execution path。

执行顺序应保持：

```text
validate plan
↓
verify/load Dataset authority
↓
verify Calculation Graph / identity
↓
P7.2 deterministic execution
↓
P7.3 immutable Result commit
↓
verified Result reload / verified commit return
↓
SUCCEEDED / EXECUTED
```

必须复用 P7.2 和 P7.3 已建立的 defensive checks。

不要在 P7.4 复制：

```text
Arrow schema validation
output column validation
timestamp axis validation
partition fingerprint logic
byte hash validation
semantic result hash logic
atomic rename logic
```

这些继续属于 Dataset/Calculation/Result authority。

---

# 11. Job Outcome Contract

P7.4 应增加一个小而明确的 operation result，用于表达这次 Job invocation 的终态。

概念上：

```text
ResearchJobOutcome
    status
    calculation_fingerprint
    calculation_result_fingerprint
    disposition
```

其中可采用：

```text
status:
    SUCCEEDED

execution disposition:
    EXECUTED
    REUSED
```

如果当前项目习惯让失败通过 exception 表达，则不要为了对称强行创建 `FAILED` outcome。

推荐语义：

```text
Successful invocation
→ returns immutable success outcome

Failure
→ raises stable domain/application error
```

而不是返回：

```text
success=False
error="something failed"
```

必须保证：

```text
EXECUTED vs REUSED
```

只是 operational provenance，不得改变：

```text
calculation_fingerprint
calculation_result_fingerprint
```

相同语义输入第一次 EXECUTED，第二次 REUSED，最终 authoritative result identity 必须相同。

不要把 `executed_at`、`worker_id` 等 operational 字段加入 semantic fingerprint。

---

# 12. Failure Semantics

P7.4 必须建立清晰 application-level failure propagation，但不要吞掉底层稳定错误语义。

应明确至少这些阶段：

```text
PLAN_VALIDATION
DATASET_VERIFICATION
RESULT_REUSE
CALCULATION_EXECUTION
RESULT_COMMIT
```

如果需要新增 Job-specific error，可以采用类似：

```text
RESEARCH_JOB_INVALID
RESEARCH_JOB_EXECUTION_FAILED
```

但禁止把所有底层错误统一抹平成一个无信息的：

```text
RESEARCH_JOB_FAILED
```

必须保留或可追踪到底层稳定原因，例如：

```text
RESEARCH_DATASET_VERIFICATION_FAILED
RESULT_NOT_FOUND
RESULT_CORRUPT
RESULT_INVALID
RESULT_COMMIT_FAILED
DETERMINISTIC_RESULT_CONFLICT
```

最佳目标：

```text
Job phase
+
stable code
+
underlying domain cause
```

具体错误继承结构请遵循当前仓库 error model，不要发明完全不同的异常系统。

# 13. Re-entrant Recovery Semantics

P7.4 v1 不应引入复杂 mutable Job database。

不要实现：

```text
QUEUED
RUNNING
PAUSED
RETRYING
CANCEL_REQUESTED
worker lease
scheduler heartbeat
job checkpoint database
```

P7.4 应利用 P7.3 immutable result authority，建立 **re-entry recovery**。

## 情形 A：Result commit 前进程崩溃

```text
Result absent
↓
相同 Job 再次执行
↓
verified load => NOT_FOUND
↓
重新执行
↓
commit
```

## 情形 B：Result 已 commit，但进程在返回 outcome 前崩溃

```text
Result valid
↓
相同 Job 再次执行
↓
verified load
↓
REUSED
```

## 情形 C：Result durable state 已损坏

```text
verified load
↓
RESULT_CORRUPT
↓
fail closed
```

这就是 P7.4 v1 的 recovery model。

不要提前创建第二套 mutable recovery authority。

---

# 14. Concurrency Semantics

P7.4 必须验证 concurrent same-job behavior。

当两个 process/thread 同时提交完全相同 semantic Job：

```text
Job A ─┐
       ├→ same calculation_fingerprint
Job B ─┘
```

允许两者都进入 ephemeral calculation，但 durable result 最终必须仍只有一个 authority。

依赖 P7.3 当前 commit/race semantics：

```text
first durable winner
→ authority

second same verified result
→ idempotent success / reuse-equivalent success

second different result
→ DETERMINISTIC_RESULT_CONFLICT
```

P7.4 不应再引入一个独立 global lock authority 来替换 P7.3 的 durable conflict contract，除非 current repository 已明确需要且有充分设计依据。

测试必须证明 concurrent same-job 最终不会形成两个 semantic authorities。

# 19. Required Test Matrix

实现完成后，必须建立足够完整的正式 tests。

下面是最低要求；应根据 current APIs 调整具体测试名。

## 19.1 Happy path — first execution

输入：

```text
valid verified Dataset
+
valid canonical Calculation Graph
+
no existing Result
```

期望：

```text
Job validates
→ P7.2 executes
→ P7.3 commits
→ returns success outcome
→ disposition = EXECUTED
→ exact calculation_fingerprint
→ exact calculation_result_fingerprint
```

---

## 19.2 Same job — verified reuse

第一次运行完成后再次提交 exact same plan。

必须证明：

```text
load_verified succeeds
→ Calculation Executor is not invoked
→ Result commit is not repeated unnecessarily
→ disposition = REUSED
```

使用 spy/fake/monkeypatch 时应遵循项目测试习惯，不要侵入 production design。

---

## 19.3 Fresh-process reuse

在新的 Store/Executor instance 或等价 fresh-process simulation 下提交同一 Job。

必须证明结果 identity 和 values 可从 durable authority 恢复并 reuse。

---

## 19.4 Missing Result triggers execution

`RESULT_NOT_FOUND` 是唯一标准 miss path。

不得把其他 result read errors 当 miss。

---

## 19.5 Corrupt Result fail-closed

制造 physical/semantic corruption，提交同一 Job。

必须证明：

```text
load_verified => RESULT_CORRUPT
→ Calculation Executor NOT invoked
→ no automatic repair
→ no overwrite
→ failure propagated
```

这是 P7.4 最重要的 negative test 之一。

---

## 19.6 Result invalid/path identity mismatch fail-closed

如果 current Result Store 区分 `RESULT_INVALID` 等错误，也必须证明它不会 fallback execute。

---

## 19.7 Dataset verification failure

Dataset snapshot 不存在、损坏或 verification failure 时：

```text
Job fails
→ no Calculation Result published
→ no fake success outcome
```

复用 current stable dataset error semantics。

---

## 19.8 Graph / calculation identity mismatch

构造 forged/mismatched plan，例如：

```text
wrong graph fingerprint
wrong dataset fingerprint linkage
wrong calculation fingerprint if API exposes it
```

必须 fail closed。

不要允许 caller 提供一个未经 recomputation/verification 的 `calculation_fingerprint` 作为 authority。

---

## 19.9 Calculation failure

让 P7.2 backend 执行失败。

必须证明：

```text
no durable Result
no success outcome
stable failure propagation
```

---

## 19.10 Result commit failure

模拟 P7.3 stage write / verification / rename failure。

必须证明：

```text
Job fails
no partially published authority
```

依赖 P7.3 的 atomic semantics，不重新实现 cleanup protocol。

---

## 19.11 Deterministic result conflict

同一 calculation semantic identity 对应不同 verified result 时：

```text
DETERMINISTIC_RESULT_CONFLICT
```

必须传播并 fail closed。

不得转成 REUSED。

---

## 19.12 Concurrent same-job

并发执行 exact same job。

必须证明：

```text
one durable authority
both invocations converge to same final identity
no duplicate semantic result
```

---

## 19.13 EXECUTED vs REUSED identity invariance

必须明确证明：

```text
first run: EXECUTED
second run: REUSED
```

但：

```text
calculation_fingerprint identical
calculation_result_fingerprint identical
```

---

## 19.14 Operational provenance does not affect semantic identity

如果 Job Outcome 包含 run id / audit time 等字段，改变这些字段不得改变 Calculation/Result identity。

---

## 19.15 Trading boundary architecture tests

自动检查 Research Job production files 不导入禁止的 trading modules/classes。

---

## 19.16 Research Runtime remains unsupported

如果 current truth 仍如此，则测试冻结该事实。

---

## 19.17 Official Factor remains current truth

若官方 Factor provider 当前为空，不得因为 P7.4 改变；相关现有 tests 必须继续通过。

# 20. API Design Principles

新增 public API 时遵循：

1. immutable value objects 优先；
2. constructor 做 structural validation；
3. authority validation 不要散落到 caller；
4. stable domain error codes；
5. no boolean soup；
6. no ambiguous optional fields；
7. exact naming；
8. 不暴露 filesystem path 作为 semantic input；
9. 不允许 wall-clock default 悄悄进入 identity；
10. 不允许 implicit global registry 决定 execution semantics；
11. 不要建立仅有一个 implementation 却没有 architecture boundary 价值的多层 interface hierarchy；
12. Port/Protocol 只在确实需要 inversion/testability 且符合 current style 时引入。

---

# 21. Determinism Requirements

P7.4 必须保证相同 semantic job 在以下变化下仍收敛到相同 authoritative result identity：

```text
process restart
new executor instance
new store instance
filesystem root change
physical Parquet settings change（如果 upstream authority identity 已独立）
job invocation timestamp change
run id change
caller code path change
EXECUTED vs REUSED
```

这些 operational 差异不能进入 semantic identity。

如果某项当前底层 authority 尚未保证，不要在 P7.4 私自伪造保证，应在报告中明确边界。

---

# 22. Security / Integrity / Fail-Closed Requirements

沿用 P7.1/P7.3 风格：

- 所有 durable identity 必须通过当前 canonical validator；
- 不信任 caller 提供的 fingerprint linkage；
- durable authority 必须 verified before use；
- corrupt target 不自动覆盖；
- deterministic conflict 不吞掉；
- unknown serialized fields（如果存在 serialization）必须 reject；
- invalid version 必须 reject；
- 不允许 path traversal 等 physical data influence semantic plan；
- 不允许 symlink/physical bypass 绕过 existing store verification。

P7.4 不需要自己重复 filesystem hardening，但必须保证只通过 verified store API 读取 authoritative Result。

# 33. P7.4 的核心不变量总结

实现过程中，任何设计不确定时，以以下不变量为判断标准：

```text
1. Research Job != Trading Cluster
2. Research Job 不拥有 Trading authorities
3. Resolved Plan 只包含 exact semantic references
4. 不为同一 semantic fact 创建重复 identity authority

6. Result reuse 必须依赖 load_verified，而不是 exists
7. RESULT_NOT_FOUND 才是 execute miss
8. RESULT_CORRUPT / INVALID 必须 fail closed
9. Calculation Result != Research Result != Research Artifact
10. Job invocation provenance 不得进入 calculation/result semantic identity
11. P7.4 recovery 采用 deterministic re-entry，不引入 mutable Job DB
12. 同一 Job 并发必须收敛到一个 durable authority
13. P7.2 Executor 继续负责 calculation execution
14. P7.3 Store 继续负责 immutable result authority
15. P7.4 只负责 application orchestration
16. Research Runtime Factory 不得因 P7.4 被勉强激活
17. 不实现 Sweep / Statistics / Scheduler / Web
18. Repository current truth 高于本 Prompt
```
