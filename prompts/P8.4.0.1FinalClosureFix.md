# 5. 问题一 — Dataset Source Spelling 泄漏 Resolved Identity

## 5.1 当前问题

当前 Research Calculation Input 可以表达：

```python
source="close"
```

或者：

```python
source="bar.close"
```

而 Resolver 当前类似：

```python
field = source.removeprefix("bar.")
```

最终两者都会 lowering 成：

```text
bar.close
```

即：

```text
same exact execution semantics
```

但是 `OnlyResearchCalculationInstance.semantic_dict()` 仍可能保留原始：

```text
close
```

或：

```text
bar.close
```

从而进入：

```text
resolved_definition_fingerprint
```

导致：

```text
same Graph
same Specification
same Workload

but

different resolved_definition_fingerprint
```

这违反：

> Same authoritative resolved semantics must produce the same resolved semantic identity.

---

# 6. Dataset Source 的正确 V1 Contract

优先采用最简单、最明确的规则：

> **Research Definition V1 只允许 canonical Dataset source spelling：`bar.<field>`。**

例如合法：

```text

bar.low
bar.close
bar.volume
```

非法：

```text
open

```



# 11. 问题二 — Diagnostic Path 被 Semantic Canonicalization 改写

这是本任务最重要的修复。

---

# 12. 当前问题

Boolean AST 为了 semantic identity，目前会 canonicalize：

```text
A AND B
B AND A
```

成为相同结构。

这本身是正确的。

但是如果模型构造阶段直接：

```python
only_canonicalize_research_expression()
```

排序 operands，那么：

用户提交：

```text
signals.entry.operands[0] = RSI < 30
signals.entry.operands[1] = Momentum > "bad"
```

canonicalization 后可能变成：

```text
operands[0] = Momentum > "bad"
operands[1] = RSI < 30
```

之后 Resolver 返回：

```text
signals.entry.operands[0].right
```

这个 path 已经不是用户提交时的：

```text
operands[0]
```

。

未来 Web Builder 无法可靠把 error 映射回用户正在编辑的 control。

必须对应 submitted Definition 中的真实顺序。
