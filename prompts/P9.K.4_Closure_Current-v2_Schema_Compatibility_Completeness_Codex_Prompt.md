# 3. First-Principles Compatibility Model

Do not add isolated `if` statements without preserving the underlying model.

The compatibility direction frozen by ADR 0103 is:

```text
old v2 client
→ new v2 server
```

Therefore:

## Request compatibility

Every request that was valid under the old contract must remain valid under the new contract:

```text
Accepted(old_request)
⊆
Accepted(new_request)
```

## Response compatibility

Every response the new server may legally produce must remain consumable by the old client:

```text
Produced(new_response)
⊆
Consumable(old_response)
```

All rules for:

```text
type
enum
const
required
properties
additionalProperties
composition
constraints
```

must be derived from these two directional set relationships.

Do not treat request and response compatibility as symmetric.

Current v2 uses `Literal[...]`, which FastAPI/Pydantic emits as `const`.


# 10. `const` and `enum` Interaction

Do not create contradictory rules.

Conceptually:

```text
const A
≈ exact singleton value set {A}
```

and:

```text
enum [A, B]
≈ finite allowed value set {A, B}
```

If a schema contains both or transitions between them, compatibility must still follow the same directional allowed-value-set logic.

Implement the minimum needed for current v2 and characterization fixtures.

Do not build a generic symbolic set engine unless necessary.

