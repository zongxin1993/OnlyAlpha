# 1. Task Purpose

P9.K.4 turns OpenAPI from generated documentation into a **governed public product compatibility artifact**.

The actual problem is not:

```text
“we need another OpenAPI tool”
```

The actual problem is:

> How does OnlyAlpha ensure that one public HTTP contract has one authoring authority, one deterministic canonical projection, one immutable accepted compatibility baseline, one exact contract identity, and one mechanical breaking-change decision?

Current architecture already has:

```text

        ↓

        ↓
contracts/research-api/v2/openapi.json
        ↓
openapi-typescript
        ↓
generated.ts
```

and already supports freshness checking.

K4 must preserve this foundation and add:

```text
canonical contract identity
+
lint
+
compatibility comparison
+
API versioning rules
+
client-generation governance
+
mechanical CI enforcement
```

without changing business semantics.

# 8. Breaking-Change Policy

Implement/verify at least the following categories.

## 8.1 Path / Operation breaking changes

Breaking:

```text
remove path
remove HTTP method
rename path
change method
remove operation
```

---

## 8.2 Request breaking changes

Breaking examples:

```text
optional field → required
add required field
string → integer
nullable → non-nullable
remove accepted enum value
narrow pattern
narrow numeric range
remove accepted content type
new required HTTP header
```

---

## 8.3 Response breaking changes

Breaking examples:

```text
remove response field
change response field type
required response field → optional/may disappear
remove existing response status
remove response content type
change nullability in a way old clients cannot safely consume
```

---

## 8.4 Enum direction must be understood

Request enum expansion:

```text
A | B
→ A | B | C
```

is normally compatible for old-client → new-server behavior.

Response enum expansion:

```text
A | B
→ A | B | C
```

may be breaking because an old generated client may not understand `C`.

Do not blindly inherit a third-party tool's default enum classification without characterization tests.

---

## 8.5 operationId is part of public client compatibility

Changing an `operationId` can rename generated client symbols while path/method remain unchanged.

For current v2 policy:

```text
operationId change
→ breaking
```

unless a later ADR deliberately changes this policy.

# 49. Final Engineering Principle

Do not optimize for “using OpenAPI tools”.

Optimize for this unique deterministic contract chain:

```text
FastAPI Routes + API DTO
        ↓
one deterministic canonical OpenAPI
        ↓
one exact SHA256 contract identity
        ↓
one immutable Git historical baseline
        ↓
one compatibility verdict
        ↓
one generated client source
```

The two most important anti-corruption rules are:

```text
candidate contract and accepted baseline
must never be mutable together
```

and:

```text
API compatibility identity
must never become business/semantic identity
```

K4 is correct when public compatibility changes become mechanically visible and reviewable, while the current HTTP behavior, Research semantics, Strategy/P9.0 semantics, persistence semantics and canonical v2 contract remain unchanged.
