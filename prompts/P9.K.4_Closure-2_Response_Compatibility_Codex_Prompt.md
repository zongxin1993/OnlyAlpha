# 2. 本任务要解决的真实问题

当前 `scripts/openapi_contract.py` 已实现大量 direction-aware compatibility：

```text
type
enum
const
additionalProperties
items
composition
recursive references
discriminator
constraints
unknown schema vocabulary fail-closed
```

但当前 response-side compatibility 仍存在漏判。

## 2.1 根本 invariant

ADR 0103 冻结的兼容方向是：

```text
old-v2-client
→
new-v2-server
```

因此：

### Request

旧客户端过去可以发送的请求，新服务端必须继续接受：

```text
OldValidRequests ⊆ NewAcceptedRequests
```

### Response

新服务端未来可能产生的响应，旧客户端必须仍然能够消费：

```text
NewPossibleResponses ⊆ OldClientConsumableResponses
```

这不是“JSON 文档差异比较”。

这是两个 contract 描述的 **语义允许集合之间的包含关系**。

所有实现与测试必须围绕这个第一性原理展开。

# 4. 缺陷 A：closed response 新增 named property 被漏判

当前 `_schema_changes()` 的 property traversal 主要从 old properties 向 new properties 遍历。

因此以下 response change 可以被错误判为 COMPATIBLE。

Old：

```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "status": {
      "type": "string"
    }
  },
  "required": [
    "status"
  ]
}
```

New：

```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "status": {
      "type": "string"
    },
    "detail": {
      "type": "string"
    }
  },
  "required": [
    "status"
  ]
}
```

即使 `detail` 是 optional，这也必须是：

```text
BREAKING
```

原因：

```text
New server can emit:
{"status":"A","detail":"x"}

Old client schema:
additionalProperties = false

Therefore:
new response set ⊄ old consumable response set
```

这不是 style 问题，也不是未来 hardening。

这是 ADR 0103 response compatibility invariant 的 correctness defect。

# 5. 缺陷 B：new response status 没有进入 old-client compatibility 检查

当前 response comparison 主要遍历 old response statuses。

因此：

```text
old:

new:
200
202
```

新增 `202` 可能没有被发现。

本次 Closure-2 采用严格且保守的当前 v2 policy：

```text

```

不要在本任务中重新讨论或放宽旧 policy。

目标是关闭 false-negative，而不是重写 compatibility policy。

# 7. 第一性原理下的正确 response property 语义

对于一个 **new-only named response property**：

```text
property ∈ new.properties
property ∉ old.properties
```

不能一律判 BREAKING。

必须根据 old schema 对“原本未知字段”的接受能力判断。

## 7.1 冻结决策矩阵

| old `additionalProperties` | new-only response property | Verdict |
|---|---|---|
| `false` | 任意新增字段 | BREAKING |
| `true` | 任意新增字段 | COMPATIBLE |
| missing | 等价于 `true` | COMPATIBLE |
| schema | new property schema 是 old AP schema 的子集 | COMPATIBLE |
| schema | new property schema 超出 old AP schema | BREAKING |

其中 response 方向仍然是：

```text
new ⊆ old
```

# 8. 关键例子：additionalProperties schema

Old：

```json
{
  "type": "object",
  "additionalProperties": {
    "type": "string",
    "minLength": 1
  }
}
```

New：

```json
{
  "type": "object",
  "properties": {
    "detail": {
      "type": "string",
      "minLength": 5
    }
  }
}
```

这里：

```text
new detail values
⊆
old wildcard values
```

因此：

```text
COMPATIBLE
```

反过来：

Old：

```json
{
  "type": "object",
  "additionalProperties": {
    "type": "string",
    "minLength": 5
  }
}
```

New：

```json
{
  "type": "object",
  "properties": {
    "detail": {
      "type": "string",
      "minLength": 1
    }
  }
}
```

则：

```text
new detail values
⊄
old wildcard values
```

必须：

```text
BREAKING
```

不要用“新增字段一律 breaking”这种错误简化。

# 11. 推荐的新 property 处理逻辑

现有 shared property traversal 保留。

新增：

```text
new_only_properties =
new_properties.keys() - old_properties.keys()
```

对于 response direction：

## old additionalProperties == FORBID

```text
任何 new-only named property
→ BREAKING
```

错误信息应稳定、可排序、可测试。

例如：

```text
<location>.<name>: response property was added but old schema forbids additional properties
```

不要依赖 dict 物理顺序。

---

## old additionalProperties == ALLOW_ANY

```text
new-only property
→ COMPATIBLE
```

因为 old client 本来允许任意字段和值。

---

## old additionalProperties == SCHEMA

必须把：

```text
old wildcard schema
```

与：

```text
new named property schema
```

继续交给现有 direction-aware `_schema_changes()`：

```python
_schema_changes(
    old_additional_schema,
    new_property_schema,
    old_document,
    new_document,
    direction="response",
    ...
)
```

这样才能复用已经验证的：

```text
type
enum
const
constraints
recursive refs
composition
additionalProperties
```

逻辑。

不要复制一套新的 schema comparison。

这是唯一性原则的一部分：

```text
一个 compatibility semantic rule
只能有一个 authoritative implementation path。
```

# 12. existing additionalProperties wildcard comparison 必须保留

当前已有：

```text

vs
```

它负责 wildcard 空间本身的变化。


两者语义不同。

不得为了修本问题删除现有 AP comparison。
