# 2. P7.3 要解决的核心问题

P7.2 当前已经能够产生 deterministic ephemeral output。

P7.3 要正式回答四个问题：

```text
1. Identity
这个结果是谁？

2. Integrity
这个结果是否被修改、损坏或伪造？

3. Determinism
同一个 semantic calculation 是否只能对应一个 canonical result？

4. Durability
进程退出后，结果是否仍然能够被可信地验证和恢复？
```

P7.3 的成功标准不是：

```text
Parquet file exists
```

而是：

```text
Verified Dataset
+
Canonical Calculation Graph
+
Exact RESEARCH execution
        ↓
Canonical Logical Result
        ↓
Stable Result Content Identity
        ↓
Immutable Durable Commit
        ↓
Verified Reload
```

# 3. 核心 Identity 分层

这是整个 P7.3 最重要的设计。

必须严格区分以下 identity。

---

## 3.1 Calculation Semantic Identity

继续使用 P7.2 已存在的：

```text
calculation_fingerprint
```

它回答：

> What semantic calculation should be executed?

当前如果其语义是：

```text
schema_version
+
dataset_snapshot_fingerprint
+
calculation_graph_fingerprint
+
backend = RESEARCH
```

则 P7.3 不得修改其组成。

禁止向 Calculation fingerprint 加入：

```text
result values
created_at
filesystem path
Parquet configuration
compression
row_group_size
hostname
PID
worker count
Python version
PyArrow version
plugin path
temporary directory
```

P7.3 必须把当前 Calculation semantic identity 视为 frozen upstream authority。

---

## 3.2 Result Content Identity

P7.3 新增正式：

```text
result_content_fingerprint
```

它回答：

> What canonical logical result was actually produced?

Result content identity 必须基于逻辑结果，而不是物理文件。

至少应覆盖：

```text
node fingerprint
instrument identity
timestamp axis
output names
output logical types
output values
canonical ordering
```

根据当前 output contract，还应考虑：

```text
nullability
dimensions
semantic type
unit
```

如果这些是 Calculation Definition 已经正式声明的 contract，则 Result identity 可以通过 node definition / graph authority间接引用；不要不必要重复信息。

必须明确 canonical serialization。

## 3.3 Calculation Result Identity

新增：

```text
calculation_result_fingerprint
```

建议语义：

```text
HASH(
    result_schema_version,
    calculation_fingerprint,
    result_content_fingerprint
)
```

它回答：

> What immutable durable Calculation Result is this?

最终名字可以根据当前 naming convention 调整，但语义必须保持三层分离：

```text
Calculation Fingerprint
= what should be calculated

Result Content Fingerprint
= what canonical logical output was produced

Calculation Result Fingerprint
= identity of the durable result fact
```

# 4. 最重要的 Determinism Invariant

P7.3 必须正式建立：

```text
same calculation_fingerprint
→ exactly one canonical result content
```

这是核心 invariant。

---

## 4.1 Idempotent Same Result

如果 Store 已经存在：

```text
Calculation C
→ Result Content R1
```

再次提交：

```text
Calculation C
→ Result Content R1
```

必须：

```text
idempotent success
```

不得生成第二份 mutable duplicate authority。

---

## 4.2 Deterministic Result Conflict

如果 Store 已经存在：

```text
Calculation C
→ Result Content R1
```

再次提交：

```text
Calculation C
→ Result Content R2
```

并且：

```text
R1 != R2
```

必须：

```text
fail closed
```

建议稳定 domain error：

```text
DETERMINISTIC_RESULT_CONFLICT
```

实际 error naming 应遵循当前 Research Calculation error style。

绝对禁止：

```text
overwrite old result
store both and pick latest
silently replace
treat as cache miss
ignore mismatch
```

这是 P7.3 最重要的 consistency contract 之一。

---

# 5. Durable Store 的 Authority Key

重点评估 durable directory key。

优先设计为：

```text
calculation_fingerprint
```

作为一级 durable authority key。

理由：

```text
one calculation
→ exactly one canonical result
```

物理布局可以类似：

```text
<root>/
└── sha256/
    └── ab/
        └── <calculation_fingerprint>/
            ├── manifest.json
            └── data/
                ├── ...
```

Manifest 内再保存：

```text
result_content_fingerprint
calculation_result_fingerprint
```

这样：

```text
target absent
→ commit

target exists + same canonical result
→ verify + idempotent success

target exists + different canonical result
→ deterministic conflict
```

不要引入一个额外 mutable mapping：

```text
calculation → current result
```

除非当前 Repository 事实明确要求，否则优先避免 mutable index authority。


```text

│

│   ├── Instrument A
```

```text

```

必须保留 instrument identity。

不要把 instrument_id 丢到文件路径中而不进入 manifest semantic verification。



```text

timestamps canonical

```

是否需要重新读取 Dataset Snapshot 验证 instrument universe，应根据 current architecture 仔细设计。

原则：

> Durable Store 不得成为绕过 P7.2 validation 的后门。

# 14. Atomic Commit Protocol

必须采用 staged atomic commit。

建议流程：

```text
validate execution admission
        ↓
canonicalize logical result
        ↓
compute partition semantic fingerprints
        ↓
compute global result_content_fingerprint
        ↓
compute calculation_result_fingerprint
        ↓
resolve target by calculation_fingerprint
        ↓
if target exists:
    verify existing
    compare semantic result
    same → idempotent success
    different → deterministic conflict
        ↓
create .stage-<uuid>
        ↓
write partition files
        ↓
read back
        ↓
verify exact logical round-trip
        ↓
compute byte hashes
        ↓
write exact manifest
        ↓
verify whole staging root
        ↓
atomic rename(stage, target)
        ↓
if rename races with another writer:
    verify target
    same → idempotent success
    different → deterministic conflict
        ↓
remove staging remnants
```

必须保证：

```text
partial committed result
```

永远不可见。

正式 load 必须是 fail-closed verification。

```text

        ↓

        ↓

        ↓
```

# 19. Corruption vs Deterministic Conflict

必须区分两类问题。

## Corruption

已存在 durable state 自身无法通过验证，例如：

```text
missing file
byte hash mismatch
semantic hash mismatch
manifest mismatch
wrong row count
wrong schema
wrong identity
```

应报：

```text
RESULT_CORRUPT
```

或 current error model 下等价稳定 domain error。

## Deterministic Conflict

已有结果本身是完整、合法、verified 的：

```text
C → R1
```

但新的 candidate：

```text
C → R2
R1 != R2
```

这是：

```text
DETERMINISTIC_RESULT_CONFLICT
```

两者语义不同，不要混为一个 generic IO error。

# 49. Concurrency / Race Semantics

P7.3 不需要构建复杂 lock manager。

但必须正确处理最基本的 concurrent commit race：

```text
Writer A stages C/R1
Writer B stages C/R1
A rename succeeds
B rename sees target exists
B verifies target
same R1
→ idempotent success
```

如果：

```text
A = C/R1
B = C/R2
```

则：

```text
one wins
other verifies existing
→ deterministic conflict
```

不要通过：

```text
delete target and retry
```

解决 race。

```text

```

且不能进入 Result semantic fingerprint。

除非某个 implementation version 会改变 observable semantics；这种情况应通过 Calculation semantic version 解决，而不是把 runtime version 塞进 Result identity。

```text

```

第一版若固定 one `(node, instrument)` = one file，可以先保持简单。

不要提前设计任意 repartition framework。

# 52. Result Serialization Contract

Result identity 不能通过：

```text

pickle(table)
Python hash()
```

计算。

必须使用：

```text
canonical explicit serialization
+

```

遵守现有 `onlyalpha.canonical` philosophy。

Decimal / integer / string / boolean / null 等值必须精确、稳定。

timestamp 必须保持明确纳秒 integer semantic 或 current P7.2 authority。

```text
different instrument
```

# 54. Node Identity

```text

different Calculation node
→ same semantic partition
```

如果 Graph alias 仍是 presentation identity：

> P7.3 不得让 alias 进入 Result semantic identity。

# 55. Timestamp Authority

继续服从 P7.2 timestamp semantic。


```text

OBSERVATION_TIME

```

存储层不得自行 reinterpret timestamp。

timestamp values 必须 canonical、strictly increasing / unique，依据 P7.2 current contract。


Store 不得创造第二套 output schema definition。

# 58. Store Read API 的验证等级


```text

```


# 61. Commit Existing Corrupt Target

```text

+

```

```text

repair
```

应该：

```text

```

因为一旦 immutable authority 已出现但损坏，自动覆盖会销毁 forensic evidence，并掩盖存储问题。

# 70. 最终执行原则

1. 先读 current Repository。
2. 以 current HEAD 为唯一事实来源。
3. 先冻结 identity 和 durable contract，再写 Store。
4. 不修改 P7.0/P7.1/P7.2 semantic identity。
5. Durable boundary 必须 defensive validation。
6. Result identity 必须 logical，不是 physical bytes。
7. Same Calculation 只能对应一个 canonical Result。
8. Existing same Result 是幂等。
9. Existing different Result 是 determinism violation。
10. Corruption fail closed。
11. No overwrite / repair / fallback。
12. Staging + full verification + atomic publish。
13. Formal load 必须 verified。
14. 不做 Cache。
15. 不激活 Research Runtime。
16. 不实现 Job / Sweep / Factor / Research Result / Artifact / API / Web。
17. 不引入 generic immutable-store framework。
18. 完整执行当前 quality gates。
19. 最终 SHA 再进入 Final-SHA Certification。
20. 不自动开始下一阶段。

P7.3 的成功不是“多了一套 Parquet 文件”。

真正成功标准是：
