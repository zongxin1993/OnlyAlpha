# 3. 本任务真正要解决的问题

不要把问题定义成：

“coverage 不够。”

应定义成：

Research Result 已经成为 durable Research authority，但现有测试证据没有充分覆盖它应该保证的破坏性路径、严格输入契约、原子发布、确定性冲突和 referential-integrity failure semantics。

Research 主链当前语义大致为：

Dataset
  ↓
Calculation
  ↓
Job
  ↓
Factor / Target / Sweep
  ↓
Evaluation / Statistics
  ↓
Research Result
  ↓
Research Artifact
  ↓
Research Query
  ↓
Read-only API

Research Result 的职责不是重新计算 Statistics。

Research Result 的职责是：

对一个 canonical Research Result Plan 所指定的一组 verified Statistics Result authority 进行确定性、不可变、可验证的组合，并形成一个 durable Research Result authority。

因此它至少必须可靠保证：

1. 非法对象不能进入 durable authority。
2. malformed serialization 必须 fail closed。
3. corrupt authority 不能被解释成 missing。
4. Statistics logical identity mismatch 必须被拒绝。
5. Statistics Result identity mismatch 必须被拒绝。
6. cross-Dataset composition 必须被拒绝。
7. Dataset linkage mismatch 必须被拒绝。
8. content fingerprint tampering 必须被拒绝。
9. Research Result fingerprint tampering 必须被拒绝。
10. 同一 Plan 出现不同 deterministic outcome 必须 conflict。
11. 同一 deterministic Result 并发提交必须收敛为一个 authority。
12. publication failure 不得留下半完成 authority。
13. staging failure 必须清理。
14. existing authority 不能被失败写入覆盖。
15. physical representation 必须是 exact、可验证的。
16. path identity 和 manifest identity 必须一致。
17. load-time verification 不得绕过 upstream authority validation。

Coverage 是发现这些 evidence gap 的工具。

Coverage 不是最终目的。

不要立刻改测试。

| Location | Uncovered Decision | Contract Meaning | Existing Evidence | Needed Action |
|---|---|---|---|---|

例如：

`result_store.py::_read_verified`
→ manifest symlink branch

对每一个 missing branch，先分类：

A. Public correctness contract，应该测试  
B. Durable boundary defensive contract，应该测试  
C. Genuine unreachable/dead code，应该删除或解释  
D. Duplicate defensive verification，有意保留，需判断最自然的边界测试  
E. Tooling artefact，需证明后才能改 infrastructure

不得默认所有 missing branch 都必须人工触发。

# 12. Block B — Result Store Corruption Contract

Research Result Store 必须清楚区分：

MISSING
!=
CORRUPT
!=
INVALID INPUT
!=
DETERMINISTIC CONFLICT
!=
COMMIT FAILURE

不要只检查“raises”。

必须 assert exact stable error code / classification。

根据 current implementation 补齐以下有意义场景。

## 12.1 Missing authority

不存在的合法 Plan fingerprint：

→ `RESEARCH_RESULT_NOT_FOUND`

非法 fingerprint 输入：

按照 current frozen public contract 验证 exact error classification。

不要自行重新定义错误语义。

---

## 12.2 Authority physical corruption

覆盖：

- authority root symlink
- `manifest.json` symlink
- unexpected extra file
- missing manifest
- malformed JSON
- JSON top level 非 object
- unsupported/invalid manifest schema
- path Plan fingerprint 与 manifest Plan fingerprint 不一致

预期：

CORRUPT

而不是：

MISSING
REBUILD
EMPTY RESULT

---

## 12.3 Corrupt authority must never be overwritten

如果 existing target 已存在但 corrupt：

重新 commit 相同或新的 candidate 不得：

- 删除 corrupt authority
- 覆盖 corrupt authority
- silently treat as missing
- create second authority

必须 fail closed。

在测试中验证 durable bytes / physical state 没有被错误修改。

# 13. Block C — Referential Integrity

Research Result 只是 verified composition。

因此 upstream verification 是它的核心，而不是 implementation detail。

明确覆盖：

## 13.1 Statistics logical identity mismatch

Reference：

statistics_fingerprint = A

verified upstream manifest：

statistics_fingerprint = B

必须 fail closed。

---

## 13.2 Statistics Result identity mismatch

Reference：

statistics_result_fingerprint = X

verified upstream：

statistics_result_fingerprint = Y

必须 fail closed。

不要把 logical identity 和 Result identity 合并成一个测试语义。

它们是两种不同 Authority linkage。

---

## 13.3 Cross-Dataset composition

两个 Statistics Result 分别来自：

Dataset D1
Dataset D2

不得组合为同一个 Research Result。

必须 fail closed。

这是 Research Result 最重要的 semantic invariant 之一。

---

## 13.4 Manifest Dataset linkage mismatch

所有 upstream 均来自 D1，

但 Research Result manifest 声称 D2：

必须 fail closed。

---

## 13.5 Content fingerprint tampering

References 合法，但 content fingerprint 不等于 canonical recomputation：

必须 fail closed。

---

## 13.6 Result fingerprint tampering

Plan + content 正确，但 Result fingerprint 不等于 canonical recomputation：

必须 fail closed。

# 15. Block E — Atomic Publication

这是本任务最重要的 correctness area 之一。

Research Result publication 预期流程大致是：

admit candidate
   ↓
create staging directory
   ↓
write exact manifest
   ↓
read-back verified staging
   ↓
atomic rename
   ↓
verified load committed authority
   ↓
Outcome

必须证明失败是 atomic 的。

---

## 15.1 Stage verification failure

模拟或构造真正有意义的：

stage 已写入，但 read-back verification 失败。

验证：

- stable `RESEARCH_RESULT_COMMIT_FAILED`
- final target 不存在
- `.stage-*` 被清理
- 不存在 partial durable authority

---

## 15.2 Rename failure with no winning target

`os.rename(stage, target)` 失败，

且 target 并不存在。

必须：

- fail closed
- map to commit failure
- staging cleanup
- target absent

---

## 15.3 Concurrent same-result publication

构造 race-like case：

Process/actor A staging
Process/actor B 先发布完全相同 semantic Result
A rename 失败并发现 target 已存在

A 必须：

verified-load existing
→ semantic equality
→ `REUSED`

最终只有一个 authority。

---

## 15.4 Concurrent conflicting publication

同一 Plan fingerprint 下，

winning target 与 candidate 的：

- content fingerprint
或
- Result fingerprint

不一致。

必须：

`DETERMINISTIC_RESULT_CONFLICT`

不能：

- REUSED
- overwrite
- ignore
- take latest

---

## 15.5 Existing authority immutability

对 commit failure / conflict 前后比较 existing durable state。

验证：

before bytes == after bytes

或者采用 repository 当前最合适的 immutable state assertion。

不能只 assert error。

# 19. Production Code 修改规则

NO semantic production change.

只有以下情况允许修改 production code。

## A. 测试证明真实 correctness bug

- corrupt authority 被错误当成 missing
- race conflict 被错误 REUSED
- failed publication 留下 stage
- existing authority 被错误覆盖

smallest correctness patch

## B. 证明 branch 永远不可达

如果依据：

- frozen constructor invariants
- exact public API
- exact serialized parser
- type boundary

durable boundary 的 defense-in-depth 不是有意设计。

如果某 defensive path 返回了错误的 stable error code，允许最小修复。

不得借机 redesign error taxonomy。

# 20. Coverage Acceptance

不断用 targeted command 开发，不要每次都跑 full suite。

核心开发命令：

`uv run python scripts/test_suite.py research-result --coverage`

或者 current canonical equivalent。

本任务必须达到 frozen contract：

Research Result line coverage >= 95%
Research Result branch coverage >= 90%

如果自然的 correctness tests 能达到更高覆盖率，可以接受。

不要为了 100% 写低价值测试。

不要以“刚好 95.00 / 90.00”为目标。

目标是 contract completeness。

---

# 21. Verification Strategy

严格遵守：

targeted
→ affected
→ broad only when justified

不要浪费 token 和 CI 时间。

# 22. Block F — Targeted Verification

完成测试后至少执行：

1.

`uv run python scripts/test_suite.py research-result --coverage`

必须 PASS。

2.

`uv run python scripts/test_suite.py research-result`

必须 PASS。

3. Research Result architecture tests。

4. test lane/coverage contract tests。

5. 针对修改文件的 Ruff / format。

如果 production source 修改：

运行 relevant Mypy。

---

# 23. Block G — Affected Expansion

如果只修改：

tests/research/result
+
docs

则本地 Task Gate 不需要无理由运行全仓所有 lanes。

但如果修改：

`src/onlyalpha/research/result/**`

必须评估 downstream impact。

Research Result 的直接消费者至少包括：

Research Artifact

其后是：

Research Query/API

因此 production public behavior 或 Result contract 有变化时，至少考虑执行：

- research-result
- research-artifact
- research-query

如果只修内部 commit cleanup 且 public contract 不变，也仍应根据 Impact Resolver / dependency topology 判断最小充分测试。

不要仅根据“我只改了一行”判断范围。

应根据：

who imports/calls/loads this authority?

判断影响面。

# 24. Full Coverage / Core-Full 使用规则

开发过程中不要反复运行：

`core-full --coverage`

本任务虽然修的是 coverage gate，但单次修改的开发循环仍应 targeted。

只有最终主线 closure 阶段才需要 broad verification。

原因：

当前 exact HEAD 已知存在 Layered Quality regression。

因此完成 targeted closure 后，最终 resulting SHA 必须重新经过真正的 master-level gate。

# 25. Exact HEAD Layered Quality

最终提交/推送后的 exact resulting HEAD：

Layered Quality 必须最终：

completed
success

不要因为：

- ordinary research-result PASS
- local targeted coverage PASS
- dependency audit PASS

就声明 clean baseline。

必须确认最终 coverage job 真正走完整条链。

此前 Research Result coverage fail-fast 后，下游 coverage steps 可能被跳过，例如：

- Research Artifact coverage
- Research Query coverage
- Research Job coverage
- Research Sweep coverage
- Research Dataset coverage

因此新的 exact HEAD 不能只证明 Research Result 自己 PASS。

必须让整个 required coverage chain 实际执行完成。

# 36. Failure Classification

执行过程中所有失败必须分类。

## Type A — 本任务修改引入的 Regression

例如：

新增 test 导致 unrelated production failure，
production correctness patch 破坏 Artifact。

必须修复。

---

## Type B — Current Known Research Result Coverage Failure

这是本任务核心 scope。

必须关闭。

---

## Type C — Newly Exposed Research Result Correctness Defect

新测试证明现有 Result authority 有真实 bug。

属于本任务 scope。

做最小 correctness fix。

---

## Type D — Pre-existing Unrelated Failure

与本任务 source/test/docs 没有合理影响关系的 pre-existing failure：

记录：

PRE-EXISTING FAILURE

不要无边界扩张任务。

但是：

如果它导致 exact HEAD 无法成为 clean baseline，最终 verdict 必须诚实说明 blocker。

不能假装 accepted。

---

## Type E — Tooling / Environment Failure

例如：

network unavailable
artifact unavailable
scanner infrastructure outage

必须区分：

TEST FAILED
和
TEST COULD NOT RUN

不要把环境失败写成 PASS。

P7 CERTIFIED

P7 COMPLETE

P8 READY

最终 verdict：

LOCAL VERIFIED — REMOTE QUALITY GATE PENDING

不要使用 ACCEPTED — CLEAN DEVELOPMENT BASELINE RESTORED。

REJECTED — RESEARCH RESULT QUALITY CONTRACT NOT CLOSED

REJECTED — QUALITY CONTRACT WEAKENED

---

如果出现新的 architecture regression：

REJECTED — ARCHITECTURE REGRESSION
