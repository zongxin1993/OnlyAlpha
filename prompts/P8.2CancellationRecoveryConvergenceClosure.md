============================================================
0. 任务定位
============================================================

这是 P8.2 的 correctness closure。

它不是新的产品能力，
不是 P8.3，
也不是重新设计 Scheduler / Worker / Attempt / Lease。

本任务只解决一个已经识别出的根本一致性问题：

Cancellation
+
Immutable Semantic Completion
+
Worker Crash
+
Lease Expiry

交叉发生时，

ResearchRun 的最终 outcome
不能因为 Worker 是否多存活了几毫秒而发生变化。

当前 P8.2 已经建立：

ResearchRun
→ Attempt
→ Lease
→ Worker
→ OnlyEngine
→ OnlyResearchRuntime
→ immutable Result / Artifact
→ fenced operational finalization

并且已经分别支持：

A.

CANCEL_REQUESTED
+
Result/Artifact complete
+
Worker still alive
→ COMPLETED

以及：

B.

Result/Artifact complete
+
Worker crash
+
lease expiry
+
recovery
→ COMPLETED

但是需要重新验证 current HEAD 是否仍存在以下交叉缺口：

Result + Artifact 已经 durable committed
        ↓
用户请求 Cancel
        ↓
Run = CANCEL_REQUESTED
        ↓
Worker 在 operational finalization 前 crash
        ↓
Attempt lease expires
        ↓
当前 recovery 直接：
Run → CANCELLED

如果这仍然是 current implementation：

那么系统存在：

same durable semantic facts
+
different process survival timing
→ different terminal Run outcome

这是 correctness bug。

本任务必须从第一性原理消除这个问题。

============================================================
1. 第一原则
============================================================

本任务必须冻结下面这个核心不变量：

ResearchRun terminal outcome
must be determined by authoritative durable facts,

not by whether the Worker survived long enough
to project those facts into PostgreSQL.

也就是说：

如果 exact Research Result
和 exact Artifact

已经作为 immutable semantic authorities
durable committed
并且 verified，

则：

Worker crash
不得把本应 COMPLETED 的 Research
改变成 CANCELLED。

同时：

Cancel != Rollback

Cancellation 不能删除、
修改、
回滚已经提交的 immutable semantic facts。

但另一方面：

Cancellation 也不能因为存在部分 semantic facts
就强制继续完成缺失的 Research 工作。

因此必须严格区分：

SEMANTICALLY COMPLETE

和：

PARTIALLY COMMITTED

13. Stale Worker Semantic Writes
============================================================

不要假设：

lease expiry
→ old Worker立刻停止。

P8.2 明确不以 Worker cooperation
作为 correctness premise。

因此 recovery设计必须考虑：

旧 Worker可能仍然在做 deterministic semantic computation。

Operationally：

stale Worker永远不能：

Run → COMPLETED
Run → FAILED
Run → CANCELLED

Semantic immutable stores如果接受：

same identity
same content

这是 deterministic duplicate work。

如果发现 conflict：

existing semantic authority必须 fail closed。

不能为了 cancellation recovery
删除 stale Worker写出的 immutable facts。

43. 核心 Acceptance Matrix
============================================================

至少通过：

CASE 1 — Normal cancellation

RUNNING
→ CANCEL_REQUESTED
→ before semantic completion
→ active Worker cooperatively stops
→ CANCELLED

CASE 2 — Normal completion race

Result + Artifact committed
→ CANCEL_REQUESTED
→ active Worker still owns lease
→ COMPLETED

CASE 3 — Crash convergence

Result + Artifact committed
→ CANCEL_REQUESTED
→ Worker crashes before operational finalize
→ lease expiry
→ reconciliation
→ COMPLETED

CASE 4 — No completion

CANCEL_REQUESTED
→ Worker crashes
→ lease expiry
→ complete semantic facts absent
→ CANCELLED

CASE 5 — Partial Result

Research Result exists
Artifact absent
→ CANCEL_REQUESTED
→ crash
→ recovery
→ CANCELLED
→ Result preserved

CASE 6 — Corrupt completion

Expected Result/Artifact discovered
but verified-load fails
→ FAIL CLOSED
→ must not silently CANCEL

CASE 7 — Last attempt

Attempt number == max_attempts
Result + Artifact already committed
Cancel requested
Worker crash
→ COMPLETED

CASE 8 — Stale Worker

old Attempt expired
reconciliation/terminal outcome committed
old Worker resumes
→ cannot mutate operational outcome

CASE 9 — Concurrent reconciliation

two actors race
→ one terminal transition
→ no rewrite

CASE 10 — Existing non-cancel crash recovery

Artifact committed
Worker crash
no cancellation
→ existing P8.2 recovery still COMPLETED
