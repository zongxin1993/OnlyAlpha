# 1. 第一性原理

P8.4.0 要解决的问题不是：

```text
“怎么执行一个 Research”
```

这个问题 P7/P8.0 已经解决。

当前已有：

```text
OnlyResearchSpecification
→ OnlyResearchSpecificationResolver
→ OnlyResearchWorkloadPlan
→ OnlyResearchRuntime
```

P8.4.0 要解决的是：

```text
“研究员想研究什么”
        ↓
“OnlyAlpha 精确执行什么”
```

因此必须建立一个位于现有 Specification 之上的正式 authoring Domain：

```text
Research Definition
```

三层职责必须严格区分：

```text
Research Definition
→ 用户研究意图

Research Specification
→ exact execution contract

Research Workload
→ Runtime composition contract
```

禁止把三者混成一个大对象。

# 6. Calculation Instance

用户不是在编辑内部 Graph node。

用户声明的是：

```text
Registered Calculation Definition
        ↓
Calculation Instance
```

概念字段：

```text
instance_key

exact calculation type reference

parameter bindings

allowed input configuration
    only if existing registered Definition exposes such authoring input

published outputs

primary output
    UX/default only
```

例如：

```text
instance_key = "rsi_fast"

type_reference =
    INDICATOR
    onlyalpha.indicator.rsi
    semantic_version = ...
```

---

## 6.1 instance_key

`instance_key` 是 Definition-local logical identity。

例如：

```text
rsi_fast
rsi_slow
momentum
liquidity
```

必须：

```text
stable
explicit
unique within Definition
```

禁止使用 display name 作为 semantic identity。

```text
display_name != instance_key
```

---

# 7. Parameter Binding

正式参数只能有两种：

```text
Fixed(value)

Sweep(values)
```

---

## 7.1 Fixed

必须有：

```text
exactly one normalized value
```

参数 normalization 必须调用现有 Calculation parameter schema。

不要自行复制参数规则。

---

## 7.2 Sweep

必须：

```text
finite
explicit
canonical
```

建议 V1：

```text
Sweep
→ >= 2 distinct normalized values
```

例如：

```text
Sweep([7, 14, 21])
```

合法。

```text
Sweep([14])
```

拒绝，要求改为：

```text
Fixed(14)
```

---

## 7.3 Sweep ordering 不影响 identity

例如：

```text
[7,14,21]
```

与：

```text
[21,7,14]
```

必须 canonicalize 成相同 semantic representation。

重复值：

```text
[7,14,14,21]
```

不要静默产生重复 Candidate。

应：

```text
normalize
+
explicit duplicate handling
```

优先 fail closed。

---

## 7.4 不实现

P8.4.0 禁止引入：

```text
zip sweep
dependent sweep
conditional sweep
random search
Bayesian optimization
adaptive optimization
optimizer framework
```

V1 只有：

```text
finite Cartesian Product
```

# 10. Global Candidate Space

这是 P8.4.0 的核心任务。

当前 P8.0 Specification 的 Sweep 主要是 Calculation-local。

P8.4 产品语义需要：

```text
Definition-level Global Candidate Space
```

例如：

```text
RSI.period
=
[7,14,21]

Momentum.window
=
[10,20]
```

必须形成：

```text
3 × 2 = 6
```

个 Research Candidates。

Candidate 是：

```text
one exact assignment of all global swept dimensions
```

例如：

```text
C1:
RSI.period = 7
Momentum.window = 10

C2:
RSI.period = 7
Momentum.window = 20

...
```

# 11. Candidate Graph

优先实现方向：

> 将所有参与 global sweep 的非 Target Decision Calculations 编译到一个组合的 Candidate Decision/Calculation Graph Template 中。

例如：

```text
Candidate Decision Graph
├── RSI
├── Momentum
├── Eligibility
├── Entry Signal
└── Exit Signal
```

Sweep dimensions：

```text
RSI.period
Momentum.window
```

全部属于同一个 graph template。

这样现有：

```text
Sweep Planner
+
Graph Template Materializer
```

可以自然产生：

```text
Candidate-relative exact graph
```

禁止重新实现第二套：

```text
Candidate Join Engine
Candidate Signal Resolver
```

如果现有 Sweep/Graph infrastructure 无法直接完成，应做最小必要扩展，而不是另建体系。

---

# 12. Candidate Identity

Candidate identity 不能只是：

```text
period=14
window=20
```

因为相同参数出现在不同 Research context 中不一定是同一个 exact Candidate。

Candidate identity 至少必须考虑：

```text
candidate schema/version
canonical Research/Definition context
canonical sweep assignment
exact resolved Dataset context
    if current identity architecture requires it
```

最终 exact fingerprint formula 请根据现有 identity conventions 实现。

必须证明：

```text
same semantic Definition + same authorities
→ same Candidate identity
```

且：

```text
different exact Research context
→ cannot accidentally collapse
```

不要将 display ordering 纳入 identity。

---

# 13. Eligibility / Entry / Exit Domain Semantics

三者共享 Boolean expression mechanics。

但必须保持三个不同 Domain role。

```text
Eligibility
→ observation/instrument 是否符合研究/决策资格

Entry Signal
→ 当前 observation Entry condition 是否成立

Exit Signal
→ 当前 observation Exit condition 是否成立
```

绝对禁止自动：

```text
effective_entry =
eligibility AND entry
```

或者：

```text
effective_exit =
eligibility AND exit
```

这会丢失独立事实并偷偷加入 Trading Policy。

---

# 14. Research Signal != Order

必须明确保持：

```text
ENTRY_SIGNAL
!=
BUY Order

EXIT_SIGNAL
!=
SELL Order
```

Research 中：

```text
ENTRY_SIGNAL[t] = true
```

只表示：

```text
Entry condition true at t
```

Research 不拥有：

```text
Position
Account
Order
Fill
Broker
Risk Reservation
Capital allocation
```

不要将这些类型引入 P8.4.0。

# 15. Typed Boolean AST

第一版正式 grammar：

```text
AND
OR
NOT
Comparison
```

Comparison：

```text
==
!=
<
<=
>
>=
```

Operand：

```text
DatasetFieldRef

Published ResearchVariableRef

TypedLiteral
```

---

## 15.1 Type Admission

复用现有：

```text
Calculation Output Definition
Dataset Schema
OnlyDataType
```

等正式类型。

不要创建第二套 primitive type system。

建议保守 V1：

```text
DECIMAL
INTEGER
→ == != < <= > >=

STRING
→ == !=

BOOLEAN
→ == !=
```

根据现有 OnlyDataType 的真实定义调整。

禁止：

```text
implicit arbitrary numeric/string conversion
```

---

## 15.2 Typed Literal

Literal 必须进入 canonical normalized form。

例如：

```text
RSI.value < 30
```

如果：

```text
RSI.value = DECIMAL
```

那么 `30` 最终必须归一化到正式 Decimal representation。

不要让：

```text
30
30.0
Decimal("30")
```

在 semantic identity 中产生不必要差异。

---

# 16. Boolean AST Canonicalization

需要 deterministic canonicalization。

至少处理：

```text
AND
OR
```

的：

```text
associativity
commutativity
```

例如：

```text
A AND B

B AND A
```

应得到相同 canonical form。

同理：

```text
(A AND B) AND C

A AND (B AND C)
```

应该结构归一化。

推荐：

```text
flatten AND/OR
canonicalize children
sort children by canonical/fingerprint order
```

但不要做完整 symbolic optimizer。

本阶段不要实现：

```text
A AND true → A
A OR false → A
NOT NOT A → A
global common subexpression elimination
SAT simplification
```

结构 canonicalization 即可。

这是本任务最关键部分之一。

禁止：

```text

Python eval

string DSL interpreter
```

```text

        ↓
```

# 18. Example Lowering

Definition：

```text
Entry:

RSI.value < 30
AND
Momentum.score > 0
```

概念 Graph：

```text

                             │
                             AND
                             │
```

```text
=
(RSI[t] < 30)
AND
(Momentum.score[t] > 0)
```

```text

```

而不是 side-effect callback。

# 27. Candidate Cardinality Guard

Global Cartesian Product 必须有明确上限。

不要让：

```text
100 × 100 × 100 × ...
```

到执行阶段才爆炸。

需要：

```text
resolve-time admission
```

并产生明确错误。

优先：

```text
fail before graph materialization / runtime execution
```

具体 limit 如果当前工程已有统一 resource/admission convention，则复用。

若没有，不要随意设特别大的 magic number。

可以定义一个明确、可配置、测试覆盖的 V1 bounded limit。

```text
calculations[momentum].parameters.window

signals.entry.operands[1]

statistics[0]
```

不要只抛：

```text

```

如果现有 OnlyAlpha error hierarchy 已经有统一 pattern，应遵守当前 pattern。

不应该依赖：

```text

Builder section order
Sweep value ordering
display name
UI metadata
Graphviz layout
```

必须：

```text
canonical representation
→ stable fingerprint
```

但注意：

```text
Definition fingerprint
!=
Specification fingerprint
!=
Dataset fingerprint
!=
Candidate fingerprint
```

不要把所有 identity 合成一个万能 hash。

# 32. Cross-Runtime Semantic Boundary

P8.4.0 不实现 Trading Decision Runtime。

但是设计必须支持未来：

```text
Same Decision semantics
        │
        ├── RESEARCH
        │     batch/vectorized
        │
        ├── BACKTEST
        │     historical incremental/event-driven
        │
        ├── SIM
        │     realtime incremental/event-driven
        │
        └── LIVE
              realtime incremental/event-driven
```

必须保持思想：

```text
Execution Strategy can differ.

Semantic Logic cannot differ.
```

不要在 Definition 中编码：

```text
if runtime == RESEARCH ...
if runtime == BACKTEST ...
```

# 33. 不要把 Research Definition 直接命名为 StrategyDefinition


# 41. Predicate Implementation Decision Checklist

在决定是否新增：

```text
OnlyCalculationKind.PREDICATE
```

前，必须回答：

1. 当前 Calculation Definition 是否允许 BOOLEAN output？
2. 当前 Graph 是否允许 BOOLEAN node output 连接到 BOOLEAN input？
3. 当前 Research Executor 是否已经支持 Boolean Arrow Array？
4. 当前 execution shape 是否对 Indicator/Factor/Target 写死？
5. 当前 Registry 是否要求 kind-specific semantic metadata？
6. 当前 Result identity 是否能保存该节点语义？
7. 当前 Graph Template 是否能序列化这些 internal primitives？
8. role-bearing terminal 是否必须成为 distinct Calculation definition？
9. 新 kind 是否会无意暴露到 public authoring Catalog？
10. 是否能保证它只作为 internal Research compiler primitive？

然后：

```text
选择最小、最真实、最不破坏现有语义的方案。
```

如果新增 `PREDICATE`：

必须写清楚为什么现有三个 kind 无法真实表达。
