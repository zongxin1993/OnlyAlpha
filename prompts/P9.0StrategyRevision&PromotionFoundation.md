# 1. Mission

Implement P9.0 so that OnlyAlpha has **exactly one authoritative Strategy identity and exactly one Strategy execution form**.

The problem is not merely “strategy versioning”.

The real problem is to eliminate the possibility that:

```text
Research semantics
        ↓
Candidate
        ↓
someone rewrites equivalent-looking Python Strategy logic
        ↓
Backtest / SIM / LIVE execute another semantic authority
```

P9.0 must establish:

```text
Research
   ↓
Candidate
   ↓
Explicit Freeze
   ↓
Immutable Strategy Revision
   ↓
strategy_fingerprint
   ↓
Authoritative Strategy Resolver
   ↓
Exact Calculation TRADING execution
   ↓
StrategyDecision
   ↓
Backtest / SIM / LIVE downstream components
```

After P9.0:

- Candidate is **not executable**.
- arbitrary Python Strategy code is **not a strategy authority**.
- `strategy_path` / `config_path` dynamic strategy loading is **not a valid production strategy execution path**.
- Backtest, SIM and LIVE do **not** define separate strategy semantics.
- `strategy_fingerprint` is the **single authoritative Strategy identity**.

# 2. Non-negotiable architectural invariants

These are permanent constraints for this task.

## 2.1 Uniqueness

There must be one and only one Strategy semantic/executable identity:

```text
strategy_fingerprint
```

If two frozen strategies have the same `strategy_fingerprint`, OnlyAlpha must consider them the **same Strategy**.

Do not introduce any second authoritative identity such as:

```text
strategy_revision_uuid
strategy_version_id
runtime_strategy_id
backtest_strategy_fingerprint
sim_strategy_fingerprint
live_strategy_fingerprint
```

A catalog/display/family identifier may exist for UI/query purposes, but it must never participate in Runtime identity.

---

## 2.2 Determinism

For the same:

```text
Strategy fingerprint
+
same admitted market observation history/state
```

OnlyAlpha must produce the same:

```text
ELIGIBILITY
ENTRY
EXIT
```

Runtime type must not alter strategy decision semantics.

---

## 2.3 Only one Strategy execution form

P9.0 final acceptance must not leave two executable strategy systems.

The old path:

```text
strategy_path
config_path
dynamic import
OnlyStrategy subclass
custom on_bar decision logic
```

must no longer be a valid strategy execution authority.

If `OnlyStrategy` lifecycle abstractions are still temporarily useful inside the Trading Kernel, there may be one internal revision-backed adapter, but users/runtime configuration must not be able to supply arbitrary Strategy subclasses.

---

## 2.4 Runtime != Strategy

Backtest / SIM / LIVE differ in execution reality, not in decision semantics.

```text
Strategy Revision
      ↓
Authoritative Resolver
      ↓
Calculation TRADING backend
      ↓
StrategyDecision
      ↓
Portfolio / Risk / Execution
```

Do not create:

```text
BacktestStrategy
SimStrategy
LiveStrategy
```

as independent semantic implementations.

---

## 2.5 Research provenance must not contaminate Strategy identity

The following do not belong in `strategy_fingerprint`:

```text
Research Run ID
Candidate provenance
Scientific Artifact identity
Dataset Snapshot
Dataset time range
Research statistics
PnL
Sharpe
drawdown
trade records
signal time series
capital
account
Portfolio
Risk
Broker
Fee
Execution
Runtime
deployment
created_at
created_by
comment
display name
```

A Strategy Revision answers:

> What exact executable strategy is this?

Provenance answers:

> Where did this strategy come from and why was it admitted?

These must remain separate domains.

---

## 2.6 Freeze is also Trading Admission

Freeze is not serialization.

Freeze is the unique legal:

```text
Research Candidate
→ executable Strategy
```

boundary.

Freeze must fail closed unless the candidate is provably executable by the Trading Calculation backend.

A Research candidate may be researchable but not tradeable.

---

## 2.7 Market input semantics are part of Strategy identity

Different bar/input semantics can produce different signals and therefore define different strategies.

P9.0 must freeze exact market-input semantics required by the Strategy.

At minimum for BAR V1:

```text
data kind
bar step
aggregation
price type
aggregation source
adjustment semantics
observation admission semantics
```

V1 should use:

```text
FINAL_ONLY / CLOSED_BAR_ONLY
```

for Strategy bar admission.

Do not include Dataset Snapshot or time range.

---

## 2.8 Strict implementation identity

Calculation semantic identity alone is not enough.

A Strategy Revision must bind the exact admitted:

```text
Research implementation identity
Trading implementation identity
```

for every strategy-relevant Calculation.

If implementation identity changes, the Strategy fingerprint changes.

Even if a developer claims “this is only a refactor”, OnlyAlpha must require a new frozen Strategy identity.

Prefer false-positive identity churn over a false-negative where behavior changed but Strategy identity did not.

---

## 2.9 Definition != implementation != evidence

Keep these separate:

```text
Calculation semantic definition
Calculation implementation identity
Equivalence/admission evidence
```

Do not pollute Calculation semantic fingerprint with implementation details.

Do not put CI/test evidence into Strategy fingerprint.

---

## 2.10 Database != semantic authority

Immutable Strategy Revision content must be owned by an immutable semantic store.

PostgreSQL may own:

```text
catalog metadata
query indexes
freeze provenance index
promotion records
deployment namespace binding
```

PostgreSQL must not silently become a second mutable copy of Strategy semantic truth.

---

## 2.11 Shared deployment semantic namespace

Use one OnlyAlpha semantic deployment namespace identity.

Conceptually:

```text
semantic namespace
├── research
├── calculation
└── strategy
```

Reuse the P8 deployment-coherence philosophy.

Do not create unrelated independent Research/Strategy namespace identities that can drift from one another.

Do not over-generalize all domain stores into one giant generic store merely for abstraction.

# 9. P9.0.3 — Unique Candidate Freeze Authority

## Goal

Create the only legal Candidate → Strategy boundary.

---

## Freeze request must be narrow

The request must reference authoritative Research evidence.

Do **not** allow caller-supplied Strategy semantics.

A request should conceptually contain only enough to locate the exact candidate, e.g.:

```text
research result / run identity
candidate_fingerprint
optional catalog metadata
optional actor/comment
```

Do not allow request fields such as:

```text
graph JSON
Strategy parameters
Universe JSON
output bindings
implementation identities
```

The Freeze service must reconstruct all Strategy semantics from authoritative Research/Calculation data.

---

## Authoritative Freeze flow

Implement the equivalent of:

```text
1. load_verified Research Result
2. verify upstream Calculation Results
3. locate exact Candidate
4. recompute Candidate fingerprint
5. resolve exact Calculation Graph
6. extract strategy-relevant decision semantics
7. exclude Targets/Statistics/evaluation-only semantics
8. derive exact Universe
9. derive exact Market Input Contract
10. verify signal/output roles
11. resolve Research implementation identities
12. resolve Trading implementation identities
13. execute Trading Admission
14. construct immutable Strategy Revision
15. compute strategy_fingerprint
16. commit Strategy to immutable Store
17. append Freeze provenance record
18. return canonical strategy_fingerprint
```

Do not trust the candidate fingerprint supplied by the caller without recomputation.

---

## Freeze provenance

Define a separate append-only provenance record, conceptually:

```text
OnlyStrategyFreezeRecord

schema_version
candidate_fingerprint
research_result_fingerprint
strategy_fingerprint
admission_evidence_reference/fingerprint
actor
created_at
record_fingerprint
```

Research provenance belongs here, not inside Strategy identity.

---

## Idempotency

Required behavior:

```text
C1 → S1
C1 → S1
```

must not create a second Strategy or duplicate identical provenance relation.

Return a deterministic `REUSED`-style outcome.

But:

```text
C1 → S1
C2 → S1
```

must store only one Strategy `S1` while preserving both provenance relations.

# 11. P9.0.5 — Unique Strategy Execution Path, StrategyDecision and Legacy Removal

## Goal

Make the frozen Strategy Revision the only executable Strategy form.

This is a hard P9.0 acceptance gate.

---

## Strategy Execution Resolver

Create one authoritative resolver:

```text
strategy_fingerprint
        ↓
StrategyStore.load_verified()
        ↓
StrategyRevision
        ↓
verify exact Calculation identities
        ↓
verify exact implementation fingerprints
        ↓
resolve TRADING implementations
        ↓
immutable Strategy Execution Plan
```

The Execution Plan is a deterministic projection of the Strategy Revision.

It is **not a second Strategy identity**.

Do not introduce an authoritative `execution_plan_fingerprint` that Runtime starts using instead of `strategy_fingerprint`.

The plan must retain and expose the originating `strategy_fingerprint`.

---

## StrategyDecision

Define one provider/runtime-neutral Strategy output contract.

Conceptually:

```text
OnlyStrategyDecision

schema_version
strategy_fingerprint
instrument_id
observation_key
observation_fingerprint
decision_time
eligibility
entry
exit
```

Do not include:

```text
order side
order quantity
order price
broker
account
position size
capital allocation
execution algorithm
```

Strategy ends at signal semantics.

---

## Observation identity

For P9.0 BAR V1 distinguish:

### ObservationKey

Which logical observation position is this?

Conceptually includes:

```text
instrument
bar specification
bar close/end timestamp
market-input semantics
```

### ObservationFingerprint

What exact finalized market data was observed at that logical position?

Conceptually hash canonical exact BAR content.

A corrected bar may therefore have:

```text
same ObservationKey
different ObservationFingerprint
```

Do not include transport facts such as:

```text
WebSocket connection id
provider receive timestamp
transport sequence
network session id
```

in Strategy semantic observation identity.

---

## FINAL bar only

P9.0 Strategy BAR input must admit only FINAL/CLOSED bars.

Do not implement partial-bar rollback/re-evaluation in P9.0.

If intrabar semantics are added later, they must be explicit new Market Input semantics and therefore yield a different Strategy identity.

---

## Migrate Runtime/Cluster composition

Current dynamic configuration must be replaced.

Target configuration conceptually becomes:

```yaml
strategy:
  fingerprint: "<sha256>"
```

Runtime/Cluster composition must resolve Strategy through the authoritative Strategy Resolver.

Keep:

```text
cluster id
account
capital
risk profile
broker
runtime profiles
```

outside Strategy identity.

---

## Remove legacy strategy authority

At P9.0 final acceptance, the following must not remain a valid execution path:

```text
OnlyStrategyImportConfig.strategy_path
OnlyStrategyImportConfig.config_path
OnlyStrategyCreateRequest
dynamic strategy import
arbitrary user OnlyStrategy subclass execution
```

If an old config still supplies legacy strategy paths, fail explicitly with a stable error such as:

```text
LEGACY_STRATEGY_CONFIGURATION_UNSUPPORTED
```

Do not silently fallback.

Do not automatically translate arbitrary Python Strategy code to Strategy Revision.

Arbitrary Python code cannot be proven equivalent to an exact Decision Graph.

---

## `OnlyStrategy` lifecycle interface

Do not rewrite the entire Trading Kernel merely for naming purity.

If the kernel still needs the lifecycle interface, retain one internal revision-backed adapter, conceptually:

```text
OnlyRevisionStrategyAdapter
```

It must contain no Strategy rule authoring.

Its responsibility is only:

```text
Kernel event
→ admitted market observation
→ Execution Plan
→ StrategyDecision
```

No custom per-strategy `if ...: buy()` logic is allowed.
