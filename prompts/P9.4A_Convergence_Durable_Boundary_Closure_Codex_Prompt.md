# 5. Required Behavior A — Durable Canonical Runtime Intent Before External Dispatch

## 5.1 Root Cause

Current `OnlyOrderService.submit()` creates canonical Order and reservation state before entering the Broker execution path, but the complete local causal/economic intent is not mechanically proven durable before the external side-effect boundary.

The existing `OnlyDurableBrokerCommandEvidenceStore` is correct for Broker command knowledge, but it is explicitly not the canonical Order authority.

Do not turn the Broker command journal into a shadow Order store.

## 5.2 Required Invariant

Before any real Broker side effect may occur:

```text
Complete canonical local Order Intent
+ required causal references
+ required local reservation/economic state
MUST already be recoverable.
```

Required failure rule:

```text
Runtime intent durability failure
→ external dispatch count MUST remain 0
```

## 5.3 Preferred Architecture

Reuse the existing operation-neutral Runtime transaction foundation.

Current Runtime transaction infrastructure already supports:

- stable transaction identity;
- authority hash;
- payload hash;
- preconditions;
- ordered projections;
- durable commit;
- projection-ready state;
- recovery;
- outbox.

Prefer extending it with a new universal operation such as:

```text
OnlyRuntimeOperationKind.ORDER_INTENT
```

and a narrowly scoped planner, for example:

```text
OnlyOrderIntentRuntimeTransactionPlanner
```

or an equivalent name consistent with current project conventions.

Do not create a second durable Order-intent database or JSONL journal unless repository evidence proves the current Runtime transaction system cannot represent this universal concept.

## 5.4 ORDER_INTENT Semantic Content

A durable Order Intent must preserve enough canonical information to reconstruct and explain the Order after crash/restart.

At minimum, where already present in the existing domain:

```text
RuntimeId
AccountId
ClusterId
OrderRequestId
OrderId
ClientOrderId
InstrumentId
side
offset
order type
time in force
quantity
price
Strategy / causal reference
Risk/policy binding or durable reference
fee binding
funding-plan identity/fingerprint
required reservation identities/state
```

Do not duplicate mutable provider-specific data into Core.

## 5.5 Projections

Use existing Runtime projection vocabulary where correct.

Likely projections may include:

```text
ORDER
ACCOUNT_CASH_RESERVATION
STRATEGY_CASH_RESERVATION
POSITION_RESERVATION
MARGIN_RESERVATION
RISK_RESERVATION
RISK
```

Only include projections that are actually authoritative and required by the current Order creation path.

Do not invent duplicate projections solely to satisfy tests.

## 5.6 Dispatch Barrier

The correct order must be:

```text
validate/risk
→ allocate stable provisional identity
→ prepare ORDER_INTENT transaction
→ commit
→ apply/projection-ready
→ only then call Broker execution port
```

The hard dispatch condition should be equivalent to:

```text
COMMITTED_AND_PROJECTED
or
ALREADY_READY
```

If commit succeeds but projection is not ready:

```text
external dispatch MUST NOT occur
```

The Runtime must fail closed and rely on normal transaction recovery.

## 5.7 Identity

The intent operation identity must be deterministic and idempotent.

Prefer using stable existing request identity such as `OrderRequestId` plus Runtime/account/cluster scope rather than wall-clock/random identity.

Required behavior:

```text
same semantic request identity
+ same payload
→ same intent / idempotent

same semantic request identity
+ different payload
→ conflict / fail closed
```

A consumed sequence number may be burned after failed commit if necessary; sequence continuity is not more important than correctness.

## 5.8 Broker Command Evidence Link

Broker command evidence should reference the authoritative Runtime intent rather than copying all Runtime business state.

Prefer adding stable references such as:

```text
runtime_intent_transaction_id
runtime_intent_authority_hash
```

or an equivalent existing durable reference.

Do not move Strategy/Risk/Reservation authority into the Broker command journal.

# 6. Required Behavior B — Semantic Fact Identity Must Be Independent of Observation Provenance

## 6.1 Root Cause

Current execution identity implementations still mix business fact identity with observation-channel metadata.

This applies to:

- Accepted
- Fill
- Terminal

Current code demonstrates that:
- Fill identity correctly prefers `VenueTradeId`, but payload fingerprint still includes observation-derived data such as `external_event_id`, `external_sequence`, `source_sequence`, `ts_init`, and metadata.
- Accepted identity currently includes `update_id` and fingerprints the entire update.
- Terminal identity currently includes `update_id` and fingerprints the entire update.

As a result, the same Venue fact observed through Stream and REST can be classified as a conflict instead of a duplicate.

## 6.2 Required Principle

Separate:

```text
Semantic Fact Identity
Semantic Fact Payload
Observation Identity
Observation Provenance
```

The following observation properties must not define semantic fact identity unless they are explicitly proven to be provider-authoritative semantic attributes:

```text
update_id
source_sequence
ts_init / receive time
REST vs Stream channel
reconciliation causation marker
local receive ordering
quality flags
transport-specific event identity
```

They must remain available for audit/traceability.

## 6.3 Accepted Identity v2

Accepted must represent the semantic fact:

```text
this canonical OnlyAlpha Order
is bound to this Venue Order
and was accepted by the Venue
```

Prefer identity based on canonical scope such as:

```text
runtime_id
gateway_id
account_id
order_id
venue_order_id
semantic type = ACCEPTED
```

Do not use `update_id` as the primary semantic identity.

Required behavior:

```text
Stream Accepted(O1,V1)
REST Accepted(O1,V1)
→ same semantic identity
→ same semantic fingerprint
→ DUPLICATE
```

Conflicting Venue binding must fail closed:

```text
O1 -> V1
then
O1 -> V2
→ conflict
```

## 6.4 Fill Identity v2 / Semantic Fingerprint

Retain the current good rule:

```text
VenueTradeId
```

has priority as canonical Fill identity when present.

Refactor the semantic payload fingerprint so it only contains semantic execution properties.

Candidate semantic payload:

```text
runtime/gateway/account/order scope
venue_order_id
venue_trade_id
canonical trade_id
price
quantity
authoritative trade-event time
liquidity side if it is semantic
other canonical execution attributes
```

Exclude observation provenance such as:

```text
source_sequence
ts_init
REST/stream source
reconciliation quality flag
transport-only event id
receive metadata
```

If the same `VenueTradeId` has a different price/quantity or another true semantic field:

```text
CONFLICT
```

must remain mandatory.

## 6.5 Terminal Identity v2

Terminal identity must represent the semantic terminal transition/state, not the transport update.

Prefer identity based on:

```text
runtime_id
gateway_id
account_id
order_id
venue_order_id
terminal_status
```

Terminal semantic payload may include:

```text
terminal_status
canonical reason
venue_order_id
```

Only include timestamps if they are guaranteed canonical Venue semantic time across all supported observations.

Required behavior:

```text
Stream CANCELLED(O1,V1)
REST CANCELLED(O1,V1)
→ DUPLICATE
```

not a second terminal fact.

## 6.6 Observation Provenance

Do not delete observation evidence.

The system must still be able to answer:

```text
where was this fact observed?
when was it received?
from Stream or REST?
what provider event/update id was received?
what quality flags were present?
```

But these belong to observation/evidence, not business semantic identity.

## 6.7 ExecutionProcessor Ordering

The processing model should converge toward:

```text
validate observation envelope
→ derive semantic authority identity/fingerprint
→ durable semantic lookup
→ same identity + same semantic payload => DUPLICATE
→ same identity + different semantic payload => CONFLICT
→ new semantic fact => durable Runtime transaction
→ projections
→ preserve observation evidence
```

`update_id` dedup may remain as an ingress optimization but must not be the only semantic dedup authority.

# 8. Required Behavior C — Reconciliation Must Support Zero-Delta Verified Convergence

## 8.1 Root Cause

Current reconciliation assumes successful resolution requires discovered Broker facts and application receipts.

Current pattern:

```text
discover_order()
→ no updates
→ return
```

but `acknowledge_unknown()` requires pending facts.

This makes the following valid scenario impossible to close:

```text
POST response lost
→ command UNKNOWN
→ User Data Stream already moved Local Order to ACCEPTED
→ REST reconciliation confirms Local == Venue
→ zero missing facts
→ UNKNOWN remains forever
```

## 8.2 First-Principles Rule

Reconciliation is not “a mechanism that must mutate Local state”.

Reconciliation is:

```text
a proof that Local state and external Authority have a determined relationship
```

Therefore the following are all valid outcomes:

```text
missing facts discovered
→ apply
→ verify
→ resolved

zero missing facts
→ verify
→ resolved

evidence insufficient / conflict
→ remain unresolved
```

## 8.3 New Provider-Neutral Reconciliation Result

`OnlyBrokerVenueDiscoveryPort.discover_order()` should no longer be semantically limited to returning only:

```text
tuple[OnlyBrokerInboundUpdate, ...]
```

Introduce the smallest provider-neutral result that can distinguish at least:

```text
PRESENT
ABSENT_PROVEN
INCONCLUSIVE
```

and carry:

```text
order_id
operation
authoritative snapshot/reference when available
discovered_facts
proof/evidence identity
proof fingerprint if appropriate
observation time
```

Exact field names may differ.

Do not add Binance-specific error codes/types to Core.

## 8.4 Zero-Delta Resolution

Required coordinator behavior:

```text
result = discover_order(local)

if PRESENT and result.discovered_facts:
    enqueue
    await APPLIED/DUPLICATE receipts
    verify against Venue
    resolve if verified

if PRESENT and result.discovered_facts is empty:
    verify local == authoritative Venue state
    if verified:
        resolve UNKNOWN without fabricated fact
    else:
        remain unresolved
```

Do **not** create fake Accepted/Terminal updates just to obtain a receipt.

A verified no-op is a legitimate reconciliation success.

# 10. Required Behavior D — Authoritative Negative Proof for “No External Order”

## 10.1 Root Cause

Because `DISPATCHED` evidence must be persisted before the actual side effect, a legitimate crash window exists:

```text
DISPATCHED evidence persisted
→ process crashes
→ socket write never reaches Binance
```

After restart, OnlyAlpha must treat this as:

```text
MAY_HAVE_DISPATCHED / UNKNOWN
```

and reconcile by the same stable identity.

If the Venue truly has no order, there must be a deterministic path to resolve this uncertainty.

## 10.2 Required Rule

Core must never interpret provider-specific errors directly.

The Binance plugin must classify provider observations into provider-neutral reconciliation meaning.

Conceptually introduce something like:

```text
OnlyBinanceOrderPresenceClassifier
```

mapping Binance observations to:

```text
PRESENT
ABSENT_PROVEN
INCONCLUSIVE
```

This classifier belongs in the Binance plugin.

Core must not contain logic such as:

```python
if binance_error_code == -2013:
    ...
```

## 10.3 Official Binance Evidence

At implementation time, re-check current official Binance Spot documentation.

Use official Binance sources, especially:

- REST API:
  `https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md`
- Error codes:
  `https://github.com/binance/binance-spot-api-docs/blob/master/errors.md`
- User Data Stream:
  `https://github.com/binance/binance-spot-api-docs/blob/master/user-data-stream.md`
- Spot Testnet REST:
  `https://github.com/binance/binance-spot-api-docs/blob/master/testnet/rest-api.md`

Current verified semantics from the prior audit include:

```text
-1006 UNEXPECTED_RESP
→ execution status unknown

-1007 TIMEOUT
→ send/execution status unknown

HTTP 5XX
→ must not be treated as failed operation;
   execution status may be UNKNOWN
```

Provider rules are mutable. Re-verify before implementing negative-proof classification.

## 10.4 ABSENT_PROVEN Is Stronger Than “Query Returned No Snapshot”

Do not automatically equate:

```text
order not returned
network error
5xx
rate limit
auth failure
archived order
temporary provider inconsistency
```

with:

```text
ABSENT_PROVEN
```

`ABSENT_PROVEN` must only be produced when current provider contract and query conditions are sufficient to prove that the semantic order does not exist for the relevant reconciliation purpose.

Otherwise:

```text
INCONCLUSIVE
→ UNKNOWN remains
```

## 10.5 Negative Proof Is Not a Venue Execution Fact

If absence is proven:

```text
Broker Command Knowledge:
MAY_HAVE_DISPATCHED
→ NO_EXTERNAL_ORDER_PROVEN
→ RESOLVED
```

Do not fabricate:

```text
OrderRejected
OrderCancelled
OrderExpired
```

unless the Venue actually provides such an authoritative fact.

The proof belongs to reconciliation/command evidence.

## 10.6 No Automatic Blind Retry

This closure task must not add automatic re-submit after `ABSENT_PROVEN`.

Safe default:

```text
absence proof
→ resolve UNKNOWN
→ no automatic new POST
```

If future policy permits a resend, it must preserve:

```text
same OrderId
same ClientOrderId
same semantic Order Intent
```

and must never create a second identity merely because the earlier outcome was UNKNOWN.

## 10.7 Cancel UNKNOWN Is Different

Do not reuse submit-absence semantics blindly for cancel.

For cancel reconciliation:

```text

```

may reveal:

```text
CANCELLED
FILLED
EXPIRED
OPEN
other supported state
```

Absence alone must not be converted into `CANCELLED`.

Provider-specific cancel reconciliation stays in the plugin; Core receives canonical facts/proofs.
