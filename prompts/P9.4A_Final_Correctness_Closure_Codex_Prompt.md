# 2. First-principles invariants

All implementation decisions in this task MUST preserve the following invariants.

## 2.1 External venue Authority

For real execution facts:

```text
Binance / external venue
→ execution fact Authority
```

OnlyAlpha owns:

```text
intent
policy
strategy identity
local canonical identity
durable state
reconciliation
promotion/safety decisions
```

An HTTP response, network exception, local timeout, WebSocket transport, database row, or plugin callback is **not** execution Authority.

---

## 2.2 Communication outcome != execution outcome

For a side-effecting command, distinguish:

```text
Transport Observation
    ↓
Provider Protocol Interpretation
    ↓
Execution Knowledge
    ↓
Canonical Broker Outcome
```

Never collapse all non-2XX responses into:

```text
REJECTED
FAILED
NOT_DISPATCHED
```

A transport failure can coexist with successful venue execution.

---

## 2.3 UNKNOWN is first-class knowledge, not an OrderStatus

Keep business state and knowledge state orthogonal.

Examples:

```text
OrderStatus = SUBMITTED
SubmissionOutcome = UNKNOWN
```

or:

```text
OrderStatus = PENDING_CANCEL
CancelCommandKnowledge = UNKNOWN
```

Do **not** create business states such as:

```text
CANCEL_UNKNOWN
HTTP_TIMEOUT_ORDER
BINANCE_5XX_ORDER
```

Provider/transport uncertainty must not pollute canonical order business vocabulary.

---

## 2.4 Stable identity

For one semantic order intent:

```text
OnlyOrderId
OnlyClientOrderId
```

must remain stable across:

- timeout;
- 5XX;
- restart;
- reconciliation;
- stream reconnect;
- status query;
- retry of observation/query.

Never solve uncertainty by generating a new ClientOrderId and resubmitting the same semantic order.

---

## 2.5 Durable-before-side-effect

Before a command is allowed to cross the external side-effect boundary, enough local semantic intent must already be durably recoverable to identify and reconstruct the command after crash.

Conceptually:

```text
Order Intent
+ stable identity
+ semantic request / fingerprint
+ required runtime/account context
        ↓
DURABLE COMMIT
        ↓
==============================
 External Side Effect Boundary
==============================
        ↓
Venue dispatch
```

The exact storage mechanism must reuse the existing OnlyAlpha persistence architecture where possible.

Do not introduce a Binance-specific parallel truth store if the requirement is universal.

---

## 2.6 One canonical execution application path

All venue facts, including facts discovered by reconciliation, must ultimately enter the same canonical execution path:

```text
BrokerInboundQueue
        ↓
OnlyExecutionProcessor
        ↓
durable transaction / canonical projections
```

Reconciliation must not directly mutate:

- `OnlyOrderManager`;
- Position;
- Account;
- Fee;
- Strategy Ledger;
- Risk;
- database projections.

---

## 2.7 Reconciliation observes truth; it does not fabricate history

A REST query returning:

```text
status=CANCELLED
```

is an authoritative **current-state observation**.

It does not prove that OnlyAlpha observed or received a particular historical sequence such as:

```text
Accepted(seq=N)
Cancelled(seq=N+1)
```

Do not fabricate provider sequence numbers, timestamps, intermediate venue events, or synthetic historical execution order merely to satisfy the local state machine.

---

## 2.8 Fail-closed for risk increase

While submission outcome, cancellation, stream trust, external identity, or reconciliation is unresolved:

```text
new risk-increasing execution
→ blocked
```

but OnlyAlpha must continue:

- observation;
- inbound fill processing;
- cancellation/risk-reduction where safe;
- persistence;
- reconciliation;
- recovery.

# 3. External protocol evidence — Binance official documentation

Provider behavior is mutable. It belongs in the Binance plugin boundary and MUST NOT become permanent Core semantics.

At execution time, re-check current Binance official documentation. If current official behavior has changed, implement the **current official contract** inside the provider plugin and record the evidence in the final report.

Primary official source repository:

- `https://github.com/binance/binance-spot-api-docs`

Relevant official documents:

- REST API:
  - `https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md`
- Error codes:
  - `https://github.com/binance/binance-spot-api-docs/blob/master/errors.md`
- User Data Stream:
  - `https://github.com/binance/binance-spot-api-docs/blob/master/user-data-stream.md`
- Spot Testnet REST:
  - `https://github.com/binance/binance-spot-api-docs/blob/master/testnet/rest-api.md`

Current official evidence verified for this task design:

### 3.1 `-1007 TIMEOUT`

Binance documents `-1007 TIMEOUT` as:

```text
Send status unknown; execution status unknown.
```

and explicitly states that it does not always mean the request failed in the Matching Engine. If the status does not appear in User Data Stream, the client should query its status.

Therefore for a side-effecting order/cancel command:

```text
-1007
≠ definitive rejection
≠ definitive not-dispatched
```

unless a more specific current official provider contract proves otherwise.

### 3.2 HTTP 5XX

Binance states that HTTP `5XX` represents internal Binance errors and:

```text
must NOT be treated as a failed operation;
execution status is UNKNOWN and could have been a success.
```

Therefore a side-effecting command receiving HTTP 5XX must not cause OnlyAlpha to release reservations and conclude the external operation definitely failed.

### 3.3 Other unknown-class evidence

Current Binance error documentation also identifies cases such as:

```text
-1006 UNEXPECTED_RESP
→ Execution status unknown.
```

Use evidence-based classification. Do not maintain a simplistic rule such as:

```text
all HTTP 4XX = definitive failure
all non-2XX = KNOWN_RESULT
```

Some HTTP/provider responses can represent partial success or ambiguous execution.

### 3.4 User Data Stream

Current official User Data Stream documentation defines order updates using:

```text
executionReport
```

with fields including:

```text
client order ID
order ID
execution type
order status
last executed quantity
cumulative executed quantity
trade ID
transaction time
execution ID
```

Use current official protocol semantics. Do not move Binance field names or event-specific rules into Core.

### 3.5 Spot Testnet

Current official Spot Testnet REST documentation defines the Testnet base endpoint:

```text
https://testnet.binance.vision/api
```

The Testnet proof harness MUST hard-fail if configured against a production/mainnet host.

# C1 — Establish/prove a real durable-intent-before-dispatch barrier

## Problem

The current P9.4A code contains durable broker evidence concepts such as `INTENT_DURABLE`, `DISPATCHED`, `UNKNOWN`, reconciliation state, etc.

However, the previously audited mainline did not prove that the **real product submission path** durably commits the local semantic order intent before the Binance side effect can occur.

Definitions or test-only calls are not sufficient.

## Required behavior

For every real Binance Spot side-effecting order submission:

```text
1. canonical Order Intent exists
2. stable OnlyOrderId exists
3. stable OnlyClientOrderId exists
4. enough semantic local state is durably recoverable
5. durable commit is confirmed
6. only then may the first external socket/HTTP dispatch occur
```

The crash boundary:

```text
after durable intent
before external dispatch
```

must recover deterministically as a locally known command that was not proven externally dispatched.

The crash boundary:

```text
after external dispatch
before response/evidence completion
```

must recover as potentially dispatched / UNKNOWN unless durable evidence proves a stronger fact.

## Implementation guidance

First inspect the existing persistence/checkpoint/runtime transaction architecture.

Prefer reuse over invention.

If the existing persistence authority can provide this barrier, wire and prove it.

If a small universal Broker command durability port is truly missing, add only the minimum **market-agnostic** contract necessary.

Do not create:

```text
binance_command_truth.json
binance_order_truth.db
Binance-only shadow Order store
```

as a second authoritative state.

Do not claim `fsync`/commit durability unless the actual persistence contract provides it.

If the runtime currently cannot synchronously establish a durable barrier before dispatch, fix that architecture minimally and explicitly.

## Required evidence

Add deterministic fault-injection tests for at least:

### C1-A

```text
create order
→ durable intent succeeds
→ crash before dispatch
→ restore
→ no external order was sent
→ same OrderId/ClientOrderId remains recoverable
```

### C1-B

```text
create order
→ durable intent succeeds
→ external dispatch occurs
→ crash before response handling
→ restore
→ no blind resubmit
→ reconcile using same ClientOrderId
```

### C1-C

```text
durable intent commit fails
→ external dispatch MUST NOT happen
```

This last case is mandatory.

# C2 — Correct provider command-outcome classification

## Problem

The audited implementation classified generic non-2XX private REST responses as `KNOWN_RESULT`.

That is incorrect for Binance side-effecting commands because official documentation explicitly declares HTTP 5XX and `-1007` execution outcomes UNKNOWN.

## Required design

Do not let a generic HTTP transport layer decide venue execution truth.

Separate at least conceptually:

```text
transport observation
provider error/result
operation type
execution knowledge
```

A `GET` query failure and a `POST /api/v3/order` ambiguous response do not have identical semantic consequences.

## Required side-effect command classification

At minimum, prove correct handling for:

```text
network loss after possible write
→ UNKNOWN

socket/read timeout after possible write
→ UNKNOWN

HTTP 5XX
→ UNKNOWN

Binance -1007 TIMEOUT
→ UNKNOWN

Binance -1006 UNEXPECTED_RESP
→ UNKNOWN
```

A definitive rejection / not-dispatched result may only be produced when evidence proves the request did not reach or could not be accepted by the Matching Engine according to the current provider contract.

Use evidence-based classification rather than broad assumptions.

For example, official Binance documentation currently describes some errors such as malformed/invalid messages as rejected before the Matching Engine; such provider-specific knowledge belongs in the Binance adapter.

## Forbidden implementation

Do not implement:

```python
if status_code >= 400:
    return KNOWN_RESULT
```

Do not implement:

```python
except Exception:
    return REJECTED
```

Do not convert UNKNOWN into `FAILED` merely because reconciliation has not completed yet.

Do not release reservations while the external operation may still exist.

## Required tests

Deterministic tests must cover:

1. network timeout;
2. HTTP 500;
3. HTTP 503;
4. `-1007`;
5. `-1006`;
6. a truly definitive provider rejection;
7. successful known result;
8. UNKNOWN followed by venue query resolving to existing order;
9. UNKNOWN followed by authoritative evidence proving no order / terminal outcome according to supported provider semantics.

For all UNKNOWN cases assert:

```text
same OrderId
same ClientOrderId
no second POST
risk-increasing readiness revoked
reservation/state not incorrectly released
reconciliation required
```




## Required tests


# C4 — Fix reconciliation snapshot semantics; never fabricate provider history

## Problem

The audited Binance discovery path could represent one authoritative terminal snapshot such as:

```text
Venue status = CANCELLED
```

by fabricating:

```text
AcceptedUpdate
CancelledUpdate
```

with conflicting/same provider sequence semantics.

This prevents deterministic convergence and, more importantly, confuses a current-state snapshot with historical venue events.

## Required behavior

A reconciliation query returning a terminal state must be able to converge local state directly and deterministically **without inventing unobserved provider history**.

For example:

```text
Local:
SUBMITTED

Venue snapshot:
venue_order_id = V1
status = CANCELLED
```

must be able to produce:

```text
Local:
CANCELLED

Identity:
OrderId ↔ ClientOrderId ↔ VenueOrderId V1
```

without synthetic:

```text
Accepted(seq=N)
Cancelled(seq=N+1)
```

unless those events were genuinely observed from provider evidence.

## Core vs provider boundary

The fact that reconciliation can first observe an order in a terminal state is a universal broker concept, not Binance-specific.

However:

```text
Binance status strings
Binance field names
Binance event codes
```

remain plugin-specific.

If current canonical terminal update types cannot bind `VenueOrderId` or express a valid reconciliation observation, evolve the minimum universal canonical contract.

Prefer the smallest coherent model.

Acceptable design directions include:

1. letting canonical terminal facts carry verified external order identity when needed; or
2. introducing one explicit market-agnostic reconciliation snapshot observation if existing event semantics cannot truthfully represent the provider snapshot.

Do not add a provider-specific Core type.

## Sequence requirements

Do not generate fake provider sequence numbers.

If Binance REST snapshot data lacks a total event sequence, the plugin/Core boundary must represent that honestly.

Deduplication/replay identity for snapshot-derived facts must be deterministic and based on real stable inputs.

Do not use:

```text
current wall clock
random UUID
query attempt number
synthetic +1 sequence
```

as canonical truth identity.

## Required tests

At minimum:

### C4-A — cancelled snapshot

```text
SUBMITTED local
→ query returns CANCELLED + venue order identity
→ one reconciliation path
→ local CANCELLED
→ verify converged
```

### C4-B — filled snapshot

```text
SUBMITTED/ACCEPTED local
→ query/trades reveal FILLED
→ fill facts applied through execution processor
→ order/position/account/fee/ledger converge
```

### C4-C — duplicate snapshot

Repeated identical reconciliation query:

```text
→ no duplicated economic effect
→ deterministic duplicate/no-op
```

### C4-D — identity conflict

Same local semantic order but conflicting VenueOrderId:

```text
→ hard conflict
→ fail closed
→ readiness false
→ no silent overwrite
```

# C5 — Reconciliation facts must traverse the full runtime execution path

## Problem

Existing tests previously drained broker facts and then directly called `OrderManager.apply_*`.

That proves only Order projection behavior.

It does not prove end-to-end economic convergence.

## Required runtime path

Reconciliation-discovered facts MUST flow through:

```text
OnlyBrokerReconciliationCoordinator
        ↓
OnlyBrokerInboundQueue
        ↓
Runtime broker inbound drain / canonical dispatcher
        ↓
OnlyExecutionProcessor
        ↓
durable transaction
        ↓
Order / Position / Account / Fee / Ledger / Reservation / Risk
```

No direct Manager mutation from reconciliation code or tests.

## Application receipt

Existing `OnlyBrokerFactApplicationReceipt` or equivalent should become a real part of the runtime closure.

The coordinator may resolve UNKNOWN only when:

1. every expected discovered canonical fact is either:
   - durably applied; or
   - deterministically recognized as an already-applied identical fact;
2. no identity/sequence/conflict failure exists;
3. local state is verified against authoritative venue state;
4. stream/reconciliation trust requirements are satisfied.

A receipt must not be forged simply because a queue was drained.

If a small runtime adapter/port is useful, keep it generic and ensure its implementation still goes through `OnlyExecutionProcessor`.

## Required tests

Replace/augment tests that manually call:

```text

manager.apply_cancelled
```

with real runtime execution processing.

Verify actual economic outcomes for recovered fills:

```text

```

Use the nearest existing canonical assertions; do not build a parallel test-only economic model.

# 6. Detailed design constraints

## 6.1 Do not create a second Authority

Forbidden:

```text
Plugin-owned shadow Order state
Broker-owned parallel portfolio/account truth
Reconciliation-owned mutable order database
Test-only direct manager mutation used as product proof
```

Caches are acceptable only when derivable, non-authoritative, and safely rebuildable.

---

## 6.2 No blind retries

For side-effecting commands:

```text
UNKNOWN
→ observe/query/reconcile
```

not:

```text
UNKNOWN
→ new ClientOrderId
→ POST again
```

If a retry of the exact wire command is ever considered safe by a provider-specific contract, it must be explicitly proven, identity-preserving, and consistent with OnlyAlpha’s canonical semantics. Do not introduce such behavior casually in this task.

---

## 6.3 Query retries are not command retries

It is acceptable to retry **observations** deterministically according to bounded policy:

```text
GET order
GET trades
stream reconnect
```

provided rate-limit/backoff rules are respected.

Do not treat observation retry as permission to repeat an external side effect.

---

## 6.4 No wall-clock identity

Canonical event/receipt/dedup identity must not depend on:

```text
datetime.now()
time.time()
random UUID
process PID
query attempt count
```

unless that value is an explicit authoritative input and appropriate for the identity definition.

---

## 6.5 No provider leakage into Core

Core may understand universal concepts such as:

```text
external order identity
accepted
trade/fill
cancelled
rejected
expired
unknown command outcome
reconciliation snapshot/observation
```

Core must not understand:

```text
-1007
executionReport field "x"
Binance symbol filters
recvWindow
Binance listenKey
Binance REST path
```

---

## 6.6 No Spot/Futures semantic leakage

This task is Binance **Spot** only.

Do not:

- implement USD-M Futures;
- add Futures positions;
- add leverage/margin Futures concepts;
- generalize Spot by prematurely implementing Futures semantics.

If a universal canonical concept is needed, add only that concept.

ADR 0099 sequencing remains authoritative.
