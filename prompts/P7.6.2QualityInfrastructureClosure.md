============================================================
0. 最高原则
============================================================

OnlyAlpha 是一个面向个人与小型团队的模块化量化交易工程。

长期目标：

- Research / Backtest / Sim / Live 四种 Runtime；
- 清晰的工程边界；
- 确定性结果；
- 单一状态权威；
- 可验证；
- 可恢复；
- fail closed；
- Backtest / Sim / Live 尽可能共享同一 Trading semantic kernel；
- Research 独立服务于 batch/vectorized research efficiency。

所有工程决策必须按以下优先级权衡：

正确性
>
架构一致性
>
可验证性
>
可恢复性
>
可维护性
>
性能
>
自动化程度

不要为了：

- CI 更绿；
- CI 更快；
- 少写代码；
- Agent 更容易实现；
- 减少 workflow 数量；
- 避免远端工具失败；

破坏前面的原则。

尤其禁止：

- 通过删除测试解决测试失败；
- 通过 lowering threshold 解决 coverage 失败；
- 使用 continue-on-error 掩盖 mandatory quality failure；
- 删除 ASV 解决 ASV 失败；
- 删除 dependency security gate 后不提供等价能力；
- 把 VERIFIED / CERTIFIED 写成没有 exact evidence 支撑的宣传性状态。

它不能只是回答：

“benchmark 函数没有 crash。”

同时区分：

pytest-benchmark
和
ASV

的职责。

建议合同：

pytest-benchmark
=
current environment benchmark health
+
absolute measurement evidence

ASV
=
commit-to-commit regression comparison

------------------------------------------------------------
6.1 不允许的实现
------------------------------------------------------------

禁止：

asv failure
→ 删除 ASV

禁止：

asv failure
→ continue-on-error

禁止：

asv failure
→ --quick 以后宣称有正式 performance evidence

禁止：

asv failure
→ 随意提高 regression tolerance

禁止：

ASV 失败
→ 直接将 Nightly performance 改成 non-blocking

------------------------------------------------------------
6.2 Git history
------------------------------------------------------------

ASV commit comparison 必须保证有足够 Git history。

优先考虑 performance job 单独使用：

actions/checkout
fetch-depth: 0

原因：

- benchmark 是 Git-history-aware；
- 后续不仅可能比较 HEAD^；
- full history 更不容易产生 shallow clone 边缘错误。

不要因为 fetch-depth:2 理论上够用就牺牲验证健壮性，除非当前仓库规模或实际 benchmark 证明 full history 成本明显不合理。

------------------------------------------------------------
6.3 Benchmark definition check
------------------------------------------------------------

在正式 execution 之前增加明确 benchmark suite validation。

例如适当使用：

asv check

目的：

将：

benchmark definition broken

与：

benchmark regression/execution failed

区分开。

------------------------------------------------------------
6.4 Fresh-runner machine bootstrap
------------------------------------------------------------

GitHub-hosted runner 是 ephemeral environment。

ASV 不应依赖人工提前执行：

asv machine

CI 必须 self-contained。

提供非交互 deterministic bootstrap。

可以使用适合当前 ASV 版本的：

asv machine --yes

或等价官方机制。

但不要把所有 GitHub Runner 永久伪装成真正稳定的同一物理机器。

machine identity 应服务于：

same-run comparison

而不是制造：

cross-run hardware comparability illusion。

优先采用 run-local CI machine identity。

例如概念上：

github-actions-${GITHUB_RUN_ID}

但具体 spelling 应根据 ASV 当前行为实现。

关键 invariant：

base commit
和
candidate commit

必须在：

same runner
same environment
same machine identity
same job

内比较。

------------------------------------------------------------
6.5 使用正确的 ASV CI comparison 模式
------------------------------------------------------------

检查当前 ASV 版本官方能力。

对于 ASV 0.6.x，优先考虑：

asv continuous <base> <candidate>

而不是：

asv run --quick HEAD^!

目标是：

parent commit
vs
current commit

的 side-by-side comparison。

不要使用 --quick 作为正式结果模式。

如果 current ASV version、repository configuration 或实际 CLI contract 表明有更合适的官方方式：

使用 current verified official approach。

不要根据记忆猜参数。

7. 第二目标：Dependency Security Closure
============================================================

第一性原理：

Dependency security gate 不是依赖升级机器人。

它回答：

“当前 resolved dependency universe 是否包含已知且未批准接受的 vulnerability？”

OnlyAlpha 使用 uv workspace + uv.lock。

因此优先：

uv.lock
=
dependency security audit authority input

不要用随机：

pip freeze

因为那只是当前 runner 环境。

------------------------------------------------------------
7.1 Scanner selection
------------------------------------------------------------

基于当前 toolchain 选择：

- 可 pinned；
- 支持 uv.lock；
- 可在 Linux CI 稳定运行；
- 有清晰 non-zero exit semantics；
- 能产生机器可读 evidence；

的 dependency vulnerability scanner。

优先评估 OSV-Scanner。

但实现前必须检查当前官方版本与 CLI contract。

不要凭历史 Prompt 猜版本或参数。

如果当前 uv pinned version 原生 audit 能力不足：

不要为了这一阶段大规模升级 uv。

Quality Closure 不应隐含升级：

resolver
lock format
toolchain behavior

除非 current repository 已经自然完成了升级。

------------------------------------------------------------
7.2 Scan exact authority
------------------------------------------------------------

默认只扫描 authoritative：

uv.lock

不要无脑：

recursive scan repository

因为这可能把：

tests fixtures
example manifests
external plugin fixtures
temporary project
benchmark environment

混入正式 security authority。

如果 workspace 的 resolved dependencies 已完整包含在 root uv.lock：

root uv.lock 即正式 audit input。

------------------------------------------------------------
7.3 Fail closed
------------------------------------------------------------

默认 policy：

known unapproved vulnerability
→ fail

禁止：

continue-on-error: true

禁止：

always success

禁止：

ignore all

禁止：

因为 scanner 服务偶发错误就永远 soft-pass

对于 external scanner/network transient failure：

要清楚区分：

SCAN_INFRASTRUCTURE_FAILURE

和：

VULNERABILITY_FOUND

但两者都不应该被误报成：

security passed。

------------------------------------------------------------
7.4 Explicit exceptions
------------------------------------------------------------

如果确实存在必须暂时接受的 vulnerability：

允许 explicit exception。

Exception 至少必须包含：

- vulnerability ID；
- reason；
- expiry；

最好还包含：

- affected package；
- owner；
- reference；

不要：

ignore package globally

不要：

永久 ignore without expiry

不要：

wildcard ignore

到期以后必须重新 fail closed。

不要默认创建 exception config。

只有确实存在 finding 才创建。

------------------------------------------------------------
7.5 Evidence semantics
------------------------------------------------------------

Dependency audit 依赖 external advisory database。

因此：

same uv.lock

在不同日期可能得到不同 vulnerability state。

这不是 deterministic semantic calculation。

所以 security result 属于：

time-scoped external verification evidence

不要加入任何：

Calculation fingerprint
Dataset fingerprint
Research identity
Runtime semantic identity

Evidence 应记录：

- subject SHA
- uv.lock digest
- scanner version
- scan time
- findings
- approved exceptions

不要删除 heavy validation。

代码 + formal tests + accepted certification evidence 优先；
随后修 docs。
