# OnlyAlpha P9.0 Closure — Strategy Authority Closure & Certification
## Codex Implementation Task Prompt

> **Project:** OnlyAlpha  
> **Milestone:** P9.0 Closure  
> **Repository:** `zongxin1993/OnlyAlpha`  
> **Purpose:** Close all remaining authority, uniqueness, determinism, execution-path and certification gaps in P9.0 before P9.1 begins.
>
> This task is **not a new feature milestone**. It is a **closure/correction milestone** for P9.0.
>
> The P9.0 design is already frozen. Do not redesign Strategy Product architecture unless current repository truth proves a frozen assumption impossible. If a true architecture conflict is found, stop and report it explicitly rather than silently creating a second interpretation.

---

# 1. Mission

P9.0 Closure must make the following statement true in the actual repository, not merely in documentation:

> **For any Strategy in OnlyAlpha, there is exactly one identity, one creation authority, one admission authority, one executable semantic form, one resolver path, and one deterministic promotion-history interpretation.**

The target chain is:

```text
Verified Research
      ↓
Exact Candidate
      ↓
Unique Freeze Authority
      ↓
Verified Trading Admission
      ↓
Immutable Strategy Revision
      ↓
strategy_fingerprint
      ↓
Immutable Strategy Store
      ↓
Unique Strategy Resolver
      ↓
Exact TRADING Calculation execution
      ↓
StrategyDecision
      ↓
Explicit downstream Trading boundary
```

No other Strategy semantic or executable authority may remain valid after Closure.

---

# 2. Why this Closure exists

The initial P9.0 implementation correctly introduced:

```text
StrategyRevision
strategy_fingerprint
Candidate Freeze
immutable Strategy Store
Calculation implementation identity
StrategyExecutionResolver
StrategyDecision
append-only Promotion domain
```

but the latest audit found remaining closure gaps.

The most important unresolved problems are:

```text
1. Arbitrary Python OnlyStrategy subclasses can still form a second Strategy execution path.

2. Revision-backed Strategy currently produces StrategyDecision,
   but the formal downstream handoff boundary is not closed.

3. Trading Admission currently consumes equivalence declarations/registrations,
   but equivalence evidence is not yet a verified immutable authority.

4. Calculation implementation identity exists,
   but implementation closure / semantic dependency binding is incomplete.

5. Internal Predicate code mixes RESEARCH and TRADING runtime implementation concerns.

6. Trading Resolver still verifies RESEARCH backend availability,
   causing unnecessary Trading→Research runtime coupling.

7. Calculation checkpoint/state capability is partially inferred from method presence
   rather than being an explicit semantic/runtime contract.

8. Strategy Market Input freezes adjustment_reference,
   but Runtime BAR cannot prove that reference.
   P9.0 V1 should fail closed to RAW-only rather than pretend to support unprovable adjusted input.

9. PostgreSQL Promotion ordering uses audit timestamps as ordering assistance,
   while the actual immutable chain authority is previous_record_fingerprint.

10. Product-level Freeze/Promotion composition is not yet fully closed as one official application/operator path.

11. Architecture tests prevent some legacy paths,
    but existing tests still legitimize Python callback Strategy authoring.

12. P9.0 exact-final-SHA certification is not complete.
```

Closure must fix these structurally.

# 3. Frozen first-principles invariants

These are non-negotiable.

## 3.1 One Strategy identity

The only authoritative Strategy identity is:

```text
strategy_fingerprint
```

If two Strategy Revisions have the same fingerprint, OnlyAlpha treats them as the same Strategy.

Do not create a second runtime or revision identity authority.

Allowed non-authoritative metadata may include:

```text
display_name
catalog_family
human alias
```

but these must never control execution.

---

## 3.2 One Strategy creation authority

The only legal production path is:

```text
Verified Research Candidate
→ Freeze
→ Strategy Revision
```

No Web/API/Runtime/client may directly author:

```text
StrategyRevision
Decision Graph
Market Input Contract
implementation bindings
Strategy semantic JSON
```

for production execution.

---

## 3.3 One Strategy execution form

The only executable Strategy semantic form is:

```text
strategy_fingerprint
→ load_verified StrategyRevision
→ StrategyExecutionResolver
→ exact TRADING Calculation graph
→ StrategyDecision
```

Arbitrary user Python Strategy callback logic is forbidden as a second execution model.

---

## 3.4 Runtime != Strategy

Backtest, SIM and future LIVE differ in runtime environment, not Strategy semantics.

Do not create:

```text
BacktestStrategy
SimStrategy
LiveStrategy
```

or equivalent independent strategy implementations.

---

## 3.5 Strategy ends at semantic decision output

Strategy output is:

```text
ELIGIBILITY
ENTRY
EXIT
```

These are semantic signals.

They are not:

```text
orders
position size
capital allocation
risk decision
broker command
execution instruction
```

The downstream target remains:

```text
StrategyDecision
→ Portfolio / Position Policy
→ Risk
→ Order Intent
→ Execution
```

P9.0 Closure must establish the formal handoff, not implement later-stage portfolio/risk product behavior unless a minimal existing kernel interface is required.

---

## 3.6 Fail closed

When authority, identity, equivalence, implementation identity, state capability or market-input semantics cannot be proven:

```text
reject
```

Do not:

```text
guess
fallback
auto-repair
silently downgrade
reuse legacy behavior
```

---

## 3.7 One fact → one authority

Examples:

```text
Strategy semantic identity
→ Strategy Revision

Research provenance
→ Freeze Record

Calculation semantic identity
→ Calculation Definition

Calculation implementation identity
→ Implementation Manifest

Cross-backend equivalence
→ Verified Equivalence Evidence

Promotion history
→ append-only Promotion Records

Runtime configuration
→ Runtime/Profile configuration

Market observation fact
→ Market Data domain
```

Do not duplicate facts in multiple mutable authorities.

# 7. P9.0-C1 — Remove the second Python Strategy execution form

## Problem

Removing `strategy_path/config_path` is not sufficient if code still allows:

```python
OnlyCluster(strategy=CustomOnlyStrategy(...))
```

or if `OnlyStrategy` remains a supported public strategy-authoring abstraction.

That creates two executable semantics:

```text
A. Revision / Graph Strategy
B. Python callback Strategy
```

This violates uniqueness.

---

## Required changes

### 7.1 Remove arbitrary Strategy injection

`OnlyCluster` must no longer accept an arbitrary Strategy implementation as a public product API.

Prefer one of these shapes:

```text
OnlyCluster receives a resolved StrategyExecutionPlan
```

or:

```text
OnlyCluster receives an internal sealed Revision execution participant
```

Do not keep:

```python
strategy: OnlyStrategy
```

as a generic extensibility point.

---

### 7.2 Retain internal adapter only if kernel lifecycle requires it

If current Cluster/Pipeline lifecycle is easier to preserve with an adapter, keep exactly one internal adapter:

```text
OnlyRevisionStrategyAdapter
```

Its responsibility:

```text
Kernel lifecycle event
→ StrategyExecutionPlan
→ StrategyDecision
```

It must contain zero strategy-authoring semantics.

No per-strategy `if ... buy/sell` code.

---

### 7.3 Retire public Python Strategy authoring surface

Audit and remove or internalize as appropriate:

```text
OnlyStrategy
OnlyStrategyConfig
OnlyStrategyContext
OnlyStrategyId
```

Do not leave a public API that invites users/plugins to subclass and author trading semantics.

If any internal transitional type must remain, clearly mark it internal and structurally prevent external Strategy authoring.

---

### 7.4 Remove Strategy order/risk capabilities

A Strategy semantic executor must not receive direct access to:

```text
orders
positions
accounts
risk
broker
execution
```

If old `OnlyStrategyContext` exists solely for callback Strategy code, remove it or shrink/internalize it.

---

### 7.5 Rewrite conflicting tests

Remove or migrate tests that assert:

```text
OnlyTestMacdStrategy extends OnlyStrategy
context.orders.submit() is a legal Strategy behavior
```

Re-express test strategies through:

```text
Research Definition
→ Calculation Graph
→ Candidate
→ Revision fixture
→ ExecutionPlan
```

Do not delete useful behavior coverage; migrate it to the new authority model.

---

## C1 acceptance

Repository search + architecture tests must prove:

```text
No arbitrary production OnlyStrategy subclass execution
No OnlyCluster(strategy=<custom strategy>)
No runtime Python strategy class authority
No legacy strategy import authority
One production concrete Strategy execution implementation
```

# 10. P9.0-C4 — Separate RESEARCH and TRADING backend runtime boundaries

## Problem

A module under Research should not become the runtime home of the TRADING backend merely because both implement the same semantic Definition.

Shared semantic Definition is valid.

Shared runtime authority is not.

---

## Required refactor

Where current code mixes:

```text
Research backend
Trading backend
shared Definition
```

in a Research-owned module, split the ownership.

Target conceptual shape:

```text
Calculation semantic definition
          │
    ┌─────┴─────┐
    ▼           ▼
Research       Trading
backend        backend
```

Shared semantic helper code may live in a neutral Calculation domain module if genuinely semantic.

Do not duplicate Definition semantics.

---

## Trading Runtime dependency rule

A Trading Runtime should be able to resolve and execute its Strategy without importing or requiring Research-only runtime implementation packages.

```text

```

---

## Sole chain authority

Use:

```text

```

---

## Chain verification

For one Strategy:

1. exactly one valid head:
   ```text
   previous_record_fingerprint = null
   ```
2. every next record points to exactly one previous record;
3. no record has more than one child unless branching is explicitly designed — for P9.0, branching is invalid;
4. no cycle;
5. no orphan;
6. all rows must be consumed exactly once;
7. each record fingerprint must verify;
8. stage transition must be legal.

---

```text

display
forensics
```

but never as semantic ordering authority.

Tests must include:

