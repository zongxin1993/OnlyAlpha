# 2. 第一性原理

本任务不是：

```text
“修两个测试”
```

也不是：

```text
“为了代码漂亮再加一层 abstraction”
```

真正需要保护的是两个基础原则。

---

## 2.1 唯一性原则

同一个事实只能有一个 authority。

对于 Registered Universe：

```text
Universe Catalog 中声称存在的能力
```

必须和：

```text
Definition Resolver 真正能够执行的能力
```

来自同一个事实来源。

必须满足：

```text
Discovery Capability
==
Resolution Capability
```

绝不能出现：

```text
Discovery:
REGISTERED_POOL supported

Resolution:
registered Universe resolver unavailable
```

也不能存在：

```text
Catalog Authority A
+
Resolver Authority B
```

两个独立注入源在生产 composition 中悄悄漂移。

---

## 2.2 确定性原则

公共 Research Definition contract 必须明确区分：

```text
用户可以 author 的语义
```

和：

```text
Resolver / Compiler 内部生成的 execution primitive
```

`PREDICATE` 是：

```text
internal exact Calculation primitive
```

用于：

```text
Eligibility / Entry / Exit AST
→ deterministic lowering
→ exact Calculation Graph
```

它不是用户直接选择的公共 Calculation Kind。

因此：

```text
Public Authoring Vocabulary
!=
Internal Execution Vocabulary
```

必须在 schema 层明确成立，而不是：

```text
先允许 PREDICATE 进入 HTTP/OpenAPI
然后等 Domain Resolver 再拒绝
```

Fail-close 应发生在最窄、最靠近外部 contract 的正确边界。

# 3. 本任务明确解决的问题

---

# 3.1 Problem A — Universe Discovery / Resolution Capability Drift

当前设计中存在两个窄 Port：

```python
OnlyResearchUniverseResolver
OnlyResearchUniverseCatalog
```

这种 Port 分离本身不是错误。

真正的问题是：

```text
application composition
```

没有强制二者来自相同 underlying authority。

理论上可以：

```text
Discovery
→ Catalog A

Definition Resolver
→ Resolver B
```

从而产生 capability drift。

此外，当前实现需要检查是否存在以下实际问题：

```text
GET /api/v2/research/catalog/universes
```

可能无条件暴露：

```text
REGISTERED_POOL
REGISTERED_UNIVERSE
```

但 production Definition Resolver 并未配置 registered Universe resolver。

这违反：

```text
Discovery
=
当前系统真实可执行能力的 read-only projection
```

---

# 3.2 Problem B — PREDICATE Leaks into Public Authoring Contract

当前 Calculation Registry 正确地隐藏 internal Predicate：

```python
OnlyCalculationRegistry.descriptors()
```

不向公共 Calculation Catalog 暴露：

```text
PREDICATE
```

但是必须检查当前 HTTP DTO / OpenAPI / generated TypeScript 是否仍然使用：

```python
OnlyCalculationKind
```

作为公共：

```text
ResearchCalculationTypeReferenceDto.kind
```

如果这样，会导致 OpenAPI 把：

```text
INDICATOR
FACTOR
TARGET
PREDICATE
```

全部暴露给 Research Definition authoring。

这与当前 architecture 不一致：

```text
Definition authoring
→ INDICATOR / FACTOR / TARGET

internal exact graph
→ may contain PREDICATE
```

# 6. Universe Closure — 设计原则

---

## 6.1 不要为了 closure 创建第二个 Universe Registry

禁止出现：

```text
OnlyResearchUniverseRegistry
```

仅仅为了同时实现：

```text
list
resolve
```

而创建一个新的 authority，除非仓库当前已经存在明确的 production Universe authority，且复用它是唯一合理方式。

本任务的目的不是增加 authority。

而是确保：

```text
同一个 underlying Universe authority
```

同时为：

```text
Discovery
Resolution
```

服务。

---

# 6.2 优先最小化 Composition Drift

根据当前代码选择最简单、边界最清晰的方案。

可以考虑以下方向，但不要机械执行：

### 方案 A：一个 authority 同时满足两个 Protocol

例如现有 production implementation 可以同时实现：

```python
OnlyResearchUniverseResolver
OnlyResearchUniverseCatalog
```

composition root 只构造一个对象：

```python
universe_authority = ...

definition_resolver = OnlyResearchDefinitionResolver(
    ...,
    universe_resolver=universe_authority,
)

create_research_app(
    ...,
    universe_catalog=universe_authority,
)
```

这是优先方向。

不一定要引入新的：

```python
OnlyResearchUniverseAuthority
```

类型。

如果现有两个 Protocol 已经足够，就不要为了“统一名字”额外创造抽象。

---

### 方案 B：如果当前没有 production registered Universe authority

那么 production capability 必须诚实。

例如：

```text
supported selection kinds
=
SINGLE_INSTRUMENT
EXPLICIT_INSTRUMENT_SET
```

而不是无条件返回：

```text
REGISTERED_POOL
REGISTERED_UNIVERSE
```

等以后真实 registered Universe authority 存在时，再自然暴露这两个 capability。

---

# 6.3 Discovery 必须投影实际 executable capability

必须建立不变量：

```text
如果 registered Universe resolution 不可用

则 discovery 不得声称：
REGISTERED_POOL
REGISTERED_UNIVERSE
```

反之：

```text
如果 registered Universe authority 可用

则 catalog listing 和 resolver
必须来自同一个 authority
```

---

# 6.4 Explicit Universe 不应被影响

已有：

```text
SINGLE_INSTRUMENT
EXPLICIT_INSTRUMENT_SET
```

必须保持原有 Definition semantics。

不要因为修 registered Universe 而增加：

```text
ExplicitUniverseResolver
```

之类没有必要的新概念。

# 8. PREDICATE Closure — 设计原则

Public Research Definition authoring 必须使用一个窄 contract：

```text
INDICATOR
FACTOR
TARGET
```

Internal exact execution 可以继续使用：

```text
PREDICATE
```

---

# 8.1 不要修改 Internal Calculation Domain

禁止为了隐藏 PREDICATE 而删除：

```text
OnlyCalculationKind.PREDICATE
```

它是内部 exact Calculation semantic kind，当前 Predicate lowering 正确依赖它。

保持：

```text
OnlyCalculationKind
=
full internal/domain vocabulary
```

---

# 8.2 不要修改 Registry 的 Predicate 语义

保持：

```text
type_definitions()
→ may contain Predicate

descriptors()
→ public calculation discovery hides Predicate
```

当前这一层的设计是正确的。

不要重复实现另一套 filtering Registry。

---

# 8.3 只收紧 Public Authoring DTO

公共 Research Definition authoring 应明确限制：

```text
INDICATOR
FACTOR
TARGET
```

选择最小实现。

可以使用：

```python
Literal["INDICATOR", "FACTOR", "TARGET"]
```

或者项目现有编码风格下的窄 Enum。

选择标准：

```text
最少概念
最清楚 contract
OpenAPI 输出准确
Domain conversion 简单
无重复 semantic authority
```

如果一个 `Literal` 足够，不要为了一个 transport contract 创建新的 domain enum。

---

# 8.4 注意不要误伤 exact_specification

P8.4.1 resolve response 中：

```text
exact_specification
```

是 existing Specification transport。

它内部 exact Calculation Graph：

```text
可以包含 internal PREDICATE
```

因此本任务不能把所有 OpenAPI 中所有：

```text
OnlyCalculationKind
```

统一删除 `PREDICATE`。

必须区分：

```text
Public Definition authoring type reference
```

和：

```text
Exact Specification / exact graph contract
```

只有前者禁止 PREDICATE。

---

# 8.5 Fail-fast

以下输入：

```json
{
  "kind": "PREDICATE",
  ...
}
```

如果出现在：

```text
Research Definition calculation / target type reference
```

必须在 HTTP/Pydantic admission 层失败。

不能进入：

```text

```

以后才拒绝。

# 29. 最终原则

