# 1. Mission

Implement **P8.4.3 — Research Studio & Runs Web** as the first complete daily-use Web-native Research control/product loop:

```text
User Research Intent
        ↓
Structured Research Builder
        ↓
OnlyResearchDefinition
        ↓
Authoritative Definition Resolution
        ↓
Exact Research Specification V2
        ↓
Research Command API
        ↓
Durable Research Run
        ↓
Scheduler / Worker
        ↓
OnlyEngine → OnlyResearchRuntime
        ↓
Immutable Research Result / Scientific Artifact
        ↓
Existing Query API
        ↓
Web Result navigation
```

P8.4.3 must solve a real product problem:

> A researcher should be able to define, validate/resolve, submit, observe, cancel, and open the exact result of a Research through the browser without manually writing Python, editing raw Specification JSON, constructing Calculation Graphs, constructing Workloads, or copying result fingerprints between disconnected tools.

This increment is **not** a frontend rewrite and **not** a new Research semantic plane.

The Browser remains:

```text
Control + Presentation Client
```

and never becomes:

```text
Research Semantic Authority
```

# 2. First-principles engineering rules

Treat these as hard constraints.

## 2.1 One fact, one authority

Each fact must have exactly one owner:

```text
Research authoring semantics
→ OnlyResearchDefinition / authoritative server resolution

Exact execution semantics
→ OnlyResearchSpecification

Runtime composition
→ OnlyResearchWorkloadPlan

Run operational state
→ Research Run Authority / PostgreSQL

Dataset truth
→ existing immutable Dataset authority

Calculation truth
→ existing Calculation authority

Statistics truth
→ existing Statistics authority

Research Result truth
→ existing immutable Result authority

Portable scientific evidence
→ Scientific Artifact

Browser
→ temporary authoring state + control + presentation only
```

Do not duplicate any of these authorities in React, PostgreSQL, a new Store, or a new Registry.

## 2.2 Determinism before convenience

Equivalent admitted semantic input must continue resolving to the same identities.

Do not implement any browser-side version of:

- Definition canonical semantic fingerprinting;
- Specification fingerprinting;
- Candidate fingerprinting;
- Calculation fingerprinting;
- Result fingerprinting;
- Artifact semantic fingerprinting;
- Predicate semantic execution;
- Statistics execution;
- Candidate ranking.

The server/domain remains the only semantic source of truth.

## 2.3 Fail closed on ambiguity

If a scientific publication has no uniquely defined semantic membership, reject it explicitly.

Do not:

- guess;
- broadcast implicitly;
- infer many-to-many relationships;
- let the browser repair ambiguous backend semantics;
- silently drop evidence.

## 2.4 Prefer the smallest abstraction that owns a real responsibility

Do not introduce frameworks merely because this is a Web milestone.

Do not add unless current code proves they are necessary:

- Redux;
- Zustand;
- MobX;
- XState;
- frontend repository/service layers around the existing API client;
- generic form DSL/runtime;
- generic rule engine;
- universal AST editor;
- browser semantic graph compiler;
- server Draft Store;
- Definition persistence authority;
- new Result/Artifact/Evidence/Candidate/Signal Stores;
- WebSocket/SSE;
- new scheduler/runtime layers.

Use the repository’s existing architecture and libraries first.

## 2.5 Domain → API → Web

Dependency direction is:

```text
Domain
  ↓
API transport
  ↓
Web
```

Never redesign Domain semantics merely to make a UI implementation easier.

If Web exposes a genuine contract gap, fix the correct authoritative layer narrowly and add tests there.

# 6. Architectural invariants

Implement and test these.

## Invariant A — Browser authors Definition, not Specification

The browser may temporarily hold incomplete form state, but the only formal semantic authoring payload sent for resolution is the existing versioned Research Definition transport.

Forbidden:

```text
React State
→ private Web specification compiler
→ exact Specification
```

Required:

```text
React Draft
→ ResearchDefinitionTransport
→ server resolve
→ exact_specification
```

## Invariant B — exact Specification comes only from the latest authoritative Resolution

Run submission must use the exact Specification returned by the latest successful server resolution.

Do not reconstruct or mutate it in Web code.

## Invariant C — Editing invalidates Resolution

If semantic Draft state changes after successful resolution:

```text
old resolution = stale
Run = disabled
new Resolve required
```

A stale asynchronous resolve response must never become submit-authoritative.

## Invariant D — Run state comes only from Run Authority

The browser displays only authoritative operational facts.

Do not manufacture:

- percent progress;
- inferred execution phases;
- worker progress;
- estimated completion state.

## Invariant E — Result scientific facts come only from Artifact/Query evidence

The browser must not bypass Artifact/Query to read internal Dataset/Calculation/Statistics stores or reconstruct Research truth.

## Invariant F — UI presentation state is non-semantic

Things such as:

- open panel;
- selected tab;
- column visibility;
- inspector collapsed;
- theme;
- viewport;

must not affect Definition/Specification identity.

# 7. Stage 0 — Scientific Publication Admission Closure

This absorbs the previously discussed P8.4.2.3.

Do this first. Complete and test it before implementing the Web feature stages.

## 7.1 Problem to close

Current/previous Specification resolution permits generic `published_series` to resolve all lineages selected by a series selector.

That is acceptable only when scientific membership is semantically defined.

Two admission gaps must be closed:

### Gap A — non-candidate swept publication ambiguity

Let:

```text
evidence.candidate_calculation_id = C
```

Rules:

### Case 1 — Candidate calculation publication

If selector references `C`, publication may resolve multiple candidate lineages, and each candidate-relative member must carry the exact candidate fingerprint already owned by the resolver.

Legal.

### Case 2 — Non-candidate singleton publication

If selector references a non-candidate calculation and resolution yields exactly one lineage:

```text
candidate_fingerprint = None
```

This is legal global/singleton evidence.

Example:

```text
one fixed Target instance
```

### Case 3 — Non-candidate multi-lineage publication

If selector references a non-candidate calculation and resolves to more than one lineage:

```text
FAIL CLOSED
```

The model has no defined Candidate ↔ non-candidate multi-lineage membership relationship.

Use a stable domain error consistent with repository conventions, for example:

```text
RESEARCH_SPEC_PUBLISHED_SERIES_AMBIGUOUS
```

Exact spelling may adapt to current error taxonomy, but it must be explicit and stable.

Do not solve this by:

- adding a join table;
- adding relationship Store;
- inventing implicit Cartesian association;
- assigning unrelated candidate fingerprints;
- silently choosing one lineage.

## 7.2 Predicate publication boundary

Internal `PREDICATE` Calculation outputs must not enter generic scientific Variables publication.

The generic publication plane is for admitted public scientific outputs from the formal public Calculation vocabulary.

Eligibility / Entry / Exit evidence continues to flow through the existing Signal Evidence path.

Required invariant:

```text
INDICATOR / FACTOR / TARGET admitted public outputs
→ generic published scientific variables where otherwise valid

PREDICATE internal outputs
→ not generic published variables

ELIGIBILITY / ENTRY_SIGNAL / EXIT_SIGNAL
→ existing signal evidence path
```

Use exact Calculation kind/semantic evidence. Do not detect predicates using fragile type-id string matching.

## 7.3 Stage 0 must not change identity formulas

Do not change:

- candidate identity formula;
- Specification fingerprint;
- Calculation fingerprint;
- Result identity;
- Artifact semantic identity;
- V1 compatibility semantics.

Do not create a new schema version unless current contracts prove one is truly required. It should not be required for this closure.

## 7.4 Stage 0 tests

At minimum prove:

```text
candidate calculation swept publication
→ PASS

non-candidate singleton publication
→ PASS

non-candidate multi-lineage publication
→ explicit FAIL

PREDICATE generic publication
→ explicit FAIL

Eligibility/Entry/Exit signal publication
→ PASS
```

Also preserve fresh-process determinism:

```text
persisted exact Specification
→ fresh resolver
→ same admitted composition / same identities
```

Run relevant Result/Artifact/Query regressions to prove no leak or schema drift.

### Stage 0 Exit Gate

Do not proceed until:

```text
Scientific Publication Admission = CLOSED
```

# 10. Temporary Research Draft

A temporary incomplete Browser edit model is justified because form state can be incomplete.

Use a small feature-local Draft model.

Conceptually:

```ts
interface ResearchDraft {
    dataset: DatasetDraft;
    calculations: readonly CalculationDraft[];
    eligibility: ExpressionDraft | null;
    entry: ExpressionDraft | null;
    exit: ExpressionDraft | null;
    targets: readonly TargetDraft[];
    statistics: readonly StatisticsDraft[];

```

The exact types should follow current Web coding style.

Hard rules:

```text
ResearchDraft has no semantic fingerprint.
ResearchDraft is not a server contract.
ResearchDraft cannot be submitted as a Run.
ResearchDraft is not persisted in PostgreSQL.
ResearchDraft is not a second Research Definition.
```

Prefer a feature-local `useReducer` if current form complexity makes it clearer than many `useState` calls.

Do not add a global state library.

- ensure required UI fields are complete enough to form the transport;
- convert form text into the existing strict scalar transport shape;

- calculate Definition fingerprints;
- expand sweeps;

- lower Predicate;
- construct Calculation Graphs;

Do not duplicate DTO schemas manually when existing generated/OpenAPI/Zod transport definitions can be reused safely.

## 13.1 Generic Calculation editor

Render parameter controls from authoritative catalog metadata:

- integer;
- decimal;
- boolean;
- enum;
- string;
- required/default/min/max where supplied.

## 13.2 instance_key


## 13.3 Fixed / Sweep


Do not implement:

- random search;
- Bayesian search;
- dependent sweep;
- conditional sweep;
- zip sweep.

The Browser may show a non-authoritative estimated combination count for UX, clearly derived from local edits.

The authoritative `candidate_count` comes from server Resolution.

## 13.4 Published Outputs

Published outputs must come from Catalog outputs.

Downstream Builder references use formal logical Definition-local references, not resolved internal fingerprints.

Do not expose internal node/calculation fingerprints as ordinary authoring input.

# 18. Draft revision and stale Resolution protection

Maintain a simple local monotonic edit revision, e.g.:

```text
draftRevision: number
```

Every semantic Draft edit increments it.

A successful Resolution records the revision it resolved.

Run is allowed only if:

```text
resolution is RESOLVED
AND
resolvedRevision == current draftRevision
```

Important:

`draftRevision` is only a browser concurrency/staleness guard.

It is **not** semantic identity.

Do not hash the Draft in the Browser.

Authoritative fingerprints come from the server.

---

# 19. Concurrent Resolve race handling

Protect this case:

```text
Resolve D1 starts
↓
user edits → D2
↓
D1 response arrives later
```

The D1 response must not become the authoritative current Resolution.

Use:

```text
AbortController where practical
+
captured draft revision check
```

A stale response must be ignored.

Tests must prove this.

# 24. Idempotent Run submission

Recommended browser source:

```text

```

Follow current branded ID parsing/types if present.

Critical behavior:

```text

→ create new key
```

Do not generate a new key on each automatic retry.

Do not treat the Idempotency Key as Research semantic identity.

No new durable database table is required.

# 44. Final implementation principle

The purpose of P8.4.3 is not to maximize frontend code.

The purpose is to close the smallest correct product loop:

```text
Research Intent
→ Definition
→ Resolve
→ Exact Specification
→ Durable Run
→ Exact Result
```

while preserving:

```text
one semantic path
one authority per fact
deterministic identity
fail-closed ambiguity
thin API adapters
browser as control/presentation only
clean feature boundaries
minimal necessary abstractions
```

If a proposed implementation makes the system more flexible but weakens uniqueness, authority ownership, determinism, auditability, or fresh-process reconstruction, reject that implementation and choose the simpler deterministic design.
