# 4. P9.K.1 Goal

Implement one long-lived **Product Kernel Host** with an explicit lifecycle:

```text
CREATED
   ↓
BOOTING
   ↓
VERIFYING
   ↓
RECOVERING
   ↓
READY
   ↓
DRAINING
   ↓
STOPPED
```

Unrecoverable startup/runtime lifecycle failure:

```text
FAILED
```

The result must establish a single authoritative product lifecycle state and make product mutation admission impossible before `READY`.

The host must compose existing narrow capabilities rather than duplicate domain logic.

# 5. Core First-Principles Invariants

These invariants are mandatory.

## INV-K1-01 — One Product Lifecycle Authority

There must be one authoritative Product Kernel lifecycle state.

Subsystem readiness checks may exist, but they are inputs to Product Kernel verification.

They must not become competing product lifecycle truths.

Correct:

```text
PostgreSQL schema verification
Research deployment verification
registry verification
required roots verification
recovery verification
        ↓
OnlyAlpha Kernel Host
        ↓
READY
```

Incorrect:

```text
API-ready
Research-ready
Engine-ready
Strategy-ready
Kernel-ready

all independently deciding whether mutation is allowed
```

---

## INV-K1-02 — Deterministic Legal Transition Graph

Lifecycle state must not be arbitrary writable data.

Do not implement:

```python
kernel.state = OnlyKernelState.READY
```

as an unrestricted operation.

There must be one explicit transition authority with a closed legal graph.

At minimum:

```text
CREATED    → BOOTING
BOOTING    → VERIFYING
VERIFYING  → RECOVERING
RECOVERING → READY
READY      → DRAINING
DRAINING   → STOPPED
```

Failure transitions must be explicit and deterministic.

Illegal examples must fail closed:

```text
CREATED → READY
VERIFYING → READY
FAILED → READY
STOPPED → READY
READY → BOOTING
```

Do not silently normalize illegal transitions.

---

## INV-K1-03 — READY Is the Product Mutation Gate

The product-level mutation admission rule must be:

```text
state == READY
→ mutation may be admitted

state != READY
→ mutation rejected
```

This applies to:

```text
CREATED
BOOTING
VERIFYING
RECOVERING
DRAINING
STOPPED
FAILED
```

The host should expose a narrow, explicit mutation-readiness assertion/capability.

Do not invent a generic authorization/RBAC framework.

Do not implement route-specific readiness truths.

---

## INV-K1-04 — VERIFYING Proves; It Does Not Repair

`VERIFYING` may perform read-only or verification operations such as:

```text
configuration validity
PostgreSQL server compatibility
PostgreSQL schema compatibility
semantic namespace compatibility
registry uniqueness
semantic authority compatibility
deployment coherence
required path/root availability
```

`VERIFYING` must not:

```text
run production schema migrations
repair semantic state
rewrite manifests
invent missing Strategy truth
invent Research truth
delete corrupt state
auto-initialize incompatible namespaces
silently alter durable state to make startup pass
```

Application startup must remain fail-closed.

Production startup must not own migration capability merely because it only calls read methods.

Prefer narrow read-only verification capabilities.

---

## INV-K1-05 — Recovery Reconstructs From Existing Authorities

Recovery must follow:

```text
Durable Authority
+
Deterministic Recovery Rule
→ Reconstructed Operational State
```

Do not establish a second aggregate truth source.

Forbidden patterns include:

```text
pickle whole OnlyAlphaKernel object
kernel_state.json as product authority
opaque serialized in-memory kernel snapshot as authoritative recovery state
```

Existing state ownership remains:

```text
Immutable Semantic State
→ immutable/content-addressed stores

Operational Lifecycle
→ PostgreSQL where designed

Runtime Mutable State
→ deterministic in-memory state
  + explicit durable/checkpoint evidence where required

External Execution State
→ broker/venue authority
  + canonical local reconciliation evidence
```

P9.K.1 coordinates recovery. It does not redesign every subsystem recovery model.

---

## INV-K1-06 — Product Kernel Must Not Become a God Object

The Product Kernel Host owns orchestration/lifecycle, not all business semantics.

Do not create:

```python
class OnlyAlphaKernel:
    def create_research(...): ...
    def freeze_strategy(...): ...
    def promote_strategy(...): ...
    def calculate(...): ...
    def place_order(...): ...
    def update_position(...): ...
```

K1 must preserve existing authorities.

The intended shape is:

```text
OnlyAlphaKernelHost
    ├── lifecycle
    ├── verification coordination
    ├── recovery coordination
    ├── readiness/mutation gate
    └── lifecycle-owned resource coordination

Research authority
Strategy authority
Engine
Persistence authority
Runtime authority
...
remain responsible for their semantics
```

---

## INV-K1-07 — Product Kernel != Trading Kernel

Do not merge these concepts.

Keep:

```text

```

as the Trading Semantic Kernel location.

New Product Kernel code lives under:

```text

```

The Product Kernel may eventually orchestrate Runtimes that contain the Trading Kernel.

It must not absorb trading calculations or trading decision semantics.

---

## INV-K1-08 — Explicit Dependency Injection

Use explicit constructor-injected narrow capabilities.

Prefer:

```text
plain Python protocols/callables/narrow services
explicit ordered tuples
explicit methods
```

Avoid:

```text
service locator
dependency injection framework
generic IoC container
dynamic service registry
generic command bus
runtime reflection-based dependency resolution
```

This is a modular monolith.

Explicit dependencies are preferred over generalized infrastructure abstractions.

---

## INV-K1-09 — Deterministic Startup Ordering

Startup ordering must be explicit.

Reference lifecycle:

```text
CREATED
↓
BOOTING
↓
VERIFYING
    1. configuration
    2. PostgreSQL compatibility
    3. semantic namespace
    4. implementation registry uniqueness
    5. configured semantic authorities
↓
RECOVERING
    1. unfinished durable lifecycle
    2. required current reconciliation
↓
READY
```

The exact concrete verification set must come from current configured product scope.

Do not let ordering depend on:

```text
set iteration
filesystem iteration
unordered plugin discovery
incidental dict construction
reflection
module import accident
```

If multiple verification/recovery steps are modeled as collections, use explicit ordered immutable sequences.

---

## INV-K1-10 — Failure Is Fail-Closed and Explainable

Verification or recovery failure must transition the Product Kernel to `FAILED`.

Examples:

```text
schema incompatible
→ FAILED

semantic namespace mismatch
→ FAILED

registry ambiguity
→ FAILED

unrecoverable durable state
→ FAILED
```

Do not:

```text
continue degraded
silently ignore
retry forever
auto-migrate
auto-repair
invent fallback authority
```

Failure evidence should identify the phase and stable reason without leaking unnecessary low-level secrets.

Do not create a large error taxonomy unless required.

---

## INV-K1-11 — Liveness and Readiness Are Different Facts

Do not equate process-alive with product-ready.

Reference semantics:

```text
State        Live?     Ready?
--------------------------------
CREATED      yes       no
BOOTING      yes       no
VERIFYING    yes       no
RECOVERING   yes       no
READY        yes       yes
DRAINING     yes       no
STOPPED      no        no
FAILED       no/yes*   no
```

`FAILED` liveness should match the actual process/host semantics selected by implementation, but it must never be ready.

There must be one deterministic readiness projection:

```text
READY state → ready
all other states → not ready
```

---

## INV-K1-12 — DRAINING Closes Mutation Admission First

Transition:

```text
READY → DRAINING
```

must close new product mutation admission before shutting down owned resources.

Correct conceptual ordering:

```text
state = DRAINING
→ reject new mutation
→ drain/close owned resources
→ STOPPED
```

Avoid a race window where resources stop while mutation is still admitted.

K1 does not need to solve every future concurrent runtime race, but the lifecycle contract must be correct.


Do not add restart semantics unless current design explicitly requires them.

Do not optimize for the number of abstractions created.

```text
ONE product lifecycle authority
+
ONE legal deterministic state transition graph
+
ONE READY mutation gate
+
recovery from existing authorities
+
ZERO duplicated business truth
```

P9.K.1 should make the system more structurally inevitable, not more generic.

If an abstraction does not directly strengthen one of those properties, do not add it.
