# 1. OnlyAlpha 工程原则

本阶段所有工程决策按照：

> **正确性 > 架构一致性 > 可验证性 > 可恢复性 > 可维护性 > 性能 > 自动化程度**

进行权衡。

不能为了：

- 少写代码
- 快速完成
- 保持旧 API 表面不变
- 降低 Agent 实现难度
- 过早优化
- 过早实现 Research

而破坏更高优先级目标。

P7.0 是 P7 Research Platform 的基础层。

它不是简单的目录整理，也不是简单把几个 `.py` 文件移动到 `packages/`。

# 2. P7 总体上下文

OnlyAlpha 后续 P7 的长期目标是建立：

```text
Historical Data
      ↓
Dataset Snapshot
      ↓
Indicator / Factor Definition
      ↓
Calculation Graph
      ↓
Calculation Store
      ↓
Vectorized Research
      ↓
Research Result / Visualization
      ↓
Alpha Candidate
      ↓
Backtest
      ↓
SIM
      ↓
LIVE
```

未来还会进一步支持：

```text
Human
Web
LLM
ML Factor Mining
```

因此 P7.0 必须先解决一个根本问题：

> **OnlyAlpha 如何唯一、稳定、与 Runtime 无关地描述一个 Indicator、Factor 以及它们组成的 Calculation Graph？**

P7.0 建立的是整个系统未来的：

> **Calculation Definition Authority**

# 3. P7.0 的核心目标

P7.0 必须实现：

```text
Config / Web / LLM
        ↓
Canonical Calculation Definition
        ↓
Stable Semantic Identity
        ↓
Stable Fingerprint
        ↓
Calculation Graph
        ↓
Registry
        ↓
Backend Implementation
        ↓
Runtime
```

核心原则：

> **Definition 唯一，Execution Backend 可以不同。**

例如：

```text
EMA(close, period=20, semantic_version=1)
```

在 OnlyAlpha 中只能存在一种正式计算语义。

未来允许：

```text
EMA@1
├── Research Vectorized Backend
└── Trading Incremental Backend
```

但是不能变成：

```text
Research EMA
Trading EMA
```

两套互相独立的定义体系。

因此：

> Calculation Backend may differ.  
> Calculation Semantics must remain identical.

# 5. 最重要的架构边界

必须形成：

```text
src/onlyalpha
    定义：
        什么是 Indicator
        什么是 Factor
        什么是 Calculation Definition
        什么是 Calculation Graph
        什么是 Backend Contract
        什么是 Registry
        什么是 Semantic Identity
        什么是 Fingerprint

packages/...indicators
    提供：
        有哪些具体 Indicator 算法

packages/...factors
    提供：
        有哪些具体 Factor 算法
```

即：

> **Core owns semantics. Plugin owns algorithms.**

依赖方向只能：

```text
onlyalpha-plugin-indicators
            ↓
       onlyalpha

onlyalpha-plugin-factors
            ↓
       onlyalpha
```

禁止：

```text
onlyalpha
    ↓
concrete indicator plugin

onlyalpha
    ↓
concrete factor plugin
```

Core 不能知道：

```text
EMA
RSI
ATR
Bollinger
MomentumFactor
...
```

这些 concrete implementation 的 Python class。

Core 只应该知道：

```text
Indicator Definition
Factor Definition
Calculation Graph
Backend Protocol
Registry Protocol
Semantic Contract
```

# 6. Definition 与 Runtime Instance 必须分离

P7.0 必须明确区分：

```text
“这个计算是什么”
```

和：

```text
“这个计算现在怎么执行”
```

Canonical Definition 必须：

- immutable
- serializable
- deterministic
- canonicalizable
- content-addressable
- Runtime-independent

Definition 中禁止包含：

```text
Cluster
Runtime Context
Account
Broker
Position
Order
Reservation
Transaction
mutable deque
rolling mutable state
checkpoint state
process identity
Python object identity
```

Trading Runtime Instance 可以拥有 mutable state。

Canonical Definition 不能拥有。

# 7. Canonical Indicator Definition

根据当前 Repository 设计正式 Indicator Definition。

可以采用类似概念：

```python
OnlyIndicatorDefinition(
    type_id="onlyalpha.indicator.ema",
    semantic_version="1",
    parameters={
        "period": 20,
    },
    inputs={
        "value": "bar.close",
    },
)
```

但不要机械照抄这个 API。

最终模型应从第一性原理表达完整的 Indicator semantic definition。

至少考虑：

```text
type_id
semantic_version

parameters

input contract
input bindings

output schema

warmup semantics
missing-value semantics
timestamp semantics
numeric / precision semantics
```

必要时允许：

```text
extensions
```

但 extensions 必须受控，不能成为绕过正式 schema 的任意字典垃圾桶。

---

# 8. Stable `type_id`

Algorithm identity 不能依赖 Python class path。

禁止把长期计算身份建立在：

```text
package.module.ClassName
```

之上。

因为未来：

```text
package rename
module move
class rename
code organization refactor
```

不应该自动改变计算业务身份。

使用稳定业务 type identifier，例如概念上：

```text
onlyalpha.indicator.ema
onlyalpha.indicator.rsi
```

具体 naming convention 与当前 Repository 保持一致。

---

# 9. Semantic Version

P7.0 必须建立：

```text
type_id + semantic_version
```

作为正式算法语义身份的一部分。

例如：

```text
EMA@1
```

如果修复 bug 导致数学结果变化，或者以下计算语义发生变化：

```text
initialization
warmup
missing handling
precision
timestamp semantics
output semantics
algorithm formula
```

不能偷偷继续声明自己是：

```text
EMA@1
```

必须升级 semantic version，例如：

```text
EMA@2
```

旧 version 必须仍然可以被历史 Artifact / Candidate / Run 正确识别。

---

# 10. Parameter Schema

不要仅使用：

```python
dict[str, Any]
```

作为长期 Parameter Contract。

Indicator / Factor implementation 必须能够声明稳定的 parameter schema。

例如：

```text
period:
    type = integer
    required = true
    minimum = 1
```

Parameter Schema 将来需要同时服务：

```text
Validation
Config normalization
Fingerprint
Research parameter sweep
Web form
LLM tool schema
Documentation
```

必须明确：

```text
required
optional
default
type
allowed range
enum values
normalization rules
```

默认值处理必须 deterministic。

---

# 11. Config != Canonical Definition

当前已有：

```text
OnlyIndicatorSpec
OnlyFactorConfig
OnlyIndicatorSpecConfig
...
```

不要因为名称类似就直接假定它们已经是永久 Canonical Domain Definition。

必须重新分析它们的职责。

长期推荐：

```text
YAML / Python Config / Web / LLM
                ↓
          Config DTO
                ↓
        Normalize / Resolve
                ↓
       Canonical Definition
                ↓
           Fingerprint
```

即：

> Config 是输入格式。  
> Canonical Definition 才是 Calculation Identity Authority。

如果当前 `OnlyIndicatorSpec` 已经足够接近 canonical definition，应优先演进和复用，而不是无意义重写。

但不要为了兼容旧名字继续保留两个平行 authority。

---

# 12. Resolve Defaults Before Fingerprint

必须明确默认参数语义。

例如：

```text
EMA
period omitted
default = 20
```

与：

```text
EMA
period explicitly = 20
```

如果最终计算语义相同，则 normalize 后应产生同一个 Canonical Definition 和同一个 fingerprint。

推荐：

```text
Config
  ↓
resolve defaults
  ↓
normalize
  ↓
Canonical DTO
  ↓
fingerprint
```

---

# 13. Input Contract 与 Input Binding

不要让 Indicator 内部隐式假设：

```text
输入一定是 bar.close
```

算法声明它需要什么输入。

Definition 决定这个输入绑定到什么数据。

例如：

```text
EMA
input:
    value: numeric series
```

Definition：

```text
value -> bar.close
```

未来也可能：

```text
value -> bar.volume
value -> indicator.output
value -> factor.output
```

必须为未来 Calculation DAG 的组合能力建立基础。

---

# 14. Output Schema

Indicator / Factor output 不应该只是隐式 Python return value。

必须有稳定 Output Contract。

至少考虑：

```text
output field name
data type
nullable
semantic type
dimensions
unit（如适用）
```

不能假设一个 Indicator 只能有一个 scalar output。

例如：

```text
EMA:
    value

Bollinger:
    middle
    upper
    lower
```

这是未来：

```text
Arrow
Parquet
Calculation Store
ML Feature Matrix
Web Visualization
```

共同需要的结构信息。

---

# 15. Warmup Semantics

Warmup 是正式计算语义。

必须显式描述：

```text
minimum observations
ready condition
pre-ready output behavior
initialization method
```

例如 SMA20：

```text
20 个 observation 前输出什么？
第几个 observation ready？
```

EMA：

```text
first-value seed?
SMA seed?
其他初始化方式？
```

这些不能由 Research / Trading backend 各自决定。

优先忠实冻结当前 Trading implementation 的实际行为。

P7.0 不要趁架构迁移改变现有数学语义。

---

# 16. Missing Value Semantics

必须明确处理：

```text
NaN
None
missing bar
invalid input
```

的计算语义。

例如：

```text
SKIP
PROPAGATE
RESET
FAIL
```

具体算法可以有不同 policy，但 policy 必须成为正式 semantic contract。

禁止未来出现：

```text
Research 使用某库默认 skipna
Trading 使用自己的逻辑
```

然后两边仍然都声明实现相同 semantic version。

---

# 17. Timestamp Semantics

P7.0 必须至少建立计算节点时间语义的正式表达。

需要能够区分并根据当前 Domain 统一：

```text
bar open time
bar close time
event time
observation time
availability time
```

Calculation output 不能拥有隐含 timestamp 语义。

这是未来防止：

```text
look-ahead bias
```

的重要基础。

P7.0 不要求解决完整 Point-in-Time Research，但必须保证 Definition Contract 为此留出正确边界。

---

# 18. Numeric / Precision Semantics

检查当前 Indicator / Factor 对：

```text
Decimal
float
rounding
precision
NaN
Infinity
```

的处理。

不要在 P7.0 中随意改数学行为。

如果 precision 是算法语义的一部分，必须纳入 semantic contract。

如果 precision 是整个 OnlyAlpha 的统一 Domain invariant，则复用现有 authority，不重复设计。

---

# 19. Canonical Factor Definition

Factor 也必须拥有独立于 Runtime 的 Canonical Definition。

至少表达：

```text
type_id
semantic_version

parameters

input references
indicator dependencies
factor dependencies

factor kind
output schema
semantic policies
```

需要继续保留正式区别：

```text
TIME_SERIES
CROSS_SECTION
```

因为二者计算语义不同。

但 P7.0 不要求完整实现未来 Cross-sectional Research Engine。

---

# 20. Factor Definition 不得绑定 Trading Cluster

检查当前 Factor 是否存在类似：

```text
_only_cluster_bind(...)
on_initialize()
on_start()
on_stop()
on_bar()
on_cross_section()
```

这些 Runtime / lifecycle 能力。

必须把：

```text
Factor Definition
```

和：

```text
Trading Factor Runtime Instance
```

明确拆开。

Definition 不认识：

```text
Cluster
Runtime
Strategy Context
Account
Broker
Order
Position
```

现有 Trading runtime lifecycle 可以作为 Trading Backend / Runtime Instance 的职责继续存在。

不要破坏当前 Backtest/SIM 行为。

---

# 21. Factor 不得直接依赖 Concrete Indicator Implementation

禁止形成：

```python
from onlyalpha_plugin_indicators import EMA

class SomeFactor:
    ...
```

这种 concrete implementation coupling。

Factor Definition 应引用：

```text
Indicator Definition
Calculation Node Reference
```

实际 implementation 由 Registry / compiler / backend resolver 解决。

Plugin package 之间如果需要依赖，也必须保持语义层引用和 implementation 层解耦。

# 22. Calculation Graph Definition

P7.0 必须建立统一 Calculation Graph 的基础模型。

目标：

```text
close
  │
  ├──────────────┐
  ▼              ▼
EMA20           EMA60
  │              │
  └───────┬──────┘
          ▼
        ratio
          │
          ▼
      Factor X
```

至少需要等价于：

```text
CalculationGraphDefinition
CalculationNodeDefinition
```

的概念。

具体类名结合 Repository 决定。

---

# 23. Calculation Graph 必须是 Canonical DAG

Graph 应满足：

```text
acyclic
explicit dependencies
deterministic
serializable
canonicalizable
fingerprintable
```

必须能够检测：

```text
missing dependency
duplicate semantic node
cycle
invalid output reference
incompatible input/output schema
```

Graph 的 JSON / dict 插入顺序不同不能导致 semantic identity 随意变化。

---

# 24. Human Alias != Semantic Identity

非常重要。

例如：

```text
ema_fast
```

和：

```text
short_ema
```

如果实际上都是：

```text
EMA(close, period=20, version=1)
```

则人类 alias 可以不同，但 semantic Calculation Node identity 应相同。

不要把：

```text
display name
config key
human alias
description
```

无条件纳入 semantic fingerprint。

必须明确区分：

```text
presentation identity
semantic identity
```

这样后续 Calculation Store 才能复用公共节点。

---

# 25. Canonical Serialization

Fingerprint 之前必须建立 canonical serialization。

禁止：

```python
hash(str(obj))
```

或其他依赖 Python runtime 表示的方式。

需要：

```text
Definition
    ↓
Canonical DTO
    ↓
Canonical Serialization
    ↓
Stable Hash
```

明确处理：

```text
dict ordering
list ordering
enum representation
Decimal representation
numeric representation
None/null
default values
optional fields
schema version
dependency representation
```

优先复用 OnlyAlpha 当前已有的 canonical hashing / content fingerprint 模式。

不要在 P7.0 创建第二套与 Historical Cache / Artifact 完全无关的 hash philosophy。

---

# 26. Definition Fingerprint

P7.0 需要建立稳定 Definition Fingerprint。

Fingerprint 应建立在 semantic canonical content 上。

应考虑包含：

```text
type_id
semantic_version
resolved parameters
input bindings
dependency identities
semantic policies
output contract
```

不应该包含：

```text
absolute filesystem path
Python object id
process id
created_at
wall-clock timestamp
random UUID
human description
display alias
source code file location
```

除非 Repository 当前存在非常明确且合理的不同 identity 规则。

# 27. Registry

Plugin 化以后必须建立统一 Registry / Resolver。

目标概念：

```text
type_id
+
semantic_version
+
backend kind
        ↓
implementation
```

例如：

```text
onlyalpha.indicator.ema@1

TRADING -> available
RESEARCH -> unavailable
```

P7.0 当前只需要保证现有 Trading Backend。

不要为了形式完整实现假的 Research Backend。

未来 P7.x 再加入：

```text
RESEARCH -> VectorizedEMA
```

---

# 28. Registry 必须 Fail Closed

禁止：

```text
请求 EMA@1
找不到
自动使用 EMA@2
```

禁止：

```text
请求 RESEARCH backend
找不到
偷偷 fallback 到另一个实现
```

禁止：

```text
duplicate registration silently overrides
```

必须明确失败。

至少测试：

```text
unknown type_id
unknown semantic_version
unsupported backend
duplicate registration
ambiguous registration
invalid implementation
```

# 29. Plugin Discovery 不要过度设计

P7.0 当前目标：

```text

+
stable registration contract
+
deterministic discovery/bootstrap
```

即可。

如果当前 Repository 已经使用 Python entry point 或成熟 plugin discovery 机制，优先复用。

```text
hot reload
runtime pip install

dynamic uninstall
complex dependency solver
process sandbox
```

这些不是 P7.0 根本问题。

# 30. Backend Contract

不要强迫 Research 和 Trading 使用完全相同的方法形状。

它们执行模型天然不同。

允许未来：

```text
Trading Backend
    update(...)
    snapshot(...)
    restore(...)

Research Backend
    compute_batch(...)
```

P7.0 应统一：

```text
Definition
Input semantics
Output semantics
Algorithm semantic version
```

而不是机械统一执行 API。

建议建立适合当前设计的 backend protocol hierarchy。

# 34. 不要创建重复 Authority

```text
      ↓

      ↓
Canonical Definition
      ↓
Calculation Graph
      ↓
Registry
      ↓
Trading Backend
      ↓

```

但外部 Trading behavior 必须保持。

尤其：

```text

```

不能因为 P7.0 架构迁移改变运行结果。

---

# 36. 必须保持现有 Trading 数学行为
