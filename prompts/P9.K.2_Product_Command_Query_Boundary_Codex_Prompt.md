# 1. Task Purpose

P9.K.2 establishes the **single product-level typed intent boundary** for OnlyAlpha.

The core problem is not “there is no command bus”.

The actual problem is:

> external/product-level code must not reach multiple domain/application mutation surfaces directly.

Without K2, the product can gradually become:

```text
HTTP Route ───────→ Research Service

CLI ──────────────→ Engine

SDK ──────────────→ Strategy Service

Agent ────────────→ Promotion Service

future Web ───────→ Runtime
```

Even if every individual service is correct, the product would still have multiple mutation entrances with different admission/idempotency/audit rules.

K2 must converge that into:

```text
Product Mutation Intent
        ↓
one Product Command Boundary
        ↓
one exact handler
        ↓
one existing authoritative Application/Domain authority
```

and:

```text
Product Observation Intent
        ↓
one Product Query Boundary
        ↓
one exact read-only handler
        ↓
one authoritative fact/projection
```

# 2. Governing First-Principles Rules

All implementation decisions must follow these rules.

## 2.1 One fact → one authority

Do not move business truth into the Dispatcher.

Dispatcher does not become:

```text
Research authority
Strategy authority
Promotion authority
Runtime authority
Persistence authority
```

The existing authorities remain authoritative.

## 2.2 One mutation intent → one Command type → one Handler

For every supported Product Command:

```text
CommandType
→ exactly one canonical handler
```

No duplicate binding.
No fallback binding.
No dynamic ambiguity.

## 2.3 One observation intent → one Query type → one Handler

For every supported Product Query:

```text
QueryType
→ exactly one canonical read-only handler
```

Queries must never create hidden mutation.

## 2.4 One Product mutation gate

Every Product Command must cross:

```text
OnlyAlphaKernelHost.assert_mutation_ready()
```

before any mutation-capable handler is invoked.

Do not create:

```text
DispatcherReady
CommandReady
ResearchReady
ApplicationReady
```

as competing mutation-admission authorities.

K1 already established the unique Product lifecycle authority.

## 2.5 Unknown or ambiguous state → fail closed

Unknown Command:

```text
FAIL
```

Unknown Query:

```text
FAIL
```

Duplicate binding:

```text
FAIL at construction
```

Illegal dynamic registration:

```text
not supported
```

Never silently fallback.

## 2.6 Determinism over convenience

Dispatch semantics must not depend on:

```text
import order
dict insertion accident
set iteration
filesystem order
module discovery
subclass MRO
plugin scanning
reflection
string routing
```

Same exact type + same frozen binding topology must always select the same handler.

## 2.7 Minimum sufficient mechanism

Do not introduce:

```text
generic CQRS framework
generic message bus
event sourcing framework
service locator
IoC container
runtime plugin registry
reflection-based dispatcher
Kafka
NATS
Redis event bus
```

K2 needs a small structural boundary, not an infrastructure platform.

# 5. Command Semantics

A Product Command is:

> a request for an authoritative transition.

Examples:

```text
CreateResearchRun
CancelResearchRun
FreezeStrategy
PromoteStrategy
future StartBacktest
future StopBacktest
future StartSimulation
future StopSimulation
future CreateDeployment
```

A Product Command must not encode fabricated final state.

Forbidden:

```text
SetResearchState(CANCELLED)
SetStrategyStage(LIVE_ELIGIBLE)
PatchStrategy({...})
UpdateRuntimeState(...)
```

Preferred semantics:

```text
CancelResearchRun(run_id)
PromoteStrategy(strategy_fingerprint, to_stage, exact evidence...)
```

The authoritative Application/Domain service decides whether the transition is legal.

---

# 6. Query Semantics

A Product Query is:

> a read request over verified facts or projections that causes no hidden state transition.

Examples:

```text
GetKernelStatus
GetResearchRun
ListResearchRuns
future GetStrategy
future GetPromotionHistory
future GetBacktest
future GetSimulation
```

Query handlers must not:

```text
repair
refresh-and-write
reconcile
initialize
promote
freeze
cancel
migrate
```

unless a later task deliberately reclassifies such operation as a Command.

Command values should be immutable.

```python

```

A Command must contain explicit intent and exact references.

Do not let dispatch semantics depend on:

```text

working directory

```

Business services may already own explicit clocks/ID authorities; preserve those.

# 10. Exact-Type Dispatch

Command resolution must use exact registered type.

Conceptually:

```python
handler = handlers.get(type(command))
```

Do not use:

```text
isinstance fallback
base-class fallback
subclass matching
MRO nearest match
string command name
reflection-based handler discovery
```

Required behavior:

```text
exact registered type
→ exact handler

unregistered exact type
→ fail closed
```

This protects deterministic semantics against inheritance/refactor drift.

---

# 11. Duplicate Binding Rule

At Dispatcher construction:

```text
same Command type bound twice
→ fail closed
```

Do not:

```text
last registration wins
first registration wins silently
```

The binding topology must be validated once and then frozen.

---

# 12. No Runtime Registration

Do not expose:

```python
dispatcher.register(...)
dispatcher.unregister(...)
dispatcher.replace_handler(...)
```

The legal topology is:

```text
Composition Root
→ construct complete binding tuple
→ validate uniqueness
→ create immutable Dispatcher
→ use
```

Runtime mutation of the handler graph is forbidden.

---

# 13. Command Dispatch Algorithm

The core logic should remain conceptually equivalent to:

```python
def dispatch(command):
    kernel.assert_mutation_ready()

    handler = exact_handlers.get(type(command))
    if handler is None:
        raise UnsupportedProductCommand(...)

    return handler(command)
```

Ordering is mandatory:

```text
1. Kernel READY assertion
2. exact-type handler lookup
3. canonical handler invocation
4. return existing authoritative outcome
```

No handler invocation may happen before READY admission succeeds.

```text
26. confirm DB/OpenAPI/P9.0 semantic deltas are zero
27. update docs/evidence
28. bind final status to immutable revision
29. declare K2 DONE / VERIFIED only if BLOCKER=0 and MAJOR=0
30. only then mark K3 IMPLEMENTATION READY
```

# 49. Final Engineering Principle

Do not optimize for a generic dispatcher abstraction.

Optimize for these three invariants:

```text
One mutation intent
→ one Product Command type
→ one exact handler
→ one existing authoritative transition path
```

```text
One observation intent
→ one Product Query type
→ one exact read-only handler
→ one authoritative fact/projection
```

```text
Every Product Command
→ crosses the one Kernel READY mutation gate
```

The correct K2 implementation should be small.

Its value comes from making illegal product operation paths structurally harder, not from adding framework complexity.
