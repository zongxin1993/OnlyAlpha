# 一、总原则

必须从第一性原理出发，先识别 P8.3 真正需要解决的问题，再实施代码。

P8.3 不是简单增加几个 FastAPI 路由，也不是围绕 PostgreSQL Run Store 做一层 CRUD 包装。

它必须解决以下真实问题：

1. API 返回提交成功时，Research Run 必须已经完成 PostgreSQL 持久化。
2. API 或客户端在持久化成功后发生网络中断，重试不能创建重复 Run。
3. API、Worker、浏览器重启后，Run 状态仍然可以可靠恢复和查询。
4. 取消命令必须正确处理与 Worker claim、execution completion 的并发竞争。
5. Research Run、Attempt、Artifact、Specification 各自只有一个正式权威。
6. HTTP 层不能重新实现领域语义，不能形成第二套 Specification 或 Run 状态机。
7. P8.3 必须为 P8.4 Web Workbench 提供稳定控制契约，但不能提前盲目实现 P8.4 的产品功能。

工程优先级：

1. 正确性
2. 架构一致性
3. 可验证性
4. 可恢复性
5. 可维护性
6. 性能
7. 自动化和开发效率

禁止以“代码少”“开发快”“接口看起来完整”为理由破坏权威边界。

# 四、必须维护的权威边界

## 4.1 Specification 权威

`OnlyResearchSpecification` 及其 resolver 是 Research Specification 的唯一语义权威。

HTTP/Pydantic 层只负责：

* 请求 envelope。
* JSON transport。
* 基础类型和字段存在性。
* 调用领域解析。
* 映射稳定错误。

禁止在 API 层复制一套完整 Specification 语义模型。

推荐请求 envelope：

```python
class SubmitResearchRunRequest(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

    specification: dict[str, JsonValue]
```

随后必须调用领域入口，例如：

```python
OnlyResearchSpecification.from_dict(...)
```

具体名称以当前代码为准。

Specification 的版本演进必须继续以 `schema_version` 为判别依据。

## 4.2 Run 状态权威

现有 `ResearchRun` 聚合是状态和状态迁移的唯一权威。

API 和 Application Service 不得自行构造非法状态，也不得直接拼装数据库 UPDATE 绕过领域迁移。

必须复用或扩展现有领域 successor/transition 机制。

终态必须保持不可变。

## 4.3 Attempt、Lease 和 Fencing 权威

P8.2 Execution Store 是：

* Worker claim。
* Attempt。
* Lease。
* Fence。
* execution completion/failure。

的唯一权威。

Command API 不得：

* 创建 Attempt。
* 续租。
* 提交 execution completion。
* 绕过 fence。
* 伪造 Worker 结果。
* 强制将正在执行的 Run 修改为 `CANCELLED`。

## 4.4 Artifact 权威

Command API 只返回：

* `result_ref`
* `artifact_ref`
* 必要的运行元数据

不得返回：

* 统计内容。
* Series 内容。
* Calculation Result 内容。
* Artifact 文档内容。

这些内容必须继续由 Artifact Query API 提供。

## 4.5 Engine 权威

API 进程不得启动或替代 Worker/OnlyEngine。

没有 Worker 时，新提交的 Run 保持 `QUEUED` 是正确行为。

# 六、Admission Service 调整

检查当前 Admission Service 是否同时完成了：

```text
解析/验证
→ resolve
→ Dataset verified load
→ 创建 Run
→ store commit
```

P8.3 需要把“准备一个可提交的 Run”和“幂等原子持久化”正确分开。

推荐语义：

```text
Command Service
    ↓
检查 submission replay
    ↓
Admission/Preparation
    ↓
确定性解析和 Dataset 验证
    ↓
构造 QUEUED Run
    ↓
原子写入 Run + Submission
```

不要简单在当前 `admission.submit()` 外面增加 HTTP 路由，否则无法可靠实现提交幂等性。

同时检查当前 Admission 错误是否被统一包装成过于粗糙的异常。

HTTP 层需要区分：

* Specification 非法。
* Dataset 不存在。
* Dataset 损坏。
* Calculation/Registry resolution 失败。
* PostgreSQL 不可用。
* 数据完整性错误。

应通过稳定的类型和错误码完成映射，不允许通过解析异常字符串分类。

# 七、提交幂等性设计

## 7.1 HTTP Idempotency Key

提交接口必须要求：

```http
Idempotency-Key: <canonical UUID4>
```

要求：

* 客户端生成。
* 严格 UUID4。
* 规范化后再持久化。
* 缺失或非法返回稳定 400 错误。
* 不允许任意无限长度字符串。

## 7.2 为什么不能按 Specification 全局去重

相同 Specification 可能被用户有意运行多次。

因此：

* 相同 Key + 相同命令：返回原 Run。
* 相同 Key + 不同命令：409。
* 不同 Key + 相同 Specification：创建不同 Run。

不得使用 `specification_fingerprint` 作为全局唯一约束。

## 7.3 PostgreSQL migration

在当前 migration authority 下新增下一条前向迁移。

若当前最新迁移仍为 M3，推荐：

```text
database/postgres/migrations/
0004_research_run_submission_and_read_projection.sql
```

推荐表结构：

```sql
CREATE TABLE research_run_submission (
    submission_key UUID PRIMARY KEY,
    command_fingerprint TEXT NOT NULL,
    run_id UUID NOT NULL UNIQUE
        REFERENCES research_run(run_id)
);
```

根据当前数据库约束风格补充：

* 指纹格式约束。
* 必要的外键行为。
* canonical value 约束。
* 注释或命名约束。

同时为 Run 列表增加确定性索引：

```sql
CREATE INDEX research_run_recent_order
ON research_run (queued_at DESC, run_id DESC);
```

不要修改已经发布的历史 migration。

必须更新：

* schema version authority。
* migration checksum authority。
* migration compatibility tests。
* architecture tests。

API 启动时只能检查 schema compatibility，不得自动执行 migration。

## 7.4 原子提交

第一次提交必须在同一数据库事务中完成：

1. 插入 `research_run`。
2. 插入 `research_run_submission`。
3. 提交事务。
4. 事务成功后才返回 HTTP 202。

如果 submission key 唯一约束竞争失败：

1. 整个失败事务回滚。
2. 不能残留孤儿 Run。
3. 重新加载已有 submission。
4. 比较 command fingerprint。
5. 相同则返回已有 Run。
6. 不同则返回 409。

不要依赖：

* 进程内锁。
* 全局 Python 字典。
* Redis。
* Serializable 事务。
* 分布式锁。

优先使用 PostgreSQL 事务、唯一约束和明确的冲突恢复。

## 7.5 Replay fast path

如果 submission key 已存在并且 command fingerprint 相同：

* 直接返回已有 Run。
* 不要重新执行 Dataset verified load。
* 不要重新访问 Calculation Registry。
* 不要重新运行环境相关 resolution。
* 不要创建新的 Run。

理由：

第一次提交可能已经成功，但响应丢失。后续环境变化不能破坏已提交命令的重放语义。

仍应完成计算 command fingerprint 所需的严格、无副作用规范化。

## 8.2 Run 列表

实现：

```http
GET /api/v2/research/runs?limit=50&cursor=...
```

列表项只返回轻量摘要，不返回完整 Specification。

固定排序：

```sql
ORDER BY queued_at DESC, run_id DESC
```

使用 keyset pagination：

```sql
WHERE (queued_at, run_id) < (:queued_at, :run_id)
ORDER BY queued_at DESC, run_id DESC
LIMIT :limit_plus_one
```

Cursor 必须：

* 包含确定排序所需的精确值。
* 使用稳定规范编码。
* 能严格校验。
* 拒绝未知字段。
* 拒绝错误版本。
* 拒绝非规范时间和 UUID。
* 不依赖进程内状态。

可以使用版本化 canonical JSON + base64url，但必须保持实现小而明确。

不要使用 offset pagination。

P8.3 第一版不要盲目增加全文搜索、统计聚合或复杂过滤语言。

# 九、取消设计

实现：

```http
POST /api/v2/research/runs/{run_id}/cancellation
```

请求无业务 body。

状态语义：

| 当前状态               | 持久化结果                 |
| ------------------ | --------------------- |
| `QUEUED`           | `CANCELLED`           |
| `RUNNING`          | `CANCEL_REQUESTED`    |
| `CANCEL_REQUESTED` | 幂等返回，不增加 revision     |
| `CANCELLED`        | 幂等返回                  |
| `COMPLETED`        | 409 terminal conflict |
| `FAILED`           | 409 terminal conflict |

取消成功表示“取消命令已经可靠提交”，不保证正在运行的计算立即停止。

## 9.1 CAS 竞争处理

使用现有 revision/state compare-and-swap。

正确流程：

```text
load Run
→ 根据当前状态构造领域 successor
→ CAS commit
→ 成功则返回
→ CAS 冲突则重新加载
→ 根据最新状态重新解释命令
```

必须处理：

### Cancel 与 claim 竞争

```text
API 读到 QUEUED
Worker 提交 QUEUED → RUNNING
API 提交 QUEUED → CANCELLED 失败
API reload
API 提交 RUNNING → CANCEL_REQUESTED
```

### Cancel 与完成竞争

```text
API 读到 RUNNING
Worker 提交 RUNNING → COMPLETED
API 提交 RUNNING → CANCEL_REQUESTED 失败
API reload
API 返回 terminal conflict
```

CAS 重试必须：

* 有界，例如最多重新解释三次。
* 每次 reload 后重新获取当前 UTC 时间。
* 不复用请求开始时的旧时间。
* 不出现无限循环。
* 不越过领域状态机。
* 不直接操作 Attempt。

# 十一、错误契约

建立统一且稳定的错误结构，例如：

```json
{
  "error": {
    "phase": "ADMISSION",
    "code": "RESEARCH_DATASET_NOT_FOUND",
    "detail": "..."
  }
}
```

至少区分：

| 场景                    |     HTTP |
| --------------------- | -------: |
| 非法 Run ID             |      400 |
| 非法或缺失 Idempotency-Key |      400 |
| 请求字段非法                |      400 |
| Specification 非法      |      400 |
| Dataset Snapshot 不存在  |      404 |
| Run 不存在               |      404 |
| 同 Key 不同命令            |      409 |
| 已完成/失败 Run 无法取消       |      409 |
| PostgreSQL 暂时不可用      |      503 |
| 数据库记录损坏               |      500 |
| schema incompatible   | API 拒绝启动 |

要求：

* 领域稳定错误码尽量原样保留。
* 不通过异常字符串分类。
* 不向客户端暴露 stack trace。
* Dataset 不存在和 Dataset 损坏必须区分。
* 数据损坏必须 fail closed，不能伪装成 404 或空结果。
* 不要把所有异常统一映射成一个模糊的 500。

---

# 十二、API 工程结构

避免继续把 Artifact Query 和 Run Command 放入同一个巨大 `routes.py`。

如果符合当前包结构，推荐调整为：

```text
packages/api/onlyalpha-api/src/onlyalpha_api/
├── app.py
├── main.py
├── artifact_main.py
└── research/
    ├── artifacts/
    │   ├── __init__.py
    │   ├── errors.py
    │   ├── routes.py
    │   └── schema.py
    └── runs/
        ├── __init__.py
        ├── errors.py
        ├── routes.py
        └── schema.py
```

提供两个清晰的 App Factory：

```python
create_artifact_query_app(...)
create_research_app(...)
```

要求：

* Portable Artifact Query App 仍然只依赖 Artifact Reader。
* Full Research App 可以组合 Artifact Router 和 Run Router。
* 两个 Router 共存不代表底层服务混合。
* Artifact Query 不依赖 PostgreSQL。
* Run Command 不读取 Artifact 内容。

如果重构现有 API 目录会造成无意义的大量 churn，可以采用更小的等价结构，但必须保持上述边界并通过 architecture tests 固化。

# 十三、启动组合与 CLI

完整 Research API 启动时应：

1. 接受明确的 `user-data-root`。
2. 使用现有 `OnlyUserDataLayout` 推导 Dataset/Artifact 路径。
3. 从 `ONLYALPHA_POSTGRES_DSN` 读取 PostgreSQL DSN。
4. 使用现有 migration authority 检查兼容性。
5. 数据库版本不兼容时拒绝启动。
6. 获取现有 Calculation Registry/Plugin discovery 结果。
7. 构造 Specification Resolver。
8. 构造 Dataset Store。
9. 构造 Artifact Reader。
10. 构造 PostgreSQL Run Store。
11. 构造 Command/Query Services。
12. 创建 FastAPI app。

禁止：

* 从 CLI 参数明文传递数据库密码。
* 输出完整 DSN。
* API 启动时自动迁移数据库。
* API 启动 Worker。
* API 启动 Scheduler。
* API 请求中执行 Research。
* API 自动把长期 QUEUED Run 标记失败。

如果当前 `onlyalpha-api` 是 portable Artifact Query CLI，推荐明确迁移为：

```text
onlyalpha-api
    完整 Research API

onlyalpha-artifact-api
    Portable Artifact Query API
```

项目仍处于 Alpha 阶段，不要增加永久兼容 wrapper。迁移必须更新入口、文档和测试。

如果仓库现有 CLI 命名规范提供了更清晰的方案，应遵循当前规范并说明理由。

## 13.1 网络边界

P8.3 不实现多用户鉴权，因此完整控制 API 默认只能绑定 loopback，例如：

```text
127.0.0.1
```

不得添加 permissive CORS。

本地 Web 开发应优先使用 Vite proxy 或同源反向代理访问 `/api`。

公网暴露、身份认证和权限控制必须留给后续明确阶段。

# 十五、测试要求

所有重要语义必须由自动化测试证明。

禁止：

* `skip`
* `xfail`
* 放宽断言
* 删除失败测试掩盖问题
* Fake Store 冒充 PostgreSQL 并发验证
* 未运行测试却声称通过
* 用 sleep 猜测并发时序
* 只验证 HTTP happy path

## 15.1 领域和应用层单元测试

覆盖：

* UUID4 submission key。
* canonical command fingerprint。
* 同 Key 同命令 replay。
* 同 Key 不同命令冲突。
* 不同 Key 相同 Specification 创建不同 Run。
* replay fast path 不重新 admission。
* Admission 失败时没有持久化。
* Store 失败时不返回成功。
* Cancellation 全状态矩阵。
* CAS 冲突重新解释。
* CAS 重试上限。
* Cursor round trip。
* Cursor 非规范输入。
* 分页顺序。

## 15.2 真实 PostgreSQL 测试

覆盖：

* 空数据库 M1→最新 migration。
* 旧 schema 升级到新 schema。
* 历史 migration checksum 不变。
* 同 Key 并发提交只产生一个 Run。
* 并发冲突不产生孤儿 Run。
* 同 Key 不同命令稳定冲突。
* 不同 Key 相同 Specification 产生两个 Run。
* Run 列表确定性。
* keyset pagination 不重复。
* 新插入不破坏已有 cursor 的后续遍历。
* API/Store 重启后加载相同 Run。
* Cancel 与 claim 竞争。
* Cancel 与 complete/fail 竞争。
* 数据损坏 fail closed。

并发测试应使用明确 barrier/event 控制竞争窗口，避免通过随机 sleep 制造不稳定测试。

## 15.3 HTTP 契约测试

覆盖：

* 路由和方法。
* 202/200/400/404/409/500/503。
* `Location` header。
* CREATED/REUSED。
* body 额外字段。
* 非法 UUID。
* 非法 Idempotency-Key。
* 稳定错误 DTO。
* PostgreSQL 不可用。
* Artifact API 原行为不变。
* OpenAPI 导出。
* TypeScript generated contract。
* portable Artifact App 不需要 PostgreSQL。

## 15.4 Architecture Tests

至少证明：

* `research/command` 不依赖 FastAPI、Pydantic、Uvicorn。
* Domain 不依赖 PostgreSQL/Web。
* Artifact Query 不依赖 Run Store/PostgreSQL。
* Command Service 不读取 Artifact 内容。
* API 不导入 Worker/Scheduler/执行入口。
* Command API 不修改 Attempt/Lease/Fence。
* PostgreSQL schema 不存储 Result/Artifact 内容。
* API 不复制 Specification 语义。
* 历史 migration 不被修改。
* 新边界已进入 impact-aware verification。

# 十六、质量 Lane 和慢检查策略

根据现有 `scripts/test_suite.py` 和 CI 结构增加或调整 `research-command` lane。

建议职责：

```text
research-run
    Run 聚合和状态迁移

research-command
    submit/idempotency/cancel/run query/application/HTTP

research-postgres
    migration/real PostgreSQL/concurrency/CAS

research-query
    Artifact Query API

web
    OpenAPI/TypeScript contract/client
```

具体名称以当前 canonical lane 命名规范为准。

更新 impact rules：

* `research/command/**` → command + run + postgres。
* Run API → command + API contract + web contract。
* PostgreSQL migration → postgres + command。
* Artifact API → query + artifact。
* OpenAPI → API contract + web。

## 16.1 节省时间和 token

开发过程中不要每修改一个文件就运行完整慢测试。

采用分层验证：

### 快速循环

每完成一个小模块，运行：

* 相关 unit tests。
* 相关 contract tests。
* 相关 architecture tests。
* 针对修改文件的 lint/type checks。

### PostgreSQL 阶段

migration/store 完成后运行一次相关真实 PostgreSQL lane。

### API 阶段

运行 API contract、OpenAPI drift 和 Web contract tests。

### 最终本地闭环

代码全部完成后，运行一次与本次变更相匹配的 canonical layered verification。

### GitHub CI

把以下慢任务保留在 CI 或最终阶段，不要本地反复执行：

* 全仓库 coverage。
* CodeQL。
* 完整 recovery/conformance。
* 大范围 build/package。
* 重复的全矩阵环境测试。

但是：

* “慢”不能成为不验证关键 PostgreSQL 并发语义的理由。
* 如果本地环境支持真实 PostgreSQL，必须执行相关 lane。
* 如果某项因客观环境不能运行，必须明确记录“未运行”和原因，不能声称通过。

# 十九、完成标准

P8.3 只有满足以下条件才算完成：

1. 合法 Specification 可以提交。
2. 返回 202 前 Run 已持久化。
3. 返回 `Location`。
4. API 重启后可以查询同一 Run。
5. 相同 Key 和命令返回同一 Run。
6. replay 不重新执行环境相关 Admission。
7. 相同 Key 不同命令返回 409。
8. 不同 Key 相同 Specification 创建不同 Run。
9. 并发相同 Key 只有一个 Run。
10. 并发冲突不产生孤儿 Run。
11. 可以确定性分页查询 Run。
12. `QUEUED` 可以取消为 `CANCELLED`。
13. `RUNNING` 可以提交为 `CANCEL_REQUESTED`。
14. 取消与 claim/complete 竞争时状态合法。
15. API 不操作 Attempt/Lease/Fence。
16. Worker 和 OnlyEngine 不在 API 请求中启动。
17. Artifact API 行为不变。
18. Portable Artifact API 不依赖 PostgreSQL。
19. Result/Artifact 内容没有进入 Command API 或 PostgreSQL。
20. OpenAPI 和 TypeScript contract 同步。
21. migration、unit、contract、architecture、PostgreSQL integration 全部通过。
22. quality impact rules 可以正确选择相关 lane。
23. 没有 skip、xfail 或 Fake PASS。
24. 文档和 Roadmap 与实际代码一致。
25. 未执行的慢检查被明确记录并由 CI 承担。
26. 没有无关重构和第二套平行实现。
