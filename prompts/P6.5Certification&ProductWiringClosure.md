# 任务名称

**P6.5 Certification & Product Wiring Closure**

本任务是 P6.5 的最终产品接线与认证收口。

当前 P6.5 已经建立了大量正确的 durability / recovery 基础设施，包括但不限于：

- Runtime-neutral Checkpoint Kernel
- Runtime-neutral Recovery Kernel
- Runtime Checkpoint Schema v5
- Runtime Persistence Schema v7
- Streaming Semantic Lane
- Streaming Continuity Authority
- Streaming Timer durable state / occurrence journal
- Runtime State Lease
- Post-Recovery Authority Validation
- Recovery Finalizer
- Virtual Broker / Trading Kernel 相关 durable recovery substrate

但是：

**这些能力目前尚未完整接入 SIM 的正式 Runtime Product 生命周期。**

因此，本任务不是重新设计 P6.5，也不是重新实现 checkpoint/recovery。

本任务的唯一目标是：

> 将当前已经实现的 P6.5 durability/recovery substrate 正式接入 SIM Runtime Product，使 `SIM + durable persistence + checkpoint` 成为真正支持 new-process restart/recovery 的正式产品能力，并通过独立 fault/restart certification 和 same-SHA CI 证明其正确性。

最终必须使：

```text
SIM
=
Realtime MarketData
+ LiveClock
+ Event-driven Trading Kernel
+ Virtual Broker
+ Streaming Continuity
+ Durable Checkpoint
+ New-process Recovery
+ Timer Recovery
+ Runtime Single Writer
```

成为**正式、可运行、可测试、可恢复、可认证的产品合同**。

P6.5 Closure 的目标不是：

```text
让程序重新启动
```

而是：

> 一个 SIM Runtime 在任意合法 crash window 后，由一个全新的 OnlyAlpha 进程，以相同 Runtime identity 和 durable state root 重建后，可以重新构造与原 causal history 对应的同一个 canonical trading world。

必须证明：

```text
已提交交易历史不改变
Order identity 不改变
Trade identity 不改变
Transaction identity 不改变

Accepted 不重复产生经济效果
Fill 不重复产生经济效果
Projection 不丢失

Position 一致
Allocation 一致
Account 一致
Reservation 一致
Strategy Ledger 一致
Fee 一致
Settlement 一致

Strategy state 正确
Factor state 正确
Indicator state 正确

Virtual Broker 未完成 deterministic work 正确恢复

Streaming continuity 正确

Timer durable admitted occurrence 正确恢复

downtime missed Timer 不 retroactively trade

recovery 期间不能获得新的 LIVE trading permission

continuity proof 和 authority validation 完成后才允许进入 normal LIVE semantic admission

Runtime lifecycle 不制造 synthetic trading fact

SIM 永远不能进入 Real Broker path
```

# 3. 必须冻结的系统不变量

本任务必须围绕以下 invariants 实现。

---

## 3.1 Single Streaming Semantic Mutation Authority

Streaming Runtime 中：

> 任意时刻最多只能存在一个能够修改 trading/strategy semantic state 的 action。

必须统一串行化：

```text
finalized MarketData semantic action

Strategy on_bar

Timer semantic action

Virtual Broker deterministic due work
belonging to current semantic action

Broker inbound processing belonging
to current semantic action

Transaction commit

Projection completion

required semantic Event delivery

Checkpoint capture/write/verify

Recovery-exclusive semantic execution

STOP cutoff
```

已有 `OnlyStreamingSemanticLane` 或当前等价 abstraction 应继续作为 control/concurrency boundary。

它不得拥有经济业务语义。

依赖方向必须是：

```text
Streaming Runtime
    ↓
Semantic Lane
    ↓
Trading Facade / Trading Kernel
```

禁止：

```text
Trading Kernel
    ↓
Streaming Runtime
```

禁止为了 SIM recovery 在 Trading Kernel 中增加：

```python
if runtime_type == "SIM":
    ...
```

---

# 3.2 Stable Semantic Checkpoint

Checkpoint 必须只发生在：

```text
current semantic action complete

no concurrent semantic mutation

durable execution sequence contiguous

transactions <= covered_execution_sequence
all projection-ready

current semantic broker obligations resolved

required EventBus semantic delivery stable

checkpoint participant state self-consistent

Virtual Broker state consistent
with Trading authorities

Runtime not in an intermediate
unprovable recovery phase
```

不要求：

```text
MarketData inbound queue == empty
Observation queue == empty
future realtime updates == none
partial realtime Bar == none
```

Realtime feed 可以持续到达。

Physical queue empty 不是 semantic correctness invariant。

---

# 3.3 Durable Before Advertised

Checkpoint 必须经过：

```text
capture
→ canonical seal/hash
→ atomic durable write
→ reread
→ validate identity/hash/components
```

才允许成为 advertised durable checkpoint。

尽量复用现有：

```text
OnlyRuntimeCheckpointService
create_verified()
verify_durable()
```

不要创建 SIM-specific checkpoint service。

---

# 3.4 Economic Effect Exactly Once

系统不要求每段 Python code 在 crash 后物理意义上 exactly once execution。

要求的是：

> economic effect exactly once。

例如 recovery 可以重新观察某个事实，但不得：

```text
Accepted economic effect x2
Fill economic effect x2
Position mutation x2
Fee mutation x2
```

继续依赖现有：

```text
durable transaction identity
execution sequence
dedup authority
causal recovery session
projection-ready state
```

实现。

---

# 3.5 Subscribe-first

Streaming new-process recovery 必须：

```text
transport operational
→ subscribe realtime first
→ buffer incoming realtime evidence
→ historical repair
→ merge historical overlap + realtime suffix
→ continuity proof
```

禁止：

```text
historical recovery
→ lengthy local processing
→ subscribe realtime last
```

否则 recovery 自己会制造新的 blind gap。

---

# 3.6 Recovery Cannot Trade

在以下全部完成前：

```text
checkpoint restore
transaction-tail recovery
historical repair
buffered realtime catch-up
timer recovery
continuity proof
post-recovery authority validation
verified recovery checkpoint
```

Strategy 不得获得正常 LIVE trading permission。

Recovery replay 可以恢复已有 semantic state，但不能把 historical/recovery evidence 当成全新的 LIVE signal 再产生第二份经济事实。

---

# 3.7 Fail Closed

以下任何异常必须使 Runtime recovery 失败：

```text
checkpoint schema mismatch
persistence schema mismatch

runtime identity mismatch

config fingerprint mismatch

market composition fingerprint mismatch

participant registry fingerprint mismatch

checkpoint aggregate hash mismatch
component hash mismatch

corrupt durable state

state lease conflict

missing timer callback authority

execution tail unresolved

continuity proof failure

post-recovery authority validation failure

recovery checkpoint verification failure
```

禁止：

```text
silent fallback to memory

silent fresh boot

ignore corrupted checkpoint

ignore old schema

continue running with uncertain authority state
```

# 5. 最重要的 Closure：Runtime Lifecycle 两阶段恢复

当前 Base Runtime lifecycle 必须能够表达：

```text
initialize()
    =
local durable bootstrap

start()
    =
external transport start
+
driver-specific continuity recovery
+
normal processing cutover
```

Streaming 与 Backtest 的区别必须由 polymorphic driver/runtime hook 表达，而不是 `runtime_type` 分支。

---

# 5.1 Local Durable Bootstrap

`initialize()` / `_recover_runtime()` 阶段应完成：

```text
plugin initialize/connect

cluster initialize

acquire/use existing Runtime state authority

load latest checkpoint

if checkpoint exists:
    validate
    restore Runtime checkpoint participants
    restore Trading authorities
    restore Strategy state
    restore Streaming continuity state
    restore logical Timer state
    restore Virtual Broker state
    build execution transaction recovery session
    mark external recovery pending

if no checkpoint exists:
    mark fresh bootstrap
```

注意：

此时 Streaming transport 尚不一定已经正式 start/subscribed。

所以这里不能完成完整 realtime continuity recovery。

---

# 5.2 READY 的含义

对于 Streaming：

`READY` 必须表示：

> Runtime composition 和 local durable state 已经准备好进入 external start/recovery。

它不能错误地表示：

> 已经恢复 realtime continuity，可以正常交易。

正常 LIVE trading permission 必须在 `start()` 后续 recovery closure 中才打开。

---

# 5.3 增加 Runtime-neutral Lifecycle Hook

如果当前 Base Runtime 无法表达以上流程，应增加最小的 neutral hook。

例如概念上：

```python
def _prepare_start(self) -> None:
    ...

def _complete_start_recovery(self) -> None:
    ...
```

具体命名根据当前代码 architecture 决定。

要求：

```text
Backtest:
    mostly no-op / existing semantics

Streaming:
    start/authenticate/subscribe
    establish realtime buffer
    complete external recovery
```

Base `OnlyRuntime` 不得 import streaming/sim/backtest-specific implementation。

禁止：

```python
if self.runtime_type == "SIM":
```

# 10. Streaming New-process Recovery 完整产品流程

最终正式流程应等价于：

```text

1. Acquire Runtime state lease

2. Compose same SIM Runtime

3. initialize/connect resources

4. Local durable restore

   ├─ Strategy/Factor/Indicator
   ├─ Streaming continuity frontier
   ├─ Logical timers
   ├─ Virtual Broker deterministic state
   └─ Transaction recovery session

5. Enter READY
   external recovery pending

6. Start external resources

7. Authenticate if required

8. SUBSCRIBE REALTIME FIRST

9. Incoming realtime facts enter recovery buffer

10. Determine checkpoint frontier
    and recovery target

11. Historical repair from durable frontier

12. Resolve execution durable causal tail

13. Recover durable admitted Timer occurrences

14. Merge historical overlap
    with buffered realtime suffix

15. Deduplicate overlap

16. Advance canonical continuity frontier

17. Prove continuity

18. Reconcile timer downtime semantics

19. Post-recovery authority validation

20. Capture recovery checkpoint

21. Atomic write

22. Reread + verify durable recovery checkpoint

23. Open normal semantic trading permission

24. Rearm future logical timers at correct boundary

25. RUNNING
```

具体顺序可以根据代码 architecture 做小范围调整，但必须满足所有 causal invariants。

# 11. Subscribe-first Recovery

必须设计恢复期 realtime ingress。

要求：

```text
subscribe
→ realtime evidence immediately accepted into recovery buffer
```

但：

> recovery buffer 不是 durable authority。

它只是 operational evidence buffer。

如果 Process B 在 catch-up 前再次 crash：

```text
recovery buffer 可以丢弃
```

Process C 重新：

```text
subscribe-first
+
historical repair
```

即可重建。

因此禁止 checkpoint：

```text
MarketData queue
recovery buffer
subscription ID
partial live Bar
```

# 15. Stable Checkpoint Cadence

P6.5 V1 采用 correctness-first checkpoint policy。

不要实现：

```text
background async checkpoint

random periodic checkpoint

10-minute checkpoint

stop-only checkpoint

heuristic batching
```

Checkpoint-enabled SIM 至少：

```text
Closed-Bar Semantic Action
→ Stable Semantic Boundary
→ Verified Checkpoint
→ release next semantic permission
```

以及：

```text
Timer Semantic Action
→ Stable Semantic Boundary
→ Verified Checkpoint
```

Recovery 过程中：

禁止每 replay 一根 historical Bar 就写 checkpoint。

只允许：

```text
historical repair complete
+
transaction tail resolved
+
timer recovery complete
+
buffered realtime catch-up complete
+
continuity proof
+
authority validation
```

之后产生：

```text
Verified Recovery Checkpoint
```

# 16. Checkpoint 必须在 Semantic Exclusivity 内

不要让 background thread 与 semantic action 并发 capture checkpoint。

正确模型：

```text
SemanticLane exclusive action
    │
    ├─ semantic processing
    ├─ broker/execution completion
    ├─ stable-boundary proof
    ├─ checkpoint capture
    ├─ checkpoint write
    └─ durable verify
```

完成之后才能释放 semantic permission。

具体实现可以封装 helper，但：

- Semantic Lane 只拥有 concurrency/control；
- Runtime orchestration 决定 checkpoint policy；
- Trading Kernel 不得知道 Streaming checkpoint cadence。

---

# 17. Timer Recovery 必须完整闭环

Timer 是本阶段 correctness 的核心组成部分。

原因：

```text
Timer callback
→ arbitrary Strategy state mutation
→ maybe submit Order
```

Transaction tail 不能独立恢复 arbitrary Strategy state。

---

# 17.1 Timer 三类恢复情况

### A. Timer occurrence 已被 checkpoint 覆盖

不要重新执行。

---

### B. Timer occurrence 已 durable admitted，但 checkpoint 未覆盖

这是：

```text
incomplete semantic action
```

必须通过 durable occurrence evidence 恢复这个 semantic action。

依赖已有：

```text
transaction identity
execution recovery
dedup/idempotency
```

保证没有重复 economic effect。

---

### C. Downtime 内本应触发，但从未 durable admitted

例如：

```text
crash 10:30
one-shot timer due 10:45
restart 11:00
```

不得：

```text
restart 后 retroactively execute
10:45 strategy callback
```

它必须成为：

```text
MISSED
```

或当前等价逻辑状态。

对于 recurring timer：

恢复未来 schedule，而不是补跑停机期间所有 callback。

---

# 17.2 Timer Rearm Timing

restore checkpoint 后不要立刻 rearm wall-clock callbacks。

正确阶段：

```text
restore timer definitions

recover durable admitted occurrences

complete market continuity recovery

prove continuity

resolve downtime missed timers

rearm valid future timers

open normal LIVE trading
```

必须防止：

```text
recovery still running
+
LiveClock fires
+
new Strategy callback
```

---

# 18. Virtual Broker Recovery

SIM Virtual Broker 是正式 deterministic execution authority，不是 disposable mock。

必须保证：

```text
same unfinished Order identity

same deterministic future execution behavior

same dedup authority

same broker-side outstanding state
```

例如：

```text
Order A accepted
→ future fill pending
→ crash
```

新进程不能：

```text
Accepted A again

fill A twice

lose pending fill

change fill identity

silently terminalize A
```

检查当前 Virtual Broker checkpoint participant / reconstructible evidence。

优先复用现有实现。

不要 checkpoint Python Broker object。

---

# 19. Recovery Finalizer

所有恢复必须最终进入 Common Finalizer。

目标：

```text
Driver Recovery Complete
    ↓
Semantic Quiescence Proof
    ↓
Post-Recovery Authority Validation
    ↓
Verified Recovery Checkpoint
    ↓
Mark Recovered
    ↓
Normal LIVE Admission
```

Recovery finalizer 不得生成 trading fact。

它只能：

```text
validate
seal
persist
verify
transition lifecycle authority
```

---

# 20. Crash During Recovery

必须保证：

如果 crash 于：

```text
historical repair halfway

transaction recovery halfway

timer recovery halfway

buffered catch-up halfway

continuity proof before completion

authority validation failure
```

不得留下 advertised new checkpoint。

下一进程仍从最后一个完整 durable checkpoint 开始。

---

# 21. Crash During Checkpoint Write

保留/验证现有 write ambiguity contract：

```text
write raises
```

不代表：

```text
durable commit definitely did not happen
```

如果当前 Recovery Finalizer 已在 write exception 后重新读取验证 durable checkpoint：

保留并测试。

必须区分：

```text
CHECKPOINT_WRITE_FAILED

vs

CHECKPOINT_COMMITTED_BUT_FINALIZATION_INTERRUPTED
```

或当前等价错误合同。

# 49. 最终设计原则

整个实现过程中不断检查：

```text
Checkpoint
!= process snapshot

Recovery
!= replay everything

Queue
!= authority

Wall Clock
!= Timer semantic authority

Subscription
!= canonical state

Runtime Product
!= Trading semantics

Crash recovery
!= fresh boot fallback

Verified durable checkpoint
=
last advertised canonical trading world
```

最终目标不是：

> “SIM 可以从 checkpoint 文件启动。”

最终目标是：

> **SIM 已经成为一个正式的、单 writer 的、Streaming durable Runtime Product：在任意受支持 crash window 后，可以由一个全新的进程利用 durable canonical state、transaction tail、Timer evidence 和 external market continuity，恢复到同一个 canonical trading world，并且只有在 continuity 与 authority 均被证明后才恢复正常交易权限。**

只有达到这个标准，才能将 P6.5 标记为 DONE，并开始：
